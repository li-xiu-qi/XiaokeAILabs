# JSON、JSONL、XLSX 和 SQLite：存储体积、读写速度与索引开销实测

> **阅读导航**：[数据结构与存储成本](README.md) · [数据结构算法实测与复现](../../../experiments/data-structure-costs/README.md)

在数据工程、日志归档与本地知识库构建中，同一批结构化记录可以保存为标准的 JSON 数组、逐行追加的 JSONL、人工易读的 Excel（XLSX）电子表格，或是具备结构化查询能力的 SQLite 数据库文件。

选择存储载体时，核心工程考量不仅是“文件体积谁更小”，还包含**全量解析与流式消费的内存与耗时差异、末尾追加的单次 I/O 开销，以及建立索引带来的文件体积膨胀倍率**。

下述结果来自合成数据和特定脚本。现存记录包含部分测量输出，但未完整记录运行环境、缓存状态和重复次数；表中耗时只说明本次测量，不能作为不同格式的一般性能排名。

## 一、 体积与读写耗时：JSON、JSONL 与 XLSX 对照

在相同数据源（行数、列数与候选值池严格一致，随机种子 17）下，对比四种格式在不同数据分布下的落盘体积与读写性能：

| 评估维度 | 指标项 | XLSX（电子表格） | JSON（常规行式） | JSON（列式压缩） | JSONL（按行存储） | 核心工程启示 |
|---|---|---|---|---|---|---|
| **常规业务数据**<br>（低重复文本） | 落盘文件体积 | **8.27 MB** | 16.07 MB | 11.44 MB | 16.07 MB | XLSX 压缩机制占优，体积仅为 JSON 的 51% |
| | 全量读取耗时 | **25.53 s** | **0.24 s** | 0.11 s | 0.64 s | JSON 读盘快 **106 倍**；XLSX 遭遇严重 CPU 瓶颈 |
| | 末尾追加 1 行 | / | 0.98 s | / | **0.0008 s** | JSONL 追加比重写 JSON 快 **1200 倍** |
| | 流式读前 1000 行 | / | / | / | **0.0075 s** | 内存仅占用 1.9 MB（JSON 全量加载需 76.5 MB） |
| **枚举高重复数据**<br>（高频词项） | 落盘文件体积 | **5.86 MB** | 35.48 MB | 22.89 MB | 35.48 MB | 共享字符串表让 XLSX 体积优势扩大到 **6.1 倍** |
| | 全量读取耗时 | **51.17 s** | **0.42 s** | 0.21 s | 0.80 s | JSON 读盘快 **121 倍** |
| | 末尾追加 1 行 | / | 2.25 s | / | **0.0006 s** | JSONL 耗时不到 1 毫秒（近 3700 倍差距） |
| | 流式读前 1000 行 | / | / | / | **0.0061 s** | 内存仅占用 2.2 MB（JSON 全量加载需 174.0 MB） |

## 二、 XLSX 读取耗时的估算边界

一次 200 万单元格测试的记录给出 ZIP 解压 0.17 秒、读取耗时减去解压耗时约 50.84 秒。脚本分别测量一次 ZIP 读取和一次完整表格读取，然后用两者相减；它没有对同一次读取做分阶段采样。这个差值包含除解压之外的多种开销，不能证明 XML 解析耗时占比，也不能据此确定 CPU 瓶颈。

## 三、 SQLite vs XLSX：存储体积与索引膨胀

将数据存入 SQLite 可以获得毫秒级的结构化查询能力，但数据库页格式与 B-Tree 索引会带来显著的体积开销。

### 1. 不同数据类型下的体积膨胀基线（50,000 行数据）

| 数据分布特征 | XLSX 压缩体积 | SQLite 体积（无额外索引） | SQLite 相对 XLSX 膨胀倍率 |
|---|---|---|---|
| **常规业务数据** | 8.26 MB | 9.80 MB | 1.2x |
| **长文本不可去重数据** | 35.55 MB | 48.95 MB | 1.4x |
| **枚举高重复数据** | 5.86 MB | 18.66 MB | **3.2x** |

### 2. 索引数量对 SQLite 存储体积的放大效应（50,000 行 × 20 列）

| 建立索引数量 | SQLite 数据库落盘体积 | 相对无索引体积增长 | 相对原始 XLSX 体积膨胀 |
|---|---|---|---|
| **0（仅主键）** | 9.33 MB | 基准（100%） | 3.2x |
| **3 个单列索引** | 11.69 MB | +25.3% | 4.0x |
| **10 个单列索引** | 17.18 MB | +84.1% | 5.9x |
| **20 个全列索引** | **25.04 MB** | **+168.4%** | **8.5x** |

**工程权衡**：每增加一组 B-Tree 索引，SQLite 都需要为每个键值维护叶子节点与指针页。当 20 个字段全部建立索引时，文件体积膨胀近 8.5 倍。索引设计应严格按高频查询字段按需建立，杜绝盲目全列索引。

## 四、 SQLite 毫秒级查询实测（5,000 行 × 8 列）

在导入 SQLite 后，测试不同查询操作的实际延迟：

| 查询类型 | SQL 操作语义 | 无索引延迟 | 建立索引后延迟 | 提速效果 |
|---|---|---|---|---|
| **单行主键点查** | `SELECT * WHERE id = ?` | 0.8 ms | **0.3 ms** | 提速约 2.7 倍 |
| **数值范围过滤** | `SELECT * WHERE val1 BETWEEN ? AND ?` | 0.4 ms | **0.2 ms** | 提速约 2.0 倍 |
| **分组聚合统计** | `SELECT cat, SUM(val1) GROUP BY cat` | 1.6 ms | 1.2 ms | 提速约 25% |
| **全表求和** | `SELECT SUM(val1) FROM t` | 0.4 ms | **0.2 ms** | 提速约 2.0 倍 |
