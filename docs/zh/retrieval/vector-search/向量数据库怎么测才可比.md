# 向量数据库评测方法

> 阅读导航：[检索与排序](../README.md) · [向量搜索导览](README.md) · [向量索引与近邻搜索](向量索引与近邻搜索.md) · [向量数据库架构与选型](向量数据库架构与选型.md) · 代码实践：[`vector-db-benchmark`](../../../../experiments/vector-db-benchmark/)

在评估不同向量数据库或近邻索引的性能表现时，业界公开基准常因度量边界不一致而得出失真结论：例如将 Docker 容器内存与宿主 Python 进程内存混同对比、在未对齐召回率的前提下单比响应延迟，或是使用均匀分布的随机合成向量脱离真实业务。关于不同部署架构与底层索引原理，参见 [向量数据库架构与选型](向量数据库架构与选型.md)。为了使对比具备真实的工程决策与复核价值，评测设计必须在同一召回率门槛下严格锁定资源度量边界、内存统计口径与混合检索流程。本文系统梳理向量数据库公平对比的五项核心判据与可复核实验设计标准。

---

## 一、概念与问题概述

### 1. 向量数据库评测的常见偏误

在评测实践中，最常出现的误导性对比包括三类：
1. **脱离召回率单比延迟**：A 数据库默认配置下 Recall@10 为 0.98、延迟 8 ms；B 数据库默认配置下 Recall@10 仅为 0.65、延迟 2 ms。脱离召回精度宣布 B 性能领先是不成立的；
2. **内存统计边界混淆**：把 Docker 容器的整体常驻内存（包含守护进程、文件系统缓存与运行时环境）与单机轻量库的宿主进程 RSS 内存直接并列比较；
3. **合成数据与真实文本向量分布差异**：纯高斯或均匀分布的随机浮点向量没有真实的语义聚类结构，无法反映图索引或倒排桶在长尾聚类下的真实探测效率。

### 2. 真实近邻召回率（Recall@k）基准设定

近似最近邻（ANN）检索以部分精度损失换取计算加速。评测时必须首先使用暴力穷举搜索（Flat）计算出欧氏距离或余弦内积的前 $k$ 项精确真值集合（$\text{Exact}_k$）。对于近似索引返回的候选集合 $\text{ANN}_k$：

$$\operatorname{Recall@}k = \frac{|\text{ANN}_k \cap \text{Exact}_k|}{k}$$

只有将各候选数据库的参数（如 HNSW 的 `efSearch`、IVF 的 `nprobe`）调节至完全相同的召回率基准线（如统一锁定在 $\operatorname{Recall@}10 \ge 0.95$ 或 $0.98$）时，所测量的查询吞吐（QPS）与响应延迟（P50、P99）才具备同条件可比性。

## 二、核心原理

### 1. 四大多维物理度量口径（下载、安装、存储与运行内存）

评估系统资源占用时，不能使用笼统的“空间占用”表述，必须拆解为四个独立的工程度量口径：

| 度量口径 | 测量物理对象 | 对应实际工程问题 |
|---|---|---|
| **下载体积** | Wheel 包、二进制归档或 Docker 镜像拉取字节数 | 部署分发开销与冷启动镜像拉取耗时 |
| **安装体积** | 解压后文件系统实际占用的静态磁盘字节数 | 容器镜像层或虚拟机基础磁盘配额 |
| **存储增量** | 写入 $N$ 条向量及对应标量元数据后，数据目录的磁盘增量 | 持久化硬件扩容与存储备份成本 |
| **运行内存** | 建立并加载索引后服务稳定运行的物理内存峰值（RSS） | 内存配额预算与单机最大可承载向量规模 |

### 2. 同一召回率门槛下对比延迟与吞吐原则

正确对比方法应绘制 **Recall-Latency Pareto 前沿曲线**：
- 在不同探测宽度下记录一系列 `(Recall@k, Latency)` 坐标点；
- 在固定召回率阈值（如 0.95）切面处，提取并比较各方案的 P99 延迟；
- 避免仅凭单一默认配置给出的单点数据断言优劣。

### 3. 内存测量环境边界：进程 RSS vs 容器 cgroup vs mmap

在对比嵌入式引擎（如 sqlite-vec、LanceDB）与专用服务端（如 Qdrant、Milvus）时，必须明确内存观测通道：
- **容器 cgroup vs 宿主 RSS**：Docker 容器的内存包含守护进程、文件系统缓存与语言运行时；嵌入式引擎的内存直接体现于宿主应用进程的物理常驻集（RSS）。两者不能直接并列；
- **内存映射（mmap）机制的隐性开销**：采用 mmap 的列式引擎（如 LanceDB）在低物理内存下可依赖操作系统缺页换页运行。仅统计 RSS 会低估其在高频并发热点访问下的磁盘 I/O 压力；
- **基线扣除与压实确认**：测量必须在写入前后分别采样，使用净增量作为评估依据，并等待后台索引合并与压缩（Compaction）彻底完成。

## 三、工程代价与加速方案

### 1. 静态单次查询 vs 持续高并发读写性能相变

许多评测仅在写入完成后进行纯静态只读查询测试。但在生产环境中，数据持续写入与近实时索引更新会引发锁竞争与后台线程争抢：
- 测试需覆盖持续并发写入的同时执行高并发查询（混合读写场景）；
- 记录写入吞吐（Vectors/sec）对查询 P99 延迟的拖慢比率。

### 2. 标量过滤对图遍历效率的实际拖慢测定

单纯的纯向量近邻搜索并不能反映生产负载。测试必须引入带有选择率阶梯（如过滤保留 100%、10%、1%、0.1% 数据）的标量联合查询：
- 评估数据库在预过滤（Pre-Filtering）下是否会导致图遍历连通性中断；
- 测量带过滤条件相比纯向量检索的额外延迟放大倍数。

### 3. 双路混合检索与倒数排名融合（RRF）代价

生产检索常结合文本 BM25 与向量稠密检索。在评测混合检索吞吐时，通常基于倒数排名融合（Reciprocal Rank Fusion, RRF）：

$$\operatorname{RRF\_Score}(d \in D) = \sum_{m \in M} \frac{1}{k + r_m(d)}$$

其中 $M$ 为参与检索的通道集合（如 BM25 与稠密向量），$r_m(d)$ 是文档 $d$ 在通道 $m$ 中的排名，平滑常量 $k$ 通常设为 60。评测需核查双路并行召回与打分合并带来的额外服务端调度延迟。

## 四、选型指南与协同架构

### 1. 可复核向量数据库对比基准测试清单

规范的基准评测报告应完整固化以下元数据：
1. **数据清单**：向量维度（如 768 或 1024）、数值精度（FP32/FP16/INT8）、L2 归一化状态、文档与查询样本量；
2. **硬件环境**：CPU 型号与物理核数、内存规格、NVMe SSD 连续/随机读写带宽、操作系统与内核版本；
3. **引擎版本与参数**：Docker 镜像 SHA-256、索引构建参数（如 HNSW 的 $M$ 与 $efConstruction$）、在线查询参数（$efSearch$）；
4. **原始指标存档**：完整保留每个查询的逐项耗时、返回 ID 列表与计算脚本，支持第三方独立复算。

### 2. 数据集真实分布对评测有效性的约束

严禁仅使用随机合成向量作为唯一评估输入。推荐采用开放领域真实文本向量数据集（如 Cohere Wiki-1M、SciFact、MS MARCO）与特定垂直业务领域向量混合构成评测集，以真实反映语义空间的局部高维拓扑聚集性。
