# 向量数据库架构与选型

> 阅读导航：[检索与排序](../README.md) · [向量搜索导览](README.md) · [向量索引与近邻搜索](向量索引与近邻搜索.md) · [向量数据库评测方法](向量数据库怎么测才可比.md) · 代码实践：[`vector-db-benchmark`](../../../../experiments/vector-db-benchmark/)

在构建知识库问答与大模型检索增强（RAG）系统时，工程团队常面临从数万到数亿条高维向量的持久化存储与毫秒级检索诉求。脱离具体业务部署场景孤立讨论跑分排名往往导致选型失真。实际生产落地中，决定架构选型的关键在于部署形态（进程内嵌入式、单机专用服务还是分布式集群）、标量属性过滤机制以及与既有存储基础设施的集成复杂度。关于底层近邻索引与内存开销推导，参见 [向量索引与近邻搜索](向量索引与近邻搜索.md)。本文系统剖析三类向量数据库部署架构的内部查询路径、标量混合过滤代价与工业选型决策矩阵。

---

## 一、概念与问题概述

### 1. 向量数据库的核心职责与传统关系库差异

传统关系型或文档数据库基于 B-Tree 或 LSM-Tree 进行等值或范围精确匹配；向量检索则是高维空间中的非精确近邻（ANN）拓扑搜索。
通用向量数据库的核心职责包括：
- **高维连续向量存储与生命周期管理**；
- **近似近邻（ANN）索引的并行构建与动态更新**；
- **标量属性（Payload）与高维向量的联合过滤查询**。

### 2. 三种部署形态与底层查询执行路径

向量数据库大致可以划分为进程内嵌入式、单节点专用服务以及分布式存算分离集群三类形态，不同形态在网络协议栈、进程边界与调度开销上差异显著：

```mermaid
flowchart TD
    subgraph 进程内嵌入式
        E1[应用程序进程] -->|C ABI / 共享内存| E2[虚拟表或嵌入引擎]
        E2 -->|本地磁盘 / mmap| E3[数据与索引文件]
    end

    subgraph 单节点专用服务
        S1[客户端应用] -->|TCP / HTTP / gRPC| S2[服务进程 API]
        S2 -->|多线程调度| S3[内存索引与分片]
        S3 -->|POSIX 块存储| S4[向量与 Payload]
    end

    subgraph 分布式集群
        D1[客户端] -->|负载均衡| D2[Proxy / 网关]
        D2 -->|元数据路由| D3[查询节点 QueryNode]
        D3 -->|分布式并行读取| D4[Segment 向量索引]
        D4 <--> D5[对象存储 / 共享持久层]
    end
```

## 二、核心原理

### 1. 进程内嵌入式架构（sqlite-vec、LanceDB）

- **运作机制**：作为链接库或扩展插件直接常驻应用程序内部。查询过程直接在应用进程地址空间或通过内存映射（mmap）读取磁盘数据，无网络协议开销；
- **代表选型**：`sqlite-vec`（为 SQLite 原生打造的轻量 C 扩展）、`LanceDB`（基于 Lance 列式格式打造的单机/嵌入式引擎）；
- **优劣权衡**：部署零门槛、单次查询无需网络序列化（延迟亚毫秒级）；但在高写入并发下受制于单机进程锁，且难以进行多节点横向扩容。

### 2. 单节点专用服务架构（Qdrant、Milvus Standalone）

- **运作机制**：作为独立守护进程常驻运行，通过 gRPC 或 RESTful 协议向应用层提供标准 API。内部维护专门的连接池、并发查询线程池、属性倒排过滤与 HNSW 内存索引；
- **代表选型**：`Qdrant`（Rust 编写，支持单向量与多向量混合存储与精密过滤）、`Milvus Standalone`（单机容器化运行）；
- **优劣权衡**：业务逻辑与数据存储解耦，支持高并发线程调度与持久化快照；引入微弱网络延迟（约 0.5~2 ms），需独立监控服务器内存水位。

### 3. 分布式存算分离架构（Milvus Distributed）

- **运作机制**：将系统解耦为协调接入层（Proxy）、日志流消息队列（Log Broker）、无状态向量检索计算节点（QueryNode）以及底层持久化对象存储（MinIO / S3）。
- **代表选型**：`Milvus Distributed`、大型 Qdrant 分布式集群；
- **优劣权衡**：支持海量向量（亿级至数十亿）水平扩展、多租户隔离与容灾备份；但系统组件繁多，运维复杂度极高，在小数据量下代理转发开销反而显著高于单机执行。

## 三、工程代价与加速方案

### 1. 标量属性预过滤 vs 后过滤的截断代价

在真实业务查询中，几乎所有检索都伴随权限范围、时间区间或类别标签的过滤（如 `user_id = 123 AND date >= 2026-01-01`）：
- **后过滤（Post-Filtering）**：先跑 HNSW 找出 Top-100 近邻向量，再剔除不满足标量属性的文档。若满足条件的文档在高维空间中高度稀疏，后过滤会导致最终返回结果不足甚至为空；
- **预过滤（Pre-Filtering / Single-Stage Filtering）**：在图遍历或倒排遍历的同时直接结合标量位图（Bitmap）进行剪枝（如 Qdrant 的过滤感知图遍历）。此方案保证返回充足有效结果，但对底层图结构的连通性有较高要求。

### 2. 向量索引内存驻留与磁盘外存技术（DiskANN）

HNSW 等图索引需要将全量向量及邻居边拓扑常驻内存，每百万 1024 维向量需要 4~8 GB 内存。针对超大规模场景，现代数据库引入了 **DiskANN** 技术：
- 仅将量化压缩码或压缩图导航骨干放入内存；
- 原始向量保留在 NVMe SSD 固态硬盘上，通过异步直接 I/O（Direct I/O）在检索末端执行快速读取与距离重排，大幅压缩单机硬件内存成本。

### 3. 数据写入并发与索引动态构建的锁开销

在持续高写入吞吐场景下，实时构建 HNSW 邻居指针需要加锁，会严重拖慢批量插入速度。
成熟数据库通常采用**分段合并机制（LSM-like Segments）**：新写入的向量首先写入未建立索引的追加缓冲区（Growing Segment），支持暴力扫描查询；当积累到阈值后再异步转为只读块并在后台线程构建 HNSW 索引。

## 四、选型指南与协同架构

### 1. 业务场景驱动的选型矩阵与核心决策树

| 业务场景特征 | 推荐优先选型 | 核心验证门槛 |
|---|---|---|
| **单机嵌入、已有 SQLite 体系、边缘设备** | **sqlite-vec** | 随数据量增长至十万级时的全量检索延迟 |
| **Python 分析流水线、列式持久化、单机分析** | **LanceDB** | 磁盘 mmap 读取吞吐与多列混合过滤效率 |
| **生产级中等规模业务（< 5000 万）、精密标量过滤** | **Qdrant** | 属性过滤对近邻召回率的影响、HNSW 内存占用 |
| **海量分布式环境（> 1 亿）、多租户集群、对象存储结合** | **Milvus** | 生产集群组件运维成本、分片路由与查询负载均衡 |

### 2. 生产级向量数据库基准测试三原则

在进行 PoC 选型测试时，应坚守以下原则：
1. **脱离召回率不谈延迟**：测试时必须固定相同的 Recall@k 阈值（如 Recall@10 ≥ 0.95），在此基准下比较 QPS 与 P99 响应耗时；
2. **使用真实业务分布向量**：随机生成的均匀合成向量无法反映真实文本向量的局部簇状集聚与各向异性分布；
3. **区分静态查询与并发写入**：测试应涵盖带标量过滤、高并发并发写读交织以及单机冷启动加载状态。关于如何搭建可复核的公平对比环境，参见 [向量数据库评测方法](向量数据库怎么测才可比.md)。
