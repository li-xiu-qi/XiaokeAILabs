# 检索模型与方法全景

> **阅读导航**：[检索与排序](README.md) · [检索系统全景与评估](检索系统全景与评估.md) · [知识蒸馏与软标签监督](知识蒸馏与软标签监督.md)

搜索“哪些论文研究药物对心脏的副作用”，系统既可以匹配药物名和“心脏”等词，也可以寻找语义相近的摘要；找到候选后，还可以让模型逐篇判断相关性。这些方法使用的信息、计算方式和适用范围不同，通常可以组合。

下面的地图按**检索时如何产生匹配信号**组织。它是主要方法的阅读地图，不代表穷尽所有研究，也不是按模型发布时间排列的排行榜。

常见组合是多路召回、融合、可选重排序，再返回结果。决策与流程控制、输入模态、训练监督及评估成本是横跨不同方法的维度。

这几项并非互斥：多向量模型也可能用于重排序；图像检索可以使用单向量或多向量；生成式检索与生成式重排序也分别解决候选查找和候选排序问题。微调与蒸馏是训练方式，不是与这些模型并列的检索类型。

## 主要方法怎么比较

| 方法 | 怎么表示和匹配 | 检索路径与适用场景 | 主要代价或限制 |
|---|---|---|---|
| 词项匹配 | 根据查询和文档中的词项及统计权重计分，如 BM25 | 倒排索引快速定位包含词项的文档；适合名称、型号和术语等精确线索 | 同义表达和分词差异可能影响匹配 |
| [学习式稀疏检索（SPLADE）](sparse/学习型稀疏检索与SPLADE.md) | 模型学习词表上的稀疏权重，也可为文本扩展相关词项，如 SPLADE | 用稀疏表示匹配，可利用倒排索引；结合学习能力与词项空间 | 扩展出的词项未必可靠；稀疏度与索引成本需要权衡 |
| 单向量稠密检索 | 查询和文档各编码成一个稠密向量，通过点积或余弦相似度计分，如 DPR、E5、BGE | 文档向量可预计算，借助精确或近似向量索引找候选；适合大规模语义召回 | 单向量需压缩信息；领域变化、精确约束及近似索引误差都影响效果 |
| 多向量后期交互 | 查询和文档各输出多个向量，再对向量间的匹配结果聚合，如 ColBERT 的 MaxSim | 文档向量可预计算，可结合索引做召回或对候选打分；适合需要细粒度匹配的场景 | 向量更多，存储、候选筛选和匹配开销要单独评估 |
| 交叉编码器重排序 | 查询和候选一起输入模型，直接输出相关分数，如 BERT 段落重排序 | 通常对第一阶段召回的有限候选逐对打分 | 计算量随候选数增长；不能找回第一阶段遗漏的文档 |
| 生成式检索 | 模型从查询生成文档标识或其他可映射结果，如 DSI | 通过生成过程获取候选，而非直接比较预存文档向量 | 文档标识设计、语料更新、生成约束及大规模扩展都需要考虑 |

这些是结构上的差别，不代表某类方法在所有数据上必然更准、更快。论文和实际系统采用的模型、硬件、数据及评测方法不同，结果不能跨条件直接排名。

### 主流检索范式工程维度对比

下表横向对照四类最具代表性的检索技术在工程落地维度的关键特征，供整体方案选型参考：

| 评估维度 | 传统无监督稀疏（BM25） | 学习型稀疏表示（SPLADE） | 单向量稠密检索（Dense Embedding） | 晚期交互多向量（ColBERT） |
|---|---|---|---|---|
| **核心机制** | 统计词频与倒排相交 | 神经全词表打分 + 词项扩展 | 序列均值/CLS 池化投影至低维空间 | 每个 Token 独立保留向量，查询逐 Token 聚合行最大值（MaxSim） |
| **向量维度** | $|V| \approx 30,000$（离散稀疏） | $|V| \approx 30,000$（连续稀疏） | $D \in [512, 1024]$（连续稠密） | $L \times D$（每文档一组 128 维向量） |
| **底层索引技术** | 传统倒排索引（Lucene/WAND） | 传统倒排索引（Lucene/Block-Max WAND） | 近似近邻向量索引（HNSW / IVF-PQ） | 残差质心倒排（PLAID） |
| **内存与存储开销** | 低（仅存整型 ID 与频次） | 低至中等（比 BM25 增加约 2 到 3 倍） | 高（数千万向量常驻内存，需数十 GB） | 很高（海量 Token 向量即使残差压缩也需要大内存） |
| **词汇不匹配容忍度** | 差（无字面交集则分数为 0） | 好（模型自动扩展近义词项） | 很好（连续语义空间平滑过渡） | 很好（细粒度 token 级软对齐） |
| **专有名词/型号精准度** | 高（精确匹配） | 高（保留字面词的主干权重） | 较弱（易产生语义偏移或近似混淆） | 高（兼顾局部细节与语义匹配） |
| **结果可解释性** | 完全可解释（词项打分可精确回溯） | 较好（可明确列出扩展词及其权重） | 较弱（仅余弦相似度浮点数，不易归因） | 较好（可回溯到具体 Token 对的打分） |

## DSI 和 LLM 有什么关系

假设用户搜索“哪些论文研究药物对心脏的副作用”：

| 方式 | 模型或系统做什么 | 输出与边界 |
|---|---|---|
| LLM 直接回答 | 根据输入和模型参数生成回答 | 可以生成论文名称或摘要，但不会自动保证论文存在，也不保证来自指定文档库 |
| DSI 生成式检索 | 模型经过检索训练，将查询映射为指定语料中的文档标识，例如 `doc-1024` | 用标识查取对应文档；标识本身不是文档内容，也不保证检索一定正确 |
| LLM 配合外部检索 | 调用关键词、向量或其他检索系统找到文档，再让 LLM 利用文档回答 | 检索由外部系统完成，回答仍需评估是否得到所给文档支持 |

LLM 是模型类别，DSI 是检索方法。DSI 原论文使用 Transformer 学习文档内容与标识之间的关系，再根据查询生成相关文档标识；也可以探索用 LLM 实现类似方法。使用 LLM 并不自动构成 DSI，调用外部索引也不等于模型自己充当索引。见 [Differentiable Search Index](https://arxiv.org/abs/2202.06991)。

## 决策模型如何参与检索

检索不仅要计算文档相关性，还要决定采用哪条路径、是否继续搜索，以及找到的内容是否足以回答问题。决策模型可以对给定选项输出选择或分数，参与这些环节。它描述的是**模型承担的决策任务**，与上面的表示和匹配方式不是同一分类轴；例如，一个模型判断查询与文档是否相关，并按分数排序时，也在承担重排序器的工作。

| 位置 | 决策问题 | 作用与边界 |
|---|---|---|
| 检索前路由 | 不检索、单次检索还是多步检索？ | 按问题调整路径和成本；路由错误可能漏掉必要证据 |
| 候选重排序 | 该文档是否满足查询？A 和 B 哪个更相关？ | 对候选逐项或成对判断后排序；不能找回候选集之外的文档 |
| 检索后判断 | 已有证据是否足够，是否需要补搜？ | 发现低质量检索结果并触发补救；判断分数需要评估与校准 |
| 分层导航 | 当前应探索哪些主题、文档或段落？ | 沿语料结构逐层缩小搜索范围；过早剪枝会丢失相关内容 |

以 Jev 这类模型为例，可以把问题和候选文档输入模型，询问文档是否满足需求，再按输出分数排序。这与交叉编码器重排序在功能上有重叠；模型结构、训练方法、分数含义和推理成本仍可能不同。输出概率并不保证校准良好，也不保证用于所有领域都有效。

已有研究展示了不同用法：

- [Decision Models as L2 Rerankers](https://www.preprints.org/manuscript/202610.1359) 使用 Jev 对商品候选逐项判断，在 ESCI 和 WANDS 上报告了相对于向量排序的 P@10 提升；在其 ESCI 设置中优于所测 Qwen3-Reranker，另一开源决策模型则没有超过随机排序。该论文是预印本，结果及成本取决于数据、候选和部署设置。
- [DecisionRAG](https://arxiv.org/abs/2610.35868) 使用决策模型沿事先构建的语料层级逐层选择分支，在论文设置中与稠密检索加重排序的完整流程进行对比。这是不同系统之间的比较，不能将差异全部归因于模型；错误剪枝也会限制召回。
- [Adaptive-RAG](https://aclanthology.org/2024.naacl-long.389/) 根据问题复杂度选择检索策略；[CRAG](https://arxiv.org/abs/2401.15884) 评估检索质量并触发补救。这两项研究展示决策在流程中的作用，不代表使用了 Jev。

上述是外部研究，并非本项目已完成的检索实测。若比较决策模型与重排序器，应固定查询、标注和候选列表，报告 NDCG、MRR、延迟与成本；全库检索和分层导航还需另外测量召回率与建索引开销。

## 文本、图像与页面属于另一条分类轴

一条文字查另一段文字，是文本检索；用文字找图片，或者用图片找图片，是跨模态或图像检索；用文字找包含表格和图表的页面，是视觉文档检索。这些任务描述的是**输入输出是什么**，而上表描述的是**怎样匹配**。

例如，[ColPali](https://arxiv.org/abs/2407.01449) 将页面图像表示为多个向量，再与文本查询做后期交互；图文单向量模型则可以把图片与文字编码到可比较的向量空间。视觉模型保留页面外观的同时，也受分辨率、小字与图像预处理影响。项目中的页面检索基线见[视觉多向量检索](colbert/视觉多向量检索.md)。

## 怎么选，怎么组合

先用真实查询和标注建立基线。对精确名称要求高的场景，先看词项检索是否漏掉同义表达；对自然语言问法变化大的场景，比较稠密检索能否补回遗漏。两路候选有互补时，再测试融合是否改善召回与排序。对候选较多且需要精细判断的场景，可以进一步评估重排序的质量收益和延迟。

选择索引时还要单独测量：同一个模型使用精确搜索和近似搜索，结果与资源消耗可能不同；数据库则在索引之外提供更新、过滤和持久化等能力。固定候选上的重排序指标不能代表全库召回。评测流程与指标见[检索系统全景与评估](检索系统全景与评估.md)。
