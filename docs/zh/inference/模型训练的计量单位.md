# 模型训练的计量单位：从 step 到 token 与 GPU 小时

> **阅读导航**：[推理与大模型机理](README.md) · [从零构建与训练全链路](大语言模型从零构建与训练全链路.md) · [预训练评测与能力基准](预训练阶段评测与能力基准.md) · [实验代码与配置](../../../experiments/llm-lifecycle-fullchain/README.md)
> 本文暂无英文版。

一篇论文说训练了 **10 万 steps**，另一篇说训练了 **48 小时**，哪一个训练得更多？仅凭这两个数字无法判断。前者通常描述训练过程，后者描述经过的时间；数据量、单步配置和使用的硬件可能完全不同。

理解训练记录，先把四类问题分开：模型更新了多少次，处理了多少数据，花了多少资源，以及效果有没有改善。它们能一起描述一次实验，却不能互相替代。

## 一、一次 step 发生了什么？

先看一个常见的监督训练循环：

```text
取一批数据 → 模型预测 → 计算 loss → 反向传播得到梯度 → 优化器更新参数
                                                           ↑
                                                一次 optimizer step
```

优化器根据梯度调整模型参数。**optimizer step 是一次优化器更新**，但论文或日志里单独写的 `step` 并没有所有项目通用的定义：它也可能指处理一个 batch、一次训练循环，或一次环境交互。看到数字时，先查作者的定义、训练框架或代码。[PyTorch 官方训练示例](https://docs.pytorch.org/tutorials/beginner/introyt/trainingyt.html)展示了计算梯度后调用 `optimizer.step()` 的基本流程。

一个优化器更新也不一定只处理一个批次。假设一次只能放下 4 条样本，可以连续处理 8 个 **micro-batch**，把梯度累积起来再更新一次：

```text
4 条/次 × 8 次梯度累积 = 一次更新使用 32 条样本
                         ↑
             8 次 micro-batch，1 次 optimizer step
```

为什么用 step？它方便对齐学习率变化、验证和保存 checkpoint 的频率，也方便描述优化进度。如果把停止条件只设成“训练两小时”，不同机器的速度差会让实际更新次数不同。但固定 step 仍不能保证数据量或效果相同，还要看每步的配置。

## 二、同样 1000 steps，为什么训练量会不同？

考虑两个只改变批大小的语言模型实验。都在单个数据并行进程上运行，不做梯度累积，每条序列固定为 128 个 token：

| 实验 | 每次更新的序列数 | 每步输入 token 位置 | 1000 步累计输入位置 |
| --- | ---: | ---: | ---: |
| A | 16 | 2,048 | 2,048,000 |
| B | 64 | 8,192 | 8,192,000 |

两者都是 1000 次更新，但 B 处理的输入位置是 A 的 4 倍。这**不意味着 B 的模型效果必然是 A 的 4 倍**：学习率、数据质量、重复程度、模型结构与训练目标也会影响结果。

对于固定长度、没有不完整 batch 的普通数据并行训练，可以先估算：

```text
每次更新的全局序列数
  = 每个数据并行进程的 micro-batch 序列数
  × 梯度累积次数 × 数据并行进程数

每次更新处理的输入 token 位置
  ≈ 全局序列数 × 序列长度
```

这里乘的是**数据并行进程数**，不一定是全部 GPU 数：张量并行等方式可能让多张卡共同处理同一批数据。动态长度、padding、样本打包、损失掩码和不完整 batch 会改变实际计数。累计处理过的 token 位置也包括重复抽到的数据，不等于去重后的语料大小；输入 token 数与实际参与 loss 的目标 token 数同样可能不同。

## 三、epoch、token 和样本数怎么选？

对于固定数据集，**epoch** 通常表示完整遍历数据集一次。假设有 1000 条样本、一次更新使用 100 条，且每轮不重复也不丢样本，那么约 10 次更新是一个 epoch。把全部数据看 3 遍，就是 3 个 epochs。

如果训练使用有放回的随机抽样，即使抽了 1000 次，也不保证 1000 条都被看过，不能简单称为完整的一轮。流式数据、持续变化的数据池和在线强化学习也可能没有自然的 epoch 边界，需看作者如何定义。

**token 或样本数**侧重描述模型处理了多少数据。语言模型的长短文本差异大，仅报告样本数可能掩盖实际 token 量；图像任务则常同时报告图像数量、分辨率和更新次数。重复读取的数据一般也会计入累计处理量。

## 四、时间、GPU 小时与 FLOPs 是资源尺度

**wall-clock time** 是经过的实际时间：例如从训练循环开始到结束经过了 2 小时。它对安排任务和比较端到端速度很有用，但报告时要说明是否包含数据加载、验证、保存和等待等环节。

**GPU-hour** 是设备占用时间的合计。4 张 GPU 同时占用 2 小时，就是 8 GPU-hours；两张占 4 小时也同样是 8 GPU-hours。它们的完成时间、训练配置与通信开销仍可能不同。

GPU-hour 也不是跨硬件的统一算力：不同型号的设备性能、实际利用率和配置不同。**FLOPs** 描述浮点运算量，更接近计算工作量，但要查清是理论估算还是实际测量，也要核对统计范围。若要比较成本，还需要 GPU 型号、数量、计时范围、吞吐量和价格等信息。

## 五、loss 决定什么时候停吗？

loss 是训练中要优化的目标函数，不是训练的时钟。监督学习中的 loss 常用于衡量预测与目标的差距；强化学习的优化目标则不一定采用这种形式。在数据和计算口径可比较的条件下，训练集平均 loss 下降，说明记录的训练目标值在改善；单个 batch 的下降也可能来自样本波动。若验证 loss 转而变差，可能开始过拟合，还需排查验证数据与评估噪声。不同目标、掩码与归一化方式下的 loss 数值也不能直接比较。

训练可以按固定 step、tokens、epoch、时间或计算预算结束，也可以观察验证指标，在连续多次没有改善时提前停止。它们经常一起用：例如预先限制 tokens 和 GPU-hours，每隔一定步数验证，保留验证效果最好的 checkpoint。[Hugging Face 的早停回调](https://huggingface.co/docs/transformers/trainer_callbacks)就是依赖评估指标与检查频率的一种实现。

对于任务能力，还要结合准确率、生成样例、格式遵循率等指标。强化学习中的 reward 是一个训练信号，也不能单独证明留出任务表现改善；还需要核对奖励定义及独立评测。

## 六、为什么论文强调不同的数？

训练类型和模型模态会影响哪些数据更方便报告，论文要回答的问题也会影响作者强调什么。下表是阅读入口，不是统一规定：

| 研究或训练场景 | 常见关注点 | 比较前还要看 |
| --- | --- | --- |
| 语言模型预训练 | 处理的 tokens、训练计算量、硬件和耗时 | 重复数据、tokenizer、序列长度、统计范围 |
| 有限数据集上的微调 | epochs、更新次数、验证指标 | 数据集大小、全局批大小、早停与 checkpoint |
| 图像模型训练 | 图像数、分辨率、更新次数 | 数据增强、批大小及分辨率变化 |
| 强化学习 | 环境交互、rollout、策略更新、reward | 每轮采样量、更新次数与奖励口径 |
| 系统效率研究 | 实际耗时、吞吐量、硬件配置 | 任务负载、测量范围、精度和比较条件 |

例如 [OpenAI Spinning Up 的 PPO 实现](https://spinningup.openai.com/en/latest/_modules/spinup/algos/tf1/ppo/ppo.html)分别配置环境交互步数和策略优化迭代次数，它们不是同一个计数。[Llama 3.1 模型卡](https://huggingface.co/meta-llama/Llama-3.1-70B/blob/main/README.md)同时报告预训练 token 规模和 H100 GPU-hours；引用时需保留其模型系列和计算范围，不能把系列总量说成单个模型的单次训练成本。

读到只写“10 万 steps”的论文，可以追问：step 指什么？global batch 和序列长度是多少？总共处理多少 token？读到只写“48 小时”，则要找使用的设备型号、数量、吞吐量和计时起止。信息缺失时，应保留“无法直接比较”的结论。

## 七、回到本仓的完整流程实验

[`llm-lifecycle-fullchain`](../../../experiments/llm-lifecycle-fullchain/README.md) 是理解训练过程的小规模实验。以仓库当前配置和脚本为例，`full` 的四个训练阶段分别设置：

| 阶段 | 配置的循环步数 | 该脚本的计数含义 |
| --- | ---: | --- |
| 预训练 | 250 | 每个循环累积 micro-batch 梯度，然后执行优化器更新；Muon + AdamW 参数分组方案与纯 AdamW 基线各跑一遍 |
| Midtrain | 120 | 每个循环执行一次优化器更新 |
| SFT | 250 | 每个循环执行一次优化器更新，loss 只计算回答及结束标记 |
| GRPO | 80 | 每个循环先采样和计算奖励；如果全部组内奖励都没有有效差异，该循环仍计 step，但不会更新参数 |

这里的 step 是脚本的循环口径；混合精度遇到数值溢出时，优化器更新也可能被跳过。RL 每步包含生成回答，不能把 80 个 RL steps 和 80 个预训练 steps 当成等量计算。

在单个数据并行进程、每个 micro-batch 16 条、长度 128、梯度累积为 1 的条件下，预训练的 250 个循环对应约 `250 × 16 × 128 = 512,000` 个累计输入 token 位置。脚本中 `tokens_seen` 按输入窗口长度计算；同一语料可反复采样，它不是去重 token 数，也不等于严格计入交叉熵的目标位置数。两种优化器方案分别记录各自训练量；计算整个预训练对照的成本时不能只看其中一份。

`wall_seconds` 用于记录训练循环耗时，包含循环内的周期验证和 checkpoint 保存，但不包含启动准备和计时之后的最终评估。脚本没有直接记录 GPU-hours。以上是代码计数口径，不代表某次运行已经完成，也不表示固定步数就是最佳停止点；具体运行应结合配置、metrics 和报告判断。
