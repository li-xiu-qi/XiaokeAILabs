# 迭代日志

## 2026-09-10：vLLM 0.28.0 在 GB10 上的首次实测

### 目标
验证 vLLM 能否在 DGX Spark（GB10）上跑 Qwen3.8-27B，并对比 llama.cpp 的实测数据。

### 部署过程踩的坑
1. **PyTorch 版本降级**：先装了 torch 2.14.0，vLLM 0.28.0 要求 2.13.0，uv 自动降级
2. **显存利用率**：GB10 统一内存只有 88.7/121.69 GB 可用（系统占用），0.85 会直接失败，必须降到 0.5
3. **缺 ninja**：FlashInfer JIT 编译采样模块需要 ninja，`uv pip install ninja` 后要把 `vllm-env/bin` 加进 PATH
4. **enforce-eager**：torch.compile 在 GB10 上要 10 分钟以上，用 `--enforce-eager` 跳过，启动从 15 分钟降到 6 分钟
5. **残留进程占显存**：失败的 vLLM 进程不退会占着 GPU 内存，导致下次启动报 "Free memory less than desired"

### 关键部署参数
```bash
./bin/python -m vllm.entrypoints.openai.api_server \
    --model ~/models/Qwen3.8-27B-BF16 \
    --trust-remote-code --dtype bfloat16 \
    --max-model-len 1024 --gpu-memory-utilization 0.5 \
    --enforce-eager --port 8000
```

### 实测结果（GB10, bs=1/bs=32, seq=128）
| 引擎 | decode tok/s | prefill tok/s | 模型预测 decode | 模型预测 prefill |
|------|-------------|---------------|-----------------|------------------|
| llama.cpp | 4.30 | 25.8 | | |
| vLLM 0.28.0 (enforce-eager) | 4.39 | 11.34 | | |
| vLLM 0.28.0 (full compile) | 4.44 | 152.04 | | |
| SGLang 0.5.19 | 4.47 | 121.53 | | |
| 模型预测 | 4.35 | 578.8 | | |

### 关键发现
- **decode 与引擎无关**：四个引擎 decode 都在 4.3-4.5 tok/s，模型预测 4.35 准确（误差 <3%）。decode 是带宽瓶颈，与推理引擎和编译策略无关。
- **torch.compile 对 prefill 影响巨大**：vLLM enforce-eager 只有 11.34 tok/s，完整编译后 152.04 tok/s，**13 倍提升**。kernel 融合在 GB10 这种弱算力硬件上效果显著。
- **vLLM full > SGLang > llama.cpp > vLLM eager**（prefill）：vLLM 完整编译 152.04 > SGLang 121.53 > llama.cpp 25.8 > vLLM eager 11.34。
- **prefill 模型预测偏高**：即使最优的 vLLM full（152.04）也只有模型预测（578.8）的 26%。GB10 的 prefill 有效算力利用率远低于模型假设的 35%，实际约 9%。混合架构的 48 层 linear attention 无法像 full attention 那样高效 batch，是主要原因。
- **vLLM max-num-seqs 限制**：混合架构的 Mamba cache 限制了最大并发。gpu_util=0.5 时只有 69 个 Mamba cache block，必须设 `--max-num-seqs 64` 否则 CUDA graph 捕获失败。
- **SGLang 的 Mamba cache 要求更高**：mem-fraction-static=0.5 时 Mamba cache 不够，需要 0.7 + max-running-requests=32。
- **SGLang CUDA graph 捕获慢**：58 个不同 token 数的 prefill graph，每个 4-6 秒，总共约 5 分钟。但捕获完后 prefill 性能不错。
- **GB10 一次只能跑一个引擎**：两个引擎同时加载模型（各 51 GB）会把 128 GB 统一内存撑爆，导致系统卡死。详见 `pkm-hub-machines/machines/dgx-spark-GB10内存管理.md`。

## 2026-09-13：LLM-Viewer 交叉验证

部署 LLM-Viewer（feifeibear fork, arXiv 2402.16363）到 GB10，做独立交叉验证。

### 部署方式
- 上传代码到 `~/LLM-Viewer/`，安装 flask/flask_cors 到 xinfer-env
- 在 `hardwares/hardware_params.py` 添加 `nvidia_GB10: bandwidth=273e9, FP16=89.3e12`
- 写 `configs/qwen3_8.py`（混合架构配置，但 LLM-Viewer 仍按 64 层全 full attention 算）
- 提取 `text_config` 为 `config_simple.json`，绕过多模态 AutoConfig 加载问题
- 跑 `analyze_cli.py` 得到逐层 CSV，用 `scripts/llm_viewer_comparison.py` 汇总

### 预测 vs 实测
| 指标 | LLM-Viewer 预测 | 实测最优 | 误差 | 反推有效带宽 |
|------|----------------|---------|------|-------------|
| Decode tok/s | 6.07 | 4.35（四引擎均值 4.30–4.47） | +39.6% | 71.6% |
| Prefill tok/s | 730.5 | 152.04（vLLM full compile） | +380.5% | 20.8%（带宽，非算力） |

### 关键发现
1. Decode 有效带宽 71.6%，与本实验标定的 82-86% 同一量级，decode 效率常数合理。差异来自 LLM-Viewer 只算 44.9 GB 权重（漏 embedding 与混合架构真实投影维度），实际读 51.1 GB；按实际字节反推是 82.4%。
2. Prefill 的偏差归因不是算力利用率，是有效带宽。查逐层 CSV，bs=1/seq=128 下所有层都是 memory bound（q_proj 算术强度 122.4 < 平衡点 327），LLM-Viewer 的 730.5 tok/s 是带宽下界。此前文档里的「有效算力利用率 20.8%」是 152.04/730.5 的倒数，属标签错误。
3. 4.80 倍偏差分解为 权重字节 1.14x × 有效带宽 4.50x，主导项是有效带宽。
4. 核心新发现：**prefill 有效带宽（60.7 GB/s，22.2% 峰值）只有 decode（224.8 GB/s，82.4% 峰值）的 27%**。原因是 prefill 每字节配十倍计算（AI 55-100 vs decode 的 1-10），在 GB10 低算力下 kernel 藏不住访存延迟。
5. 混合架构修正对性能预测影响不大（矩阵投影占 99.9%，attention 占 <1%）
6. LLM-Viewer 无法区分 enforce-eager（11.34）和 torch.compile（152.04）的差异

### 落地修正
- `docs/LLM-Viewer交叉验证.md`：完整部署流程、逐层数据、偏差分解
- `docs/Roofline模型.md`：替换了此前一版无法复现的「2026-09-09 交叉验证」记录（称反推有效带宽 272.7 GB/s，该日期在迭代日志无对应条目，数字也无法由已知输入复现）
- `scripts/hybrid_architecture_model.py`：新增 `GB10_PREFILL_EFFECTIVE_BANDWIDTH = 60.7e9` 与 `estimate_prefill_tps_bandwidth()`，prefill 从算力路径改走带宽路径；`PREFILL_COMPUTE_UTILIZATION` 的 35% 标记为机理错误口径并保留作对照
- `docs/外部计算器逆向调研-llmfit混合架构建模.md`：更新 35% 利用率的结论与对比表

### 已知边界
- 60.7 GB/s 只标定于 BF16 / bs=1 / seq=128 / vLLM full compile 一个点。换量化、换引擎、换 batch 都需重标；Q4 的 444.0 tok/s 是沿用同一带宽的外推值，不是标定值
- 从单点反推的常数代回同一点必然误差归零，没有独立预测力。这条修正的价值在偏差分解与暴露 prefill/decode 带宽不对称，不在拟合精度
- batch 增大后部分层会转 compute-bound，届时需切回算力路径
- Roofline模型.md 内部还有一处未同步的数值：平衡点在正文按 60 TFLOPs 算成 220 FLOP/byte，而硬件常数表已是实测 89.3 TFLOPS（对应 327）。涉及平衡点的结论应以 327 为准

## 2026-09-10：逆向整合 llmfit 混合架构建模

### 目标
修正 LLM-Viewer 适配器在 Qwen3.8-27B（混合架构）上的严重误差。

### 问题
LLM-Viewer 把 64 层全当 full attention，KV Cache 高估 1440x 到 1650x，
prefill 误差 2852% 到 2989%。

### 动作
1. 逆向 AlexsJones/llmfit（MIT, 35.1k star, Rust）
2. 提取 KV Cache、显存、Decode TPS、Prefill TPS 四个核心公式
3. Python 重写到 `scripts/hybrid_architecture_model.py`
4. 写文档 `docs/外部计算器逆向调研-llmfit混合架构建模.md`

### 关键公式
- KV Cache：只对 16 full attention 层计算（2 × n_kv_heads × head_dim × ctx × dtype_bytes × full_layers）
- 显存：params_b × bpp + KV Cache + 0.5 GB overhead
- Decode：bandwidth / (params_b × bpp) × efficiency（GB10 实测 86%/73%）
- Prefill：tflops × 0.35 × 1e12 / (2 × params)

### 结果（GB10, bs=1, seq=128）
| 指标 | BF16 预测/实测/误差 | Q4 预测/实测/误差 |
|------|------|------|
| decode tok/s | 4.35/4.30/1.2% | 13.12/12.10/8.4% |
| 权重显存 GB | 54.00/50.90/6.1% | 15.19/17.50/13.2% |

### 待办
- Q4_K_XL 显存偏差 13.2%，需要从实际 GGUF 文件读取精确 bpp
- Prefill 公式（35% 利用率）在 vLLM enforce-eager 下严重偏离（5004%），需要重新标定 GB10 的 prefill 效率
