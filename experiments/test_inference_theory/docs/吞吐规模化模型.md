# 吞吐规模化模型

> 实证日期 2026-09-08 · Python 3.13.0 · 脚本 `scripts/throughput_model.py` · 以 q4_k_xl 实测 12.1 t/s 为单流锚点

单流 decode 只服务一个请求，权重读一遍只产出一个 token，带宽利用率低。服务场景把多个请求打包成一批，摊薄权重读取，总吞吐远高于单流。这条模型回答：同一块卡，服务吞吐比单流高多少，batch 加到多少会碰到算力墙。

## 单流 vs 服务：带宽利用率

单流 decode 的吞吐由 roofline 给出：`tok/s = 带宽 × 效率 / 权重字节`。GB10 上 q4_k_xl 实测 12.1 t/s，反推带宽利用率 73%（脚本 [1]），即权重读取只吃满了峰值带宽的七成，剩下三成是启动开销和碎片。

服务吞吐把 B 个请求放一批：权重读一遍，同时算 B 个 token 的下一步。总吞吐 ≈ `B × 单流 t/s`，而且 batch 越大，权重读取摊薄得越充分，单请求的有效带宽利用率越接近峰值。

## 吞吐随 batch 增长（Qwen3.8-27B q4，GB10）

脚本 [2] 输出：

| batch | 带宽利用率 | 单流 t/s | 总吞吐 t/s | 相对单流 |
|---|---|---|---|---|
| 1 | 73% | 12.1 | 12.1 | 1.0x |
| 2 | 80% | 13.3 | 26.6 | 2.2x |
| 4 | 94% | 15.7 | 62.9 | 5.2x |
| 8 | 100% | 16.7 | 133.3 | 11.0x |
| 16 | 100% | 16.7 | 266.7 | 22.0x |
| 32 | 100% | 16.7 | 533.3 | 44.1x |
| 64 | 100% | 16.7 | 1066.7 | 88.2x |

batch 加到 8 时带宽利用率就顶到 100%，之后单流 t/s 不再涨，总吞吐随 batch 线性放大。所以服务场景能把总吞吐拉到单流的几十倍，这是单卡服务化的核心收益。

## 算力天花板：batch 加到多少碰墙

吞吐不能无限涨，总算力 `2×P×batch` FLOPs/token 会顶到峰值算力。带宽界吞吐（`B×单流`）等于算力界吞吐（`峰值算力/(2×P)`）时的 batch 就是拐点（脚本 [3]）：bf16 约 302，q4 约 181。超过这个 batch，再加请求也不会提升总吞吐，只是让每个请求更慢。

GB10 单卡算力天花板（脚本 [4]）约 1099 t/s，是 q4 单流 12.1 t/s 的 91 倍。这是「所有 batch 加起来」的理论总吞吐上限，实际受 KV cache 显存约束（batch 64 时 KV cache 就 137GB 爆了，见 KV cache 模型）到不了那么高。

## 实践判据

服务吞吐和单流吞吐是两个量级，选型时别用单流数字评估服务能力。batch 上限由先到的那道约束决定：KV cache 显存（batch 64 爆）通常比算力天花板（batch 181）先到，所以实际服务 batch 多在显存约束内，总吞吐大约在几十到一百多 t/s。

单流数字（12.1 t/s）适合评估交互式单用户体验，服务吞吐适合评估 API 承载能力。同一块卡，两个数字差一个量级，用错了会严重误判容量。
