# 注意力复杂度模型

> 实证日期 2026-09-08 · Python 3.13.0 · 脚本 `scripts/attention_model.py` · 拐点计算与显存墙量化

标准注意力的计算量和显存都随序列长度 S 平方增长。这条模型回答：上下文拉到多长注意力会成为瓶颈，以及 FlashAttention 和线性注意力各自解决什么。

## 注意力算力与反超拐点

一次前向里，注意力部分的算力约 `4 × L × S² × d`（QK^T 和 AV 各 `2×S²×d`，L 层数，d 是 head_dim），而投影 + MLP 部分约 `2×P×S`（P 参数量，随 S 线性）。两者相等时的上下文长度就是拐点：

```
S = P / (2 × L × d)
```

代入 Qwen3.8-27B（脚本 [1]）：拐点约 83 万 tokens。远在原生 262K 之上，说明在这个模型的常规上下文范围内，注意力算力还不是瓶颈，投影/MLP 主导。上下文要继续往上堆（比如 1M），注意力才会反超。

## 显存才是先爆的那个

标准注意力要把 S×S 的分数矩阵物化在显存里（每层每头一个），这是 O(S²) 显存。脚本 [2] 输出 Qwen3.8-27B 的分数矩阵显存（batch=1）：

| 上下文 | 注意力算力占比 | 分数矩阵显存 |
|---|---|---|
| 1K | 0.1% | 3.2 GB |
| 8K | 1.0% | 206 GB |
| 32K | 3.8% | 3299 GB |
| 128K | 13.6% | 52777 GB |
| 256K | 23.9% | 211106 GB |

8K 上下文的分数矩阵就要 206GB，远超 GB10 的 121GB。所以标准注意力在 GB10 上连 8K 都跑不了，这不是算力问题，是显存先把分数矩阵撑爆了。

## 三种解法的分工

脚本 [3] 对比了三种注意力在长上下文下的算力/显存：

| 上下文 | 标准注意力 | FlashAttention | 线性注意力/SSM |
|---|---|---|---|
| 算力 | O(S²) | O(S²) | O(S) |
| 显存 | O(S²) | O(S) | O(S) |

FlashAttention 通过分块计算、不物化完整的 S×S 矩阵，把显存从 O(S²) 降到 O(S)，但算力仍是 O(S²)（该做的乘法一个不少，只是重排了顺序提升缓存命中）。线性注意力/SSM 更进一步，用核技巧或递归把算力也降到 O(S)。

到 1M 上下文（脚本 [4]），标准注意力分数矩阵要 338 万 GB，FlashAttention 只要 3.2GB。这就是为什么跑 1M 上下文必须用 FlashAttention，是硬前提，不是优化选项。

## 实践判据

上下文长度规划要同时看两道约束：显存（KV cache 随 S 线性、注意力分数矩阵随 S²，见 KV cache 模型和本节）和算力（注意力随 S²，到拐点后主导）。GB10 上短上下文（<8K）用标准注意力即可，中等长度必须 FlashAttention，要到 1M 还得叠加 KV 量化和 NVFP4 权重。

社区在 GB10 上跑通的 1M 上下文方案（2026-08 阿里云实测），正是 NVFP4 权重 + fp8 KV + FlashAttention 三者的组合，任何一项缺失都会在某一环爆显存或算力。
