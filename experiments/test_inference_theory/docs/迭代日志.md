## 2026-09-09 · LLM-Viewer 交叉验证：Roofline 方向正确，效率常数需实测标定

在 Spark 上部署 LLM-Viewer（arXiv 2402.16363 的配套工具），对 Qwen3.8-27B/GB10 跑 BF16 与 Q4_K_XL 两种量化，与本实验的 Roofline 模型逐项对比。这是本批模型唯一的独立外部锚点，此前所有常数都是从自家实测反推的。

### 部署过程

1. clone `hahnyuan/LLM-Viewer`（Python，最后更新 2024-09-11）
2. 装依赖 `flask flask_cors easydict`（transformers 已有 5.16.1）
3. `hardwares/hardware_params.py` 里加 GB10 条目：bandwidth=273e9, FP16=89.3e12（本实验实测）, INT8=178.6e12（估算）, onchip_buffer=27648e3（借用 A100）
4. 写 `configs/Qwen3_5.py` 适配器：Qwen3_5Config 的属性在 `text_config` 子对象里，Llama.py 的 getter 直接 `getattr(model_params, ...)` 会失败
5. 用本地模型路径 `/home/ke/models/Qwen3.8-27B-BF16` 加载（HF cache 里只有 safetensors 没有 config.json）

### 对比结果（bs=1, seq=128）

| 指标 | BF16 LLM-Viewer | BF16 实测 | Q4 LLM-Viewer | Q4 实测 |
|---|---|---|---|---|
| decode tok/s | 6.11 | 4.30 | 24.37 | 12.10 |
| prefill tok/s | 735.9 | 25.8 | 1901.2 | 63.6 |
| 权重显存 GB | 42.05 | 50.90 | 10.51 | 17.50 |

### 核心结论

**Decode 阶段高度一致，验证 Roofline 方向正确**：LLM-Viewer 的 decode 完全 memory-bound，反推有效带宽 272.7 GB/s（峰值 273 的 99.9%）。本实验的 Roofline 模型用 235/198 GB/s（86%/73%）。两者差异来自 LLM-Viewer 假设 100% 带宽效率，本实验用实测标定的效率常数。**方向一致，效率常数需按硬件实际标定**。

**Prefill 阶段差异巨大，来自混合架构建模缺失**：LLM-Viewer 的 prefill 用了 89.3 TFLOPS 峰值算力，而本实验 llama.cpp 实测只有 25.8 tok/s。这个 2852%-2989% 的差异来自 Qwen3.8-27B 的 48/64 层是 linear_attention，LLM-Viewer 的适配器把所有层都当标准 Transformer 算，prefill 的 OPs 计算没有区分 linear 和 full attention 层。

**权重显存差异来自参数量与字节率**：LLM-Viewer 的 42.05 GB 对应 21.03B 参数（FP16），实际 BF16 文件 50.9 GB 对应 25.45B 参数。Q4 的 10.51 GB 对应 21.03B 参数（4-bit），实际 Q4_K_XL 文件 17.5 GB，实际字节率 0.69 B/param 高于理论 0.5 B/param。

### 量化加速比对比

| 指标 | LLM-Viewer | 本实验实测 |
|---|---|---|
| decode 加速比 | 3.99x | 2.81x |
| prefill 加速比 | 2.58x | 2.47x |
| 权重字节比 | 4.00x | — |

decode 加速比 LLM-Viewer 预测 3.99x（接近理论 4x），实测 2.81x。差异来自 llama.cpp 的 Q4_K_XL kernel 效率低于理论峰值。

### 对 docs 的影响

**Roofline 模型**：decode 阶段的带宽瓶颈判断得到独立验证，但效率常数需要标注为实测标定值（86-73%），不是理论峰值（99.9%）。

**权重显存模型**：需要补充说明实际文件字节率可能高于理论值（Q4_K_XL 0.69 vs 理论 0.5 B/param），以及 config 声明参数量与实际文件的差异。

**内存层级模型**：prefill 阶段的算力瓶颈判断对混合架构模型不适用，需要区分 linear_attention 和 full_attention 层。

### 未解决

- Prefill 的混合架构建模缺失是 LLM-Viewer 工具层面的局限（2024 年的工具不认识 2025-2026 年的混合架构），不是本实验的问题。如需精确验证 prefill，需要自己写混合架构的 roofline 模型。
- 权重显存的参数量差异（21.03B vs 25.45B）来源未查明，可能是 config 声明的参数量与实际文件不一致。

## 2026-09-08 · 建立 Embedding 吞吐外推模型（第三种形态）

在 Spark GB10 上跑了 5 个 embedding 模型（22M-558M），建立两阶段外推模型。

**实测数据**（bs=128, seq=128）：

| 模型 | 参数量 | 吞吐 | 单句延迟 |
|---|---|---|---|
| all-MiniLM-L6-v2 | 22M | 3025/s | 0.33ms |
| bge-small-zh-v1.5 | 23M | 2706/s | 0.37ms |
| jina-v2-small-en | 28M | 2767/s | 0.36ms |
| nomic-embed-text-v1.5 | 108M | 618/s | 1.62ms |
| bge-m3 | 558M | 416/s | 2.40ms |

**jina-embeddings-v4（1.8B）加载失败**：基于 Qwen2.5-VL 架构，custom code 在离线模式下 tokenizer 初始化失败。记录为边界案例，说明超大 embedding 模型可能使用 VLM 架构。

### 两阶段模型

**阶段 1（小模型 <100M）**：受 Python 层开销限制。22M-28M 的模型无论参数量多少，峰值吞吐都卡在 ~3000 sent/s。机制是 sentence-transformers 的 tokenization/pooling/normalization 开销占主导，GPU 计算时间只有几毫秒。

**阶段 2（大模型 >=100M）**：受 GPU 计算限制。吞吐与参数量成幂律关系：`throughput = 1904 / n_params^0.240`。效率不是常数（558M 是 0.667，108M 是 0.191），说明小模型的 kernel 效率更低。

### 模型精度

| 模型 | 实测 | 理论 | 误差 |
|---|---|---|---|
| all-MiniLM-L6-v2 | 3025/s | 2833/s | 6.4% |
| bge-small-zh-v1.5 | 2706/s | 2833/s | 4.7% |
| jina-v2-small-en | 2767/s | 2833/s | 2.4% |
| nomic-embed-text-v1.5 | 618/s | 618/s | 0.0% |
| bge-m3 | 416/s | 416/s | 0.0% |

所有模型误差在 10% 以内。

### 与 LLM 推理的不同构

Embedding 是第三种外推对象，与向量索引和 LLM 推理都不同：

- **无 KV Cache**：每次编码都是独立的前向传播
- **无自回归**：不像 LLM 那样逐 token 生成
- **批处理是主要优化手段**：GPU 并行处理多个样本
- **无 prefill/decode 之分**：只有一种计算模式

计算量公式相同（FLOPs = 2 × N_params × N_tokens），但机制完全不同。这个模型不能直接套用到 LLM 推理。

### 局限与后续

- 当前模型只适用于 bs=128，其他 batch size 需要额外修正
- 只验证了 seq=128，更长序列未测试
- jina-v4 加载失败说明 VLM 架构的 embedding 需要单独建模
- 待做：与 LLM-Viewer 交叉验证

## 2026-09-08 · 内存层级模型改为按层累加，部分卸载误差 63% → 8%

### 问题

`memory_hierarchy_model.py` 在部分卸载场景误差爆炸：

| -ngl | 实测 | 旧版预测 | 误差 |
|---|---|---|---|
| 0（全 CPU） | 1.5 t/s | 2.1 | 43% |
| 32（一半） | 2.1 t/s | 3.4 | 63% |
| 99（全 GPU） | 4.7 t/s | 4.7 | 0% |

用户要求压到 10% 以内。

### 诊断

旧版 `decode_tps_unified()` 的形式是「有效带宽 × 混合计算效率 × 单一利用率系数」。那个 0.94 是从 `-ngl 99` 的实测/预测比反推的，套回全 GPU 路径当然准。但 `-ngl 0` 和 `-ngl 32` 走的是完全不同的机制，套同一个系数必然失准。

 arXiv 2512.01644（A Systematic Characterization of LLM Inference on GPUs）给了机制解释：decode kernel 的 GPU Execution 只占 24%（Prefill 27%），即 70%–80% 周期停在 stall 上。而且 stall 分三类性质，不能合并：

| kernel | Decode 主导 stall | 占比 | 机制 |
|---|---|---|---|
| FFN-Up | Memory Dependency | 58% | GEMV 模式，无法隐藏权重加载延迟 |
| O-Proj / FFN-Down | Execution Dependency | 51% | 130 个活跃寄存器，可调度 warp 受限 |
| LayerNorm | Synchronization | 27.7% | 小批量 reduction 的 barrier 尾延迟 |

关键推论：三类 stall 不随层数分配同比移动，所以「层数在 GPU/CPU 间切分」时混合系数必错。

### 改法

放弃单一系数，用两端实测反推每层有效服务带宽，按层累加：

- GPU 层：54.6GB ÷ 64 层 ÷ 3.33ms = **254 GB/s** = 273 峰值的 93%
- CPU 层：54.6GB ÷ 64 层 ÷ 10.42ms = **81 GB/s** = 273 峰值的 30%

两端差 3 倍。两者读同一条物理总线，带宽峰值相同，差距纯粹来自访问效率。新增 `layer_service_bw()` 和 `decode_tps_layerwise()`，旧函数保留作对照。

### 改完的精度

| -ngl | 实测 | 新版预测 | 误差 |
|---|---|---|---|
| 0 | 1.5 t/s | 1.5 | **0%** |
| 32 | 2.1 t/s | 2.3 | **8%** |
| 99 | 4.7 t/s | 4.7 | -1% |

三档全部进入 10% 以内。11 个脚本全量自测无回归（`results/全模型自测输出.txt`）。

### 沉淀下来的约束

**任何「部分卸载」的预测都必须逐层分开算再累加，把两端效率塞进一个系数是错的。** 这条对后续所有卸载相关建模生效。

离散 GPU（4090）场景机制不同：卸载走 PCIe 30 GB/s，是带宽断崖，那条线仍走带宽模型，不吃这个结论。

### 作废 / 待校准

- `decode_tps_unified()` 标记为旧版，仅留作对照，不要在新代码里调用。
- 0.93 / 0.30 这两个系数是从 GB10 两端实测反推的，可靠。
- 论文里的 stall 比例（58%/51%/27.7%）是 **A100 的实测，不是 GB10 的**。SM 数、寄存器文件、L2 大小都不同，不能直接搬。要真正压得更准，需在 GB10 上重新标定一组「层数 × stall 比例」曲线。
