# 权重显存模型

> 实证日期 2026-09-08 · Python 3.13.0 · 脚本 `scripts/weight_memory_model.py` · 对齐实测 q4 -0%、bf16 +7%

模型权重是推理的固定显存成本，与上下文长度、batch 大小无关。这条模型回答：一个模型占多少显存，量化能压到多少，以及给定显存上限能装下哪个量化档位。

## 核心公式

```
权重显存 = 参数量 × 每参数字节数 (bytes/param)
```

每参数字节数由量化精度决定：

| 精度 | bytes/param | 说明 |
|---|---|---|
| fp32 | 4.0 | 训练常用，推理少用 |
| bf16/fp16 | 2.0 | 全精度推理 |
| fp8/int8 | 1.0 | 8-bit |
| q8_0 | 1.06 | GGUF 8-bit 含 scale |
| q6_k / q5_k_m | 0.74 / 0.64 | GGUF 中精度 |
| q4_k_xl / q4_k_m | 0.60 / 0.58 | GGUF 4-bit 主流 |
| q3_k_m / q2_k | 0.47 / 0.38 | 极限压缩 |
| nvfp4 | 0.55 | GB10 硬件原生，约 4.4 bit 含 scale |

## 对齐实测文件大小

用 Qwen3.8-27B（27.3B 参数）验证（脚本 [2]）：

| 精度 | 预测权重 | 实测文件 | 误差 |
|---|---|---|---|
| bf16 | 54.6 GB | 50.9 GB | +7% |
| q4_k_xl | 16.4 GB | 16.4 GB | -0% |

bf16 的 7% 偏差来自 GGUF 的张量对齐填充和元数据（张量按 32 字节对齐，多余部分占空间）。q4_k_xl 完全吻合，因为该量化本身就是按目标大小打包的。模型准确。

## 各量化档位显存（Qwen3.8-27B，GB10 121GB）

脚本 [1] 输出全部档位：fp32 109GB、bf16 54.6GB、fp8 27.3GB、q8 28.9GB、q6 20.2GB、q5 17.5GB、q4 16.4GB、q3 12.8GB、q2 10.4GB。在 121GB 的 GB10 上，27B 稠密模型连 fp32 都装得下，量化更多是为速度而非显存。

## 显存上限决定能不能跑

真正卡显存的是大模型（脚本 [3]）：320B 的 MoE（GLM-5.3-Flash 量级）bf16 要 640GB，GB10 121GB 装不下任何档位（最低 q2 也要 122GB），必须靠 nvfp4 + DSpark 这类专用格式或更强显存的机器。这条是「这台机器能跑什么模型」的第一道筛子。

## 量化对 decode 速度的影响

decode 是带宽瓶颈，速度 ≈ 带宽 / 权重字节，所以量化对速度的提升近似和压缩比成正比（脚本 [4]）：

| 精度 | bytes/param | 预测 decode（以 q4 实测 12.1 为锚） |
|---|---|---|
| bf16 | 2.00 | 3.6 t/s |
| fp8 | 1.00 | 7.3 t/s |
| q6_k | 0.74 | 9.8 t/s |
| q4_k_xl | 0.60 | 12.1 t/s |

这是 GB10 上量化几乎「免费提速」的数学原因：权重字节降一半，decode 速度约翻倍，而显存占用同步降一半。代价是精度损失，需要按任务验证。

## 实践判据

选量化档位的顺序：先确认显存放得下（本模型），再看 decode 速度要求（roofline 模型），最后验证该精度的输出质量是否达标。三者里显存是硬约束，速度和质量可权衡。
