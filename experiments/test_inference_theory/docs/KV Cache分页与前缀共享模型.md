# KV Cache 分页与前缀共享模型

> 整理日期 2026-09-08 · Python 3.13.0 · 脚本 `scripts/kv_paging_model.py` · 公式自测通过，命中率收益需服务数据校准

前面的 KV cache 模型假设连续内存分配（正好 S 个 token 的 KV）。真实推理服务（vLLM 的 PagedAttention）用分页管理，带来两项修正：分页内部碎片、前缀共享收益。这个模型把这两项补上，让 KV cache 的显存外推更接近真实服务。

## 分页内部碎片

KV cache 按固定页（block，如 16 token）分配，最后一个页可能只填一部分，平均浪费半页。碎片开销 = 分页字节 / 连续字节 - 1。

关键规律：**上下文若是页大小整数倍则无碎片，短上下文碎片占比高，长上下文可忽略**。实测（page_size=16，Qwen3.8-27B）：

| 上下文 | 碎片开销 |
|---|---|
| 100 | 12.0% |
| 500 | 2.4% |
| 1000 | 0.8% |
| 2000 以上 | 0.0%（整数倍时） |

页越大，非整除时单页浪费越多（64 页大小在 2000 上下文浪费 48 token = 2.4%）。所以分页碎片在长上下文服务里通常可忽略，但在大量短请求（如 100 token 的对话）场景会累积成不可忽视的开销。

## 前缀共享收益

多请求共享相同前缀（系统提示、few-shot 示例、多轮对话历史），命中时前缀的 KV 只算一次、只存一份。这是服务化推理最核心的显存优化。

系统提示 2000 token、各请求后缀 500 token 的收益：

| 请求数 | 无共享 | 有共享 | 节省比 |
|---|---|---|---|
| 1 | 0.66 GB | 0.66 GB | 0% |
| 4 | 2.62 GB | 1.05 GB | 60% |
| 16 | 10.49 GB | 2.62 GB | 75% |
| 64 | 41.94 GB | 8.91 GB | 79% |

多轮对话场景收益更大。10 轮对话、每轮新增 200 token、历史全部共享时，累计 KV 从 2.88 GB 降到 0.52 GB，**节省 82%**。这就是为什么聊天服务必须做前缀共享，否则多轮对话的 KV cache 会爆炸。

## 与连续模型的关系

前面的 KV cache 模型给出连续分配的下限（理论最小值），本模型加两项修正：

- 分页碎片：长上下文 +几% 可忽略，短上下文 +12% 需注意
- 前缀共享：多请求/多轮时 -60% 到 -82%，收益极大

真实服务的 KV cache 显存 = 连续下限经分页和共享修正。但分页和前缀共享的精确收益依赖真实命中率，需起 llama-server 后用真实服务数据校准，本模型给出的是参数化的理论上界。

## activation 显存（2026-09-08 补）

之前的推理显存公式只加固定 2GB 开销，低估了 activation。activation 与 batch、seq_len 近似线性（层数×2×hidden×seq×batch×2字节），大 batch 长序列时可达几十 GB（脚本 [6]，bf16）：

| seq | batch | 权重 | KV | activation | 总计 |
|---|---|---|---|---|---|
| 1K | 1 | 54.6 | 0.3 | 1.3 | 58.2 GB |
| 8K | 1 | 54.6 | 2.1 | 10.7 | 69.5 GB |
| 8K | 8 | 54.6 | 17.2 | 85.9 | 159.7 GB |
| 32K | 16 | 54.6 | 137.4 | 687.2 | 881.2 GB |

batch=8 时 activation 就 86GB，超过权重本身。所以长上下文大 batch 服务显存爆有三个来源：权重、KV cache、activation，之前只建模了前两个。这也是为什么实际服务的 batch 和上下文不能同时拉满，activation 是第三个硬约束。

## 实践判据

分页碎片选小页（如 16）控制短上下文开销；前缀共享是服务化必做，系统提示和多轮历史的共享命中率直接决定显存和 prefill 成本。这两个优化在 vLLM/SGLang 里都是默认开启的，理解它们的量级有助于评估服务显存和调参。
