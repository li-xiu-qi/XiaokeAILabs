# 外推的模型架构依赖性

> 整理日期 2026-09-08 · 配套脚本 `scripts/llm_spec.py`

这套外推模型和模型的关系不是一刀切的「强相关」。逐个公式看，一部分完全模型无关（纯硬件），一部分只依赖一个总参数数，还有一部分强依赖架构细节。混在一起说「强相关」会误导：该用哪个公式取决于架构，该代入哪个数取决于参数。

## 逐个外推公式的依赖程度

| 外推公式 | 模型无关项 | 依赖的模型量 | 架构相关性 |
|---|---|---|---|
| 机器平衡点 | 峰值算力、带宽（纯硬件） | 无 | 完全无关 |
| 权重显存 | 字节/参数（量化档位） | 总参数量 | 弱，只要总数 |
| Decode 速度 | 带宽、字节/参数 | dense 用总参，MoE 用激活参 | 强，dense/MoE 公式不同 |
| KV cache | 每字节 | 层数、KV头数、head_dim | 极强，见下 |
| 注意力算力 | 无 | 层数、head_dim | 中 |

关键分界：权重显存和 dense 的 decode 速度，只需要模型给一个「总参数」总数，架构是 dense 还是 MoE、多少层、什么注意力，都不进公式。对这两个量，说「和模型强相关」是夸大，它们只和一个汇总数字相关。真正架构强相关的是另外两个：MoE 的 decode 速度、KV cache。

## 架构强相关之一：MoE 的 decode 不能用总参数

这是最容易算错的地方。Decode 每步只跑激活的那部分专家，所以 MoE 的 decode 速度由激活参数决定，不是总参数。GLM-5.3-Flash 那种 320B 总参、18B 激活的 MoE，decode 速度和 18B 的 dense 模型同档，但权重显存要按 320B 算。同一个模型，decode 速度和显存用的是两个不同的参数，这就是 dense/MoE 架构带来的公式分歧。

用 dense 的总参公式去套 MoE 的 decode，会把速度低估一个数量级。反之用激活参去算显存，会以为 320B 模型装得进 121GB，实际装不下。所以 `llm_spec.py` 的 ModelConfig 里同时存了 `total_params_b` 和 `active_params_b`，decode 走激活参、显存走总参。

## 架构强相关之二：KV cache 公式由注意力机制决定

KV cache 的公式 `2×层数×KV头数×head_dim` 只对标准 MHA 和 GQA 成立。换成不同的注意力机制，KV cache 的概念和公式都变了：

**MLA（DeepSeek 用的 Multi-head Latent Attention）**：不存逐头的 K 和 V，存一个压缩后的低秩潜向量，解码时再升维投影。它的 KV cache 极小，和同规模 GQA 模型差一个量级。用 GQA 的逐头公式去算 MLA，会严重高估。

**线性注意力 / SSM / Mamba 这类**：连「KV cache」这个结构都不存在了，换成一个固定大小的循环状态，不随序列长度增长。它们的显存模型是 O(1) 于长度，和 Transformer 的 O(长度) 是两套完全不同的公式。

所以「KV cache 怎么算」这个问题，答案取决于架构是三选一：标准/GQA 用逐头公式，MLA 用潜向量公式，线性/SSM 用固定状态。抓错架构，整个长上下文的显存外推就错了。

## 落回 llm_spec 的设计

这解释了 `llm_spec.py` 为什么在模型配置里放了 `num_layers、num_key_value_heads、head_dim`，还有 `moe、num_experts、active_experts` 这些字段，而不是只存一个参数量。外推要算得准，这些结构量是必须的输入，缺一个，KV cache 或 MoE 的 decode 就算错。

当前两个模型的架构覆盖了两种情况：Qwen3.8-27B 是 dense 加 GQA（KV 公式简单，decode 用总参），GLM-5.3-Flash 是 MoE（decode 用激活参）。如果要验证这套外推模型对 MoE 也成立，得先确认它的注意力类型（是 GQA 还是 MLA），这决定 KV cache 用哪个公式，否则硬套会失真。

## 一句话总结

外推和模型的关系是「架构决定用哪个公式，参数决定代入哪个数」。说它和模型强相关，对 KV cache 和 MoE 成立；说它只依赖一个总参数量，对 dense 的显存和 decode 速度成立。分清这个，外推才不会在 MoE 和 MLA 上翻车。
