# 推测解码加速模型

> 整理日期 2026-09-08 · Python 3.13.0 · 脚本 `scripts/speculative_model.py` · 校准 GB10 社区 1.9x 加速

推测解码用小草稿模型生成候选 token，大目标模型一次前向并行验证，接受的直接采用。它是 GB10 跑出 23 t/s（相对 llama.cpp 12 t/s）的关键，这个模型回答：加速比由什么决定，以及为什么接受率是唯一的核心变量。

## 核心机制与公式

一次迭代：草稿模型自回归生成 k 个候选 token，目标模型一次前向并行验证这 k+1 个位置（含一个 bonus token）。赚到的 token 数是期望接受数：

```
E = (1-α^(k+1))/(1-α)
```

α 是草稿 token 被目标接受的比例。加速比 = E / (1 + k × cost_ratio)，cost_ratio 是草稿/目标单次前向成本比（小草稿远小于 1）。

关键洞察：**加速的全部来源是「一次目标前向验证多个 token」，但只有被接受的部分才赚到**。所以接受率 α 决定上限，草稿成本决定净收益。

## 加速比随接受率和草稿长度变化

cost_ratio=0.05（小 draft 模型）下的加速比：

| α | k=2 | k=4 | k=6 | k=8 |
|---|---|---|---|---|
| 0.5 | 1.59x | 1.61x | 1.53x | 1.43x |
| 0.7 | 1.99x | 2.31x | 2.35x | 2.28x |
| 0.8 | 2.22x | 2.80x | 3.04x | 3.09x |
| 0.9 | 2.46x | 3.41x | 4.01x | 4.38x |

两个规律：接受率越高加速比越大（α 从 0.7 到 0.9，k=8 时从 2.3x 到 4.4x）；k 不是越长越好，α 低时 k 大了浪费（α=0.5 时 k=8 反而比 k=4 慢，因为拒绝的多、白算）。所以草稿长度要匹配接受率。

## 校准 GB10 社区数据

社区实测（2026-08 阿里云测速）：GB10 上 Qwen3.8-27B，llama.cpp Q4_K_M 单流 12.1 t/s，SGLang + NEXTN 投机采样 23 t/s，加速比 1.9x。反解：达到 1.9x 需要的接受率，k=4 时约 α≥0.59，k=6 时约 α≥0.61。对应草稿模型质量较好（接受率六成以上），和 NEXTN（用目标模型自己的 MTP 头做草稿，接受率高）的设定一致。

## 草稿成本的影响

加速比受草稿成本 cost_ratio 影响（α=0.7, k=4）：

| cost_ratio | 加速比 | 有效 t/s（基线 12.1） |
|---|---|---|
| 0.02 | 2.57x | 31.1 |
| 0.05 | 2.31x | 28.0 |
| 0.10 | 1.98x | 24.0 |
| 0.20 | 1.54x | 18.6 |

草稿模型越大，cost_ratio 越高，净加速比越低。草稿太小接受率低，太大成本高，存在最优草稿规模。NEXTN 这类「用目标模型自身的草稿头」的方案，草稿成本和目标共享前向，cost_ratio 极低，所以能做到高净加速。

## 外推：乘法加速

推测解码是乘法加速，叠在任何基线之上（α=0.75, k=4, cost_ratio=0.05）：

| 基线 | 基线 t/s | 加速后 |
|---|---|---|
| llama.cpp q4 | 12.1 | 30.8 |
| SGLang nvfp4 | 18.0 | 45.8 |
| 4090 q4 | 49.0 | 124.6 |

基线越快，加速后越快，但加速比相同（都由 α 决定）。所以优化 decode 有两条相乘的路：提高基线带宽效率（量化、框架），提高接受率（更好的草稿模型）。GB10 要摸到更高速度，两条都要走。

## 实践判据

推测解码的价值几乎完全取决于接受率 α，而 α 由草稿模型和目标模型的分布对齐程度决定。选草稿模型时，优先用同系列、同分词器的小模型（或目标自带的 MTP 头），接受率最高。盲目加大草稿长度 k 在低接受率时反而有害。
