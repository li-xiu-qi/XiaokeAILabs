# 向量数据库的内存占用：如何测量才可比较

向量数据相同，不代表运行内存也相同：进程开销、索引结构、缓存、文件映射和服务依赖都可能影响读数。部署选型需要关心的是目标负载下的实际峰值和稳定占用，并明确把哪些进程和容器计入总量。

## 历史测试能说明什么

2026 年 9 月的记录使用 Windows 11、Ryzen 9 5900HX、64 GB 内存和 384 维向量，分别记录了嵌入式进程 RSS 与 Docker 容器内存。旧报告把两类增量放进同一张排名表，但它们的测量边界不同，且历史原始 JSON 未保留，因此**不能用这张表判断哪个数据库更省内存**。

旧稿把 SQLite 内存读数归因于页面压缩、把 Rust 侧分配解释为不计入同进程 RSS，这些说法没有充分依据；内存映射、缓存回收以及基线时点都可能影响差值，也不能仅凭某个阶段的增量推断索引内部存了什么。

## 如何设计可复核的测量

- **统一范围**：嵌入式方案统计完整进程及必要子进程；服务方案统计服务与依赖进程或容器，并说明客户端是否计入。
- **统一阶段**：记录空载、数据导入后、索引就绪后和稳定查询期间的占用，同时采样峰值，不只取两个时间点做差。
- **统一条件**：固定数据、索引参数、并发和查询负载，说明冷启动或预热状态，重复测试并保留原始时间序列。
- **解释指标**：RSS、容器内存和磁盘占用不是同一指标，文件缓存和共享内存的计量方式也会影响比较。

仓内 [`memory_bench3.py`](../scripts/memory_bench3.py) 保留分进程或容器采样的历史实现供阅读，入口已禁用。**其中 `drop_all` 会删除连接到的数据库里的全部集合**；不要连接已有数据的服务。脚本还需检查依赖、采样范围和结果保存方式，在全新隔离环境中修订并验证后才适合运行。
