# 向量数据库怎么选？从精确搜索到索引基准

[English](README.en.md)

![向量检索的准确率与成本](figures/search-tradeoff.svg)

知识库中的文档越来越多时，如何在可接受的时间内找出与问题相近的内容？向量数据库通过索引缩小搜索范围，但索引参数、内存和存储成本都会影响结果。这个实验介绍如何用同一批文本向量和查询，对比不同数据库及索引的**近邻召回率、查询延迟、构建时间和存储占用**，帮助你为自己的数据设计选型测试。目前可直接运行的是 sqlite-vec 合成数据示例，多库脚本仍需重新设计隔离。

本实验运行在 Windows CPU 设备上，并非 DGX Spark。历史报告缺少原始 JSON，数字只能作为历史记录和测试方法示例，不能作为可独立复核的产品排名。

## 先理解：为什么快，也可能漏结果

将文档和问题转换成向量后，精确搜索计算问题与所有文档的距离，再选出最近的 $k$ 个。它适合充当基准；数据变大时，逐一比较的成本也会增长。近似最近邻（ANN）索引通过组织向量、限制搜索范围或压缩向量来减少计算，但可能漏掉精确搜索中的近邻。

本实验使用平方欧氏距离生成精确近邻，并按每个问题的结果集合计算：

$$
\mathrm{Recall@}k = \frac{|\mathrm{ANN}_k \cap \mathrm{Exact}_k|}{k}
$$

例如精确搜索的前 10 个邻居中，索引找回 9 个，Recall@10 就是 0.9。报告汇总的是查询上的平均值。**这衡量的是索引对精确向量搜索的逼近程度，不是搜索结果对用户问题的语义相关性**；后者还需要人工标注、业务数据和独立评测。

选型时先确定能接受的召回率，再看满足它的配置在延迟、索引构建和空间上的成本。HNSW 的搜索宽度等参数可以调整速度与召回之间的权衡；不同索引和实现的参数含义并不总是一样，必须分别验证。

## 本次测了什么

| 项目 | 历史记录 |
|---|---|
| 机器 | Windows 11、Ryzen 9 5900HX、64 GB 内存，CPU 运行 |
| 数据 | 20 Newsgroups 英文文本，经 all-MiniLM-L6-v2 转为 384 维向量；报告记录约 11,293 条文档向量、40 条查询 |
| 对象 | Milvus、Qdrant 使用 Docker；SurrealDB 使用 Windows 原生进程；LanceDB、ChromaDB、sqlite-vec 为嵌入式 |
| 指标 | 精确 top-10 邻居的 Recall@10、查询延迟、建索引时间和存储增量 |

各库索引和参数不同，部署方式也不相同，因此这是一组**配置之间**的比较，不能直接归因于数据库本身。脚本会过滤部分过短文本，重建后的文档数量应以生成文件实际内容为准。

历史报告记载 Milvus HNSW 在 `ef=64` 时 p50 为 4.1 ms、Recall@10 为 0.985；LanceDB HnswPq 记录为 5.0 ms、0.538。这说明相近延迟下，配置的召回也可能相差很大，值得同时检查两项指标；两者采用不同索引，且缺少原始结果，不能由此断言产品优劣。[索引比较方法与历史记录](reports/向量索引-召回延迟与存储.md)

历史报告中的部分解释超出了现有证据，例如把某次调参无变化归结为量化的普遍特性；阅读时请以具体测量条件为限。40 条英文查询、混合部署方式和单机测试也不足以推断中文检索或线上并发性能。

## 安全运行：sqlite-vec 合成数据基准

旧版多库脚本可能删除固定名称的集合或文件，部分入口已禁用；其他历史脚本未全部加禁用保护，例如 `gen_emb.py` 会向固定路径写入并可能覆盖文件，请勿直接运行；下例只使用内存数据库和合成向量，不连接现有数据库，不读写用户文件。它仅展示精确向量搜索的测量方式，不构成跨产品排名。

```bash
python -m pip install numpy sqlite-vec
python scripts/safe_sqlite_bench.py --vectors 1000 --queries 20 --dimensions 32
```

输出查询平均 Recall@10 和查询耗时中位数。计时包含 Python 查询向量序列化、SQLite 执行和结果读取，不是纯数据库内核时间；没有单独预热，首个查询也计入。NumPy 精确距离作为参照，输出同时记录随机种子和依赖版本；不同平台、数据规模和线程条件会影响计时。历史多库基准需重新设计隔离资源后才能运行；[环境与测试方法](环境搭建.md)列出当前限制。
