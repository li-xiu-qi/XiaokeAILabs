# 部署踩坑记录

本篇记录 Jev-Omni 从干净环境到跑通四个模态过程中实际遇到的问题。只记工程细节与定位过程，通用结论与选型判断在实验报告与配套文章里。

## 一、transformers 必须 5.17.0

Jev-Omni 的底座是 Gemma 4，架构名 `Gemma4UnifiedForConditionalGeneration`。transformers 5.16 无法导入该架构，加载时直接报 `Could not import module`。官方 requirements 固定 5.17.0，不能降级。

## 二、权重格式与加载峰值

决策骨干以 FP32 分发，13 个分片共约 48 GB；底座 Gemma 4 是 BF16 单文件约 24 GB。

加载过程先把 FP32 骨干读入并搬上设备，再把全部 Linear 层转为 BF16，然后加载官方底座并替换其中的文本骨干。最终常驻约 27 GB，但读 FP32 分片阶段内存峰值接近 60 GB，统一内存设备上要按这个数字预留，不能只看最终显存。加载实测约 8 分钟，耗时集中在读盘，不是计算。

## 三、音频推理的 ffmpeg 覆盖问题

官方 `jev_omni.py` 处理音频时用 ffmpeg 把输入转码到临时 wav，命令没有传 `-y`。第一次运行正常；同一进程内第二次运行音频推理时，临时文件名复用，ffmpeg 会提示 `already exists. Overwrite? [y/N]`，非交互环境直接退出。

本实验的处理是运行时补丁：在 `_runtime.py` 里包一层 `subprocess.run`，检测到 ffmpeg 命令且没有 `-y` 时自动补上。不改官方文件，换权重版本也不丢失。

## 四、镜像与离线

直连 huggingface.co 不通的环境，下载时设 `HF_ENDPOINT=https://hf-mirror.com`，并设 `HF_HUB_DISABLE_XET=1`，镜像站对 Xet 存储返回 401。

权重缓存完整后，推理阶段开 `HF_HUB_OFFLINE=1` 和 `TRANSFORMERS_OFFLINE=1`。官方 loader 内部仍会调一次 snapshot_download，离线模式下直接命中缓存，不发请求。

## 五、音频后端依赖

processor 读取音频时调用 `transformers.audio_utils.load_audio`，该函数要求 librosa，缺了会在推理时报 `load_audio requires the librosa library`。requirements 已包含，注意 librosa 会带入 numba 和 scipy，安装时间较长。

soundfile 本身依赖 cffi 的 `_cffi_backend`，新装环境要同时装 cffi，否则 import 阶段报 `No module named '_cffi_backend'`。

## 六、视频延迟的构成

视频取 16 帧，16 张图要分别经过视觉编码器再合并进同一个序列。实测单次要 4 秒量级，不是某个环节异常。减少帧数可以线性降低这部分耗时，但会改变官方设定的输入形态，报告里要注明。

## 七、首次调用的初始化开销

模型加载完成后的第一次推理约 3 秒，明显高于后续调用，来自 CUDA 内核初始化。基准测试前必须预热，quickstart 与 bench 脚本都已包含预热步骤。

## 八、同一素材跨次判定存在波动（现象，未归因）

权重与测试素材均未改变，不同运行轮次之间，图像、音频、视频三组用例的判定与置信度出现明显变化。图像用例一轮三个选项概率压平、另一轮给出单一选项 0.99；视频用例在「基本静止」和「沿墙移动」之间翻转；音频的置信度分布也有明显移动。文本用例两轮一致。

这是只对比了两个轮次的现象，样本不足，不下机制结论，也不能判定模型不稳定。对使用方式的实际影响是：单次高置信结果不等于稳定判定，关键场景应重复采样或结合阈值，这一点在写部署文章时需要体现。后续可用固定素材多轮复跑来量化波动比例。
