# LLM-Viewer 历史对照：能从记录中确认什么？

历史记录曾将 LLM-Viewer 的阶段预测与标为实测的速率比较，并由此声称识别了实际带宽瓶颈；仓内历史测试脚本使用请求级 HTTP 耗时计算速率。**这组数字的计时边界不一致，不能验证阶段预测，也不能证明瓶颈。** 仓库内未见完整原始响应、逐层 CSV、模型配置与改动后的工具代码，无法独立重算或复现。历史测试脚本按整次 HTTP 耗时计算，但不能仅凭当前脚本确认当次运行版本完全一致。

## 原记录保留的数字

记录注明 2026-09-13、DGX Spark GB10、Qwen3.8-27B BF16、batch 1、输入长度 128。原文记录了以下数字；模型版本和完整运行环境未能由本仓证实：

| 旧标签 | LLM-Viewer 输出记录 | 请求侧计算值的历史记录 |
|---|---:|---:|
| Decode token/s | 6.07 | 4.35 |
| Prefill token/s | 730.5 | 152.04 |
| Q4 decode token/s | 22.31 | 没有对应实测 |

请求总耗时包含输入处理、生成、排队和网络，不等于纯 prefill 或 decode 时间。因此两列的比值只是不同口径数字的算术比，不是可信的预测误差。不同模型输入、输出、引擎及缓存条件也会影响读数。

## 两处不能成立的推导

1. **拟合量不是实测带宽。** 历史文档以假定的 51.1 GB 权重读取量和请求总耗时反推 60.7 GB/s。请求计时不是 prefill 计时，且每次真实读取量没有由 profiler 或硬件计数器测得；该商不能当作已测的内存流量或带宽利用率，也无法证明所有算子受内存带宽限制。
2. **误差拆分本身不相等。** 730.5 除以 152.04 约为 4.80；旧文声称这个比值等于 $1.14\times4.50$，而后者是 5.13。即使算术一致，没有独立测量权重读取量与阶段时间，也不能据此归因。

从一个数据点反推系数再代回同一数据点，得到接近零的误差是代数结果，不是独立验证。这里不能据此得出“prefill 带宽只有 decode 的四分之一”或某种设备必然是带宽瓶颈。

## 如何重新验证

记录模型和 tokenizer 的固定版本、模型配置及实际权重文件字节数，保存工具版本、源码改动和 LLM-Viewer 原始输出。固定输入与输出 token 数、采样、预热及缓存设置，使用服务端阶段指标或逐 token 时间戳分别测量 prefill 与 decode；将请求级耗时单独报告。在未用于参数标定的长度和并发上检验预测，记录逐次读数和误差。判断实际瓶颈还需要 profiler 或硬件计数器，而非以假定权重字节数反推。

[LLM-Viewer 论文](https://arxiv.org/abs/2402.16363)介绍理论性能分析；本仓[使用边界与审计](使用边界与审计.md)列出其他历史脚本的限制。[推理成本估算指南](推理成本估算指南.md)提供使用实际数据检验简化假设的例子。
