# 推理成本估算指南

## 先明确输入和输出

输入至少包含模型架构与实际权重大小、权重和 KV 精度、上下文长度、同时活跃的序列数，以及硬件可用内存和计算与带宽规格。服务系统还要明确请求长度分布、到达速率、引擎版本、并发策略与延迟目标。

输出应分别描述：权重及 KV 的预算，额外状态和运行时内存余量，预期需要测量的吞吐、首 token 延迟和逐 token 间隔。任何没有独立验证的速度数值只能作为假设情景，不能作为服务承诺。

## 1. 先算能否装下

权重的粗略预算为参数量乘以平均每参数字节数；量化文件通常还有比例因子、元数据和未量化张量，因此最好读取具体文件的字节数。文件大小也不必然等于加载后的内存占用。

标准全注意力的 KV 预算参见[首页公式](../README.md#从一个问题开始上下文会占多少内存)。同一个模型可能既有全注意力层，也有需要维护其他状态的层；每种状态应分别计入。计算所得是指定缓存布局下的数据体积，不包含分页碎片、临时工作区和框架保留内存。

可用空间也不是机器标称容量：操作系统、其他进程、分配器和设备保留都会影响可用值。将所有数量先换算成字节，再统一显示为十进制 GB 或二进制 GiB，避免相加时混用。

## 2. 再理解计算与数据移动

Roofline 的基本思想是比较运算需求和数据移动需求。算术强度 $I=F/D$ 表示每搬运一字节需要多少 FLOP；给定相应精度下的算力上限 $P$ 和内存带宽上限 $W$，理想化性能上界为：

$$P_{\mathrm{ideal}}=\min(P, I W)$$

这里的 $F$ 与 $D$ 必须对应同一操作、同一内存层级和同一工作量。它提供上界而非实际速度；不完整的数据移动估算、峰值规格与 kernel 差异都可能造成大误差。单请求 decode 有时可用读取权重的简化模型启发估算，但不应假设所有权重每一步必然从同一内存层读取，也不能忽略 KV、计算和调度。

## 3. 长上下文为何影响成本？

对长度 $S$ 的非因果稠密全注意力，假定一次乘加算两个 FLOP，计算 $QK^T$ 和 attention 与 $V$ 相乘约需

$$F_{\mathrm{attn}}\approx 4 B L H_q S^2 d_h.$$

这里 $H_q$ 是查询头数，$L$ 仅包含所估算的全注意力层。该式不包括投影、MLP、softmax 和其他类型的层。因果掩码的实际工作量取决于 kernel 如何跳过掩码区域，不能直接套用未经说明的常数。

如果一层的分数矩阵完整物化，其大小为 $B H_q S^2 b$ 字节；这只是一个中间张量，不等于系统峰值内存。FlashAttention 通过分块减少高带宽内存上的中间结果读写，避免完整物化该矩阵；它不能消除稠密注意力的平方级计算，也不能单独保证任意上下文可以装入内存。[FlashAttention 原论文](https://arxiv.org/abs/2205.14135)

## 4. 如何验证估算

1. 保存模型版本、配置、权重文件字节数、引擎版本和启动参数；确认权重和 KV 的精度。
2. 固定真实输入和输出 token 数，记录暖机、并发、缓存与采样设置；多次运行并保存原始结果。
3. 使用引擎阶段指标或逐 token 时间戳测首 token 延迟与生成间隔。HTTP 总请求时间包含排队、输入处理、输出生成及网络，不能直接叫做纯 decode 时间。
4. 将参数标定与评估数据分开，在不同长度和并发上报告误差与分布。判断带宽或计算瓶颈时结合 profiler 计数器，而不是只凭速度拟合。

模型的价值在于帮助确定该测什么、解释假设改变时的预算如何变化；实测与估算不一致时，应先核对计时边界、单位和架构，再考虑调整假设。
