# 六库分词器实现与中文支持

> 实测日期 2026-09-06 · 脚本 `scripts/probe_chinese_tokenizer.py` · 源码位置 `CodeProjects/_reference/projects/infra-and-backend/`

## 这个文档是干嘛的

回答两个问题：六个库的 BM25 各自用什么做分词，以及中文场景下哪些能用、哪些不能用。

它与 `docs/六库BM25支持度与接入难度.md` 分工不同。那份文档回答「有没有 BM25、接进来多麻烦」，本文档只回答「分词这一层具体怎么实现的」。BM25 的打分公式（k1/b/avg_len）六个库都实现了且参数可调，差异全在分词和索引结构上，而中文能不能用完全由分词决定。

## 六库里只有 Milvus 和 LanceDB 能在中文上工作

中文不是「需要分词」而是「需要分字或分词」，因为中文没有空格分隔。按空白切分的分词器对中文无能为力，整句会变成单个 token，BM25 退化成字符串精确匹配。

六个库里只有 Milvus 和 LanceDB 能在中文上正常工作，且路径完全不同。Milvus 把 jieba 编进了二进制，一个 JSON 参数就能用，还能用 `language_identifier` 在中英文混合语料里自动路由。LanceDB 需要换 `base_tokenizer`，中文可用的 `icu`（按单字切）和 `ngram` 都有噪声，它也有 jieba 但要外挂词典模型。SurrealDB、Qdrant、ChromaDB 三个在中文上确实不可用，sqlite-vec 没有全文检索。

## 分词器实现对照

| 库 | 分词实现 | 可选分词器 | 中文能力 |
|---|---|---|---|
| Milvus 3.0.0 | tantivy 的 C++ 绑定 | `jieba` `icu` `lindera` `language_identifier` `standard` `whitespace` `ngram` `class` `blank` `punct` `camel` | **原生 jieba，可自动识别语言** |
| LanceDB 0.38.0 | lance 的 Rust 实现 | `simple`(默认) `raw` `whitespace` `ngram` `icu` `icu/split`，外加 model-backed 的 `jieba/*` `lindera/*` | 换 `icu`/`ngram` 可用，jieba 需外挂词典 |
| SurrealDB 3.2.4 | 自研，analyzer 需 `DEFINE` | `Tokenizer` 只有 `Blank` `Camel` `Class` `Punct` | 无 |
| Qdrant 1.19.0 | `BasicTokenizer` = Rust `split_whitespace()` | 无额外选项 | 无 |
| ChromaDB 1.5.9 | `Bm25Tokenizer` = 正则去符号 + 空白切 + snowballstemmer | 无 | 无 |
| sqlite-vec 0.1.9 | 无全文检索 | 宿主 SQLite 可另建 FTS5 | 取决于宿主 |

## 逐库实现

### Milvus：唯一把中文分词编进二进制的

分词器在 C++ 层，路径 `internal/core/thirdparty/tantivy/tantivy-binding/src/analyzer/tokenizers/`。这个目录下有 `jieba_tokenizer.rs`、`icu_tokneizer.rs`、`lindera_tokenizer.rs`、`lang_ident_tokenizer.rs`、`ngram_tokenizer_with_chars.rs`、`char_group_tokenizer.rs`、`thai_tokenizer.rs` 共七个实现，覆盖中日泰等多种语言。

jieba 分词器用的是 `jieba_rs`，默认 `mode=search`、`hmm=true`，还内置了一份扩展词典 `dict.txt.big`（通过 `include_str!` 编译进二进制，不需要外部文件）。mode 可选 `search` 和 `exact`，search 模式会把长词再切细以提升召回。词典可通过参数覆盖，支持自定义系统词典和用户词典。

**`language_identifier` 是 Milvus 独有的能力**，源码在 `lang_ident_tokenizer.rs`。它用语言识别库（可选 `whatlang` 或 `lingua`，后者基于 `LanguageDetectorBuilder::from_all_languages()`）判断每段文本的语言，然后按 `analyzers` 映射表路由到对应分词器。映射表里 `"Chinese": "jieba"`、`"Mandarin": "jieba"` 是硬编码的语言名，识别不出来时落回 `default`。这意味着同一个字段里中文文档走 jieba、英文文档走 standard，自动分流。

配置方式是通过字段的 `analyzer_params` 传 JSON：

```json
{"tokenizer": {"type": "language_identifier", "identifier": "lingua",
  "analyzers": {"default": {"tokenizer": "standard"},
                "Chinese": {"tokenizer": "jieba", "mode": "search"}}}}
```

一个已踩的坑：`analyzers` 映射里放 `"mode"` 会被拒，报 `unknown analyzer option key: mode`。映射里的子分词器只接受 `tokenizer` 一个键，要调 mode 得直接在主 tokenizer 里用 jieba，不能走 language_identifier 这条自动路由。

### LanceDB：能力全，但要自己选对

lance 层的分词器在 `rust/lance-index/src/scalar/inverted/tokenizer/`，目录里除了 `tokenizer.rs` 还有 `jieba.rs` 和 `lindera.rs`，底层可用组件包括 `SimpleTokenizer`、`RawTokenizer`、`WhitespaceTokenizer`、`NgramTokenizer`、`IcuTokenizer`、`AsciiFoldingFilter`、`StopWordFilter`、`Stemmer`、`LowerCaser` 等。

Python 侧通过 `create_fts_index()` 的 `base_tokenizer` 参数暴露，类型定义在 `lancedb/types.py`：

```python
BuiltinTokenizerType = Literal["simple", "raw", "whitespace", "ngram", "icu", "icu/split"]
BaseTokenizerType = BuiltinTokenizerType | str   # str 用于 "jieba/*" "lindera/*"
```

默认值是 `simple`，对应 tantivy 的 SimpleTokenizer，按非字母数字字符切分。中文全是连续的「字」，在它眼里没有分隔符，所以默认对中文无效。

`icu` 和 `icu/split` 走 `icu_segmenter::WordSegmenter`，按 UAX#29 词边界切分，中文按单字切。`ngram` 按固定窗口切字符，中文可用但索引体积和噪声都更大。`jieba/default`、`lindera/ipadic` 这类是 model-backed，需要把词典模型放到 Lance 的 language model home 目录（`~/.lance/language_models`），不如 Milvus 开箱即用。

### SurrealDB：四种 tokenizer，都不是为无空格语言设计的

`Tokenizer` 枚举定义在 `surrealdb/core/src/expr/tokenizer.rs`，只有四个值：

```rust
pub enum Tokenizer { Blank, Camel, Class, Punct }
```

`Blank` 按空白切，`Punct` 按标点切，`Camel` 按驼峰命名切，`Class` 按字符类别（字母/数字/符号）切。中文文本在这些规则下都是连续的同类别字符，没有任何切点。

`Filter` 枚举有 `Ascii` `EdgeNgram` `Lowercase` `Ngram` `Snowball(Language)` `Uppercase` `Mapper(String)`。Snowball 支持 19 种语言（阿拉伯语到土耳其语，全是拼音文字，无中文）。理论上可以用 `Mapper` filter 自己插入切分符号，但这等于自己实现分词器，不属于「支持中文分词」。

### Qdrant：源码注释自己承认只是起步用

`lib/bm25/src/basic_tokenizer.rs` 的模块注释写得很直白：

> Whitespace tokenizer with optional lowercasing. Enabled by the `basic-tokenizer` feature. Provided for quick-start and tests — production users will normally bring a richer pipeline (stemming, stopwords, language-aware splitting).

实现就是 `input.split_whitespace()` 加可选小写化。分词结果用 `token_id()` 映射成 `u32`，算法是 Murmur3 32 位哈希后取绝对值，与 qdrant 既有的 BM25 稀疏向量 wire 兼容。

`Bm25Config` 的结构体字段很完整（`k` `b` `avg_len` `tokenizer` `language` `lowercase` `ascii_folding` `stopwords` `stemmer` `min_token_len`），参数层面与 Milvus、LanceDB 对齐，但底层只有 whitespace 这一种实现。中文场景要自己接分词器。

### ChromaDB：为英文设计的完整流水线，中文全部失效

实现在 `chromadb/utils/embedding_functions/schemas/bm25_tokenizer.py`，`Bm25Tokenizer.tokenize()` 的流程是四步：

1. `_remove_non_alphanumeric()`：正则 `[^\w\s]+` 带 `re.UNICODE` 替换成空格
2. `_simple_tokenize()`：`text.lower().split()` 按空白切
3. 过滤停用词（内置 `DEFAULT_ENGLISH_STOPWORDS`，约 130 个）
4. 过滤超长 token，过 `snowballstemmer.stemmer("english")` 做词干提取

前三步对中文无效（没有空格），第四步的英文词干提取对中文也无意义。实测「向量数据库的索引构建」被切成 `['向量数据库的索引构建']` 一个 token，同一段英文 "the vector database index building" 切成 `['vector', 'databas', 'index', 'build']` 四个，`database` 被还原为 `databas`。

依赖 `snowballstemmer` 和 `mmh3` 两个纯 Python 包，缺任何一个都会在 EF 构造时抛 ValueError。本环境的 pip 装包曾被一个未启动的本地代理挡住，需清空 `HTTP_PROXY`/`HTTPS_PROXY` 环境变量才能装上。

## 中文实测

语料 4 条中文句子（向量数据库、索引构建时间、天气散步、全文检索），查询「向量数据库的索引构建」，doc0 为语义相关文档。

| 库 | 配置 | 命中结果（文档下标, BM25 分） |
|---|---|---|
| Milvus | 默认无 analyzer | 空 |
| Milvus | `{"tokenizer":{"type":"jieba","mode":"search"}}` | doc0 **4.62**、doc1 4.01、doc2 0.70 |
| Milvus | `{"tokenizer":{"type":"jieba","mode":"exact"}}` | doc1 3.82、doc0 2.18、doc2 0.72 |
| Milvus | `{"tokenizer":{"type":"icu"}}` | doc1 5.03、doc0 3.36、doc2 0.69 |
| Milvus | `language_identifier`（lingua + Chinese→jieba） | 中文查询 doc1 4.34、doc0 4.25；英文查询 doc3 4.25 |
| LanceDB | `simple`（默认） | 空 |
| LanceDB | `icu` | doc1、doc0、doc2 |
| LanceDB | `icu/split` | doc1、doc0、doc2 |
| LanceDB | `ngram` | doc0、doc1 |
| LanceDB | `raw` | 空 |
| SurrealDB | `punct` / `class` / `blank` | 全空 |
| ChromaDB | `ChromaBm25EmbeddingFunction` | 全 4 条返回，距离 0.815/0.922/1.004/1.115 |

三个值得注意的细节。

**jieba 的分数尾部衰减快**（4.62、4.01、0.70），无关文档被压到很低分；icu 按单字切会把无关的 doc2「今天天气很好」带进结果（0.69 到 0.72），因为单字重叠的误匹配多。中文场景优先 jieba。

**jieba search 与 exact 的排序不同**。查询含「向量数据库」和「索引构建」两个词，doc0 两个词都有，doc1 只有「索引构建」。search 模式 doc0 排第 1，exact 模式 doc1 排第 1。差异来自 search 模式对长词的二次切分改变了词项权重分布，选哪种取决于更看重精确匹配还是召回。

**Milvus 的 language_identifier 在中英混合语料上路由正确**。同一字段里中文查询只召回两个中文文档，英文查询「inverted index keyword」只召回英文文档 doc3，没有交叉污染。这是六个库里唯一能做到的能力。

## snowballstemmer 与词干提取

snowballstemmer 是 Porter 词干提取算法的 Snowball 多语言实现，纯 Python 包（约 104 KB，无第三方依赖），作用是去掉英文单词的词形变化：`database`→`databas`、`building`→`build`、`running`→`run`。

英文检索必须做这一步，否则同根词会被当成不同词，召回直接漏。Snowball 本身是一套词干提取算法的形式化描述语言，除了 Porter 还覆盖其他语言的变体。ChromaDB 调 `snowballstemmer.stemmer("english")` 固定用英语，SurrealDB 的 `Snowball(Language)` filter 支持 19 种语言。

中文没有词形变化，也不需要这一步，所以 snowballstemmer 在中文场景完全不起作用。它出现在 ChromaDB 的 BM25 流水线里，只是那套流水线为英文设计的佐证。

## 选型建议

中文场景首选 Milvus，理由是 jieba 编译进二进制、无需外部词典、`language_identifier` 还能自动处理中英混合语料。次选 LanceDB，用 `icu` 或 `ngram` 能跑，但要在建索引时就决定用哪个分词器，且按单字切有噪声。

如果已经在用 SurrealDB 或 Qdrant，中文全文检索要自己在应用层分词（接 jieba 分词后用空白拼接再入库），等于把 Milvus 内置的能力搬到自己的代码里维护。这条路可行但要注意：分词必须在写入和查询两侧用同一套逻辑和同一份词典，否则查不出来。

ChromaDB 在中文上的表现是四个库里最弱的，不是配置问题而是架构问题，它的 BM25 是稀疏向量形式的 embedding function，整句一个 token 意味着词项空间极度稀疏，BM25 的打分几乎没有区分度。

## 复现

```bash
cd experiments/test_vector_db_bench
./.venv/Scripts/python.exe scripts/probe_chinese_tokenizer.py
```

脚本覆盖 Milvus 四种 analyzer 配置、LanceDB 五种 `base_tokenizer`、SurrealDB 三种 tokenizer、ChromaDB 一种。需要 Milvus（19530）和 SurrealDB（8000）在运行。
