# 主流分词器横向对比

> 调查日期 2026-09-06（THULAC 与 cang-jie 于同日补 clone 并完成源码核实） · 源码 `CodeProjects/_reference/projects/nlp-and-tokenizers/`（9 个仓库，623 MB） · 本地环境 `.venv`（jieba 0.42.1）、`.venv-ov`（openviking 0.4.17）

本文回答「有哪些主流分词器、它们有什么区别、我的场景该选哪个」。与 `docs/分词器的组成环节.md` 分工不同：那篇做 jieba 单点纵深（词典、DAG、HMM、四种模式），本文做横向对照。与 `docs/六库分词器实现与中文支持.md` 的分工是：那篇讲六个向量库各自接了哪个分词器、中文能不能用，本文讲分词器本身从哪来、底层怎么切。

**选型结论先行**：中文检索用 jieba（Milvus 已内置，开箱可用）；要跨语言统一用 ICU；日文用 Lindera；纯英文或嵌入式轻量场景用 tantivy 的 Simple/Whitespace；需要完整 NLP 流水线（词性、实体、句法）才上 HanLP，只为分词上 HanLP 是过度投入。

## 先把分词器分成三类

网上的对比文章常把 jieba 和 SentencePiece 放在一张表里比，那是两类东西混谈。分词器按解决什么问题分三类，选型时先定类再比同类。

**词级分词器**解决「这句话由哪些词组成」，面向全文检索。中文是主战场，因为中文没空格。jieba、HanLP、THULAC、pkuseg、IK Analyzer、Lucene SmartChinese 都属这类。

**子词分词器**解决「词典外的词怎么表示」，面向模型输入。英文为主，中文也用。BPE、WordPiece、SentencePiece、Unigram、tiktoken 属这类。它不关心语言学上的「词」，只关心用有限词表覆盖语料。向量库的 embedding 侧走这类，BM25 侧不走。

**字符级与规则分词器**解决「没有词典时怎么切」，是兜底。按空白切、按标点切、按单字切、按二元组切都属这类。tantivy 的 Simple/Whitespace/Raw/Ngram、Lucene 的 Standard/CJK、ICU 都在这类里。

BM25 全文检索用的是第一类和第三类，第二类不参与。所以本文重心在前两类，第三类作为「无词典时的默认行为」单列一节。

## 词级分词器：中文主战场

### jieba：中文检索的事实标准

前缀词典加 DAG 加动态规划加隐马尔可夫模型，四种切分模式，MIT 协议。它的地位不是精度最高，而是三个偶然因素叠加：纯 Python 无依赖、安装即用、Milvus 把它编译进了二进制。

最后一个因素对本文最重要。Milvus 内嵌的是 Rust 移植版 `jieba_rs`，算法同源，默认 `mode=search`、`hmm=true`，词典 `dict.txt.big` 通过 `include_str!` 编译进二进制，不需要外部词典文件。这让 Milvus 成为六个向量库里唯一中文开箱可用的。

jieba 的短板在生僻领域。词典是通用词表，医学、法律、金融的术语识别依赖用户词典，而用户词典要自己维护。官方 README 给的速度是精确模式 400 KB/s、全模式 1.5 MB/s（测试环境 i7-2600），这个量级在批量建索引时会成为瓶颈。

### HanLP：功能最全，但为分词用它过重

复旦团队维护，Apache 2.0（代码），PyTorch 加 TensorFlow 双引擎。HanLP 2.1 覆盖 130 种语言的 10 种联合任务，分词只是其中一项。

它和 jieba 的差别不在分词精度，在能力半径。HanLP 一套接口给出分词、词性标注（ctb/pku/863 多标注集）、命名实体识别（msra/ontonotes）、依存句法、语义角色标注、关键词提取、指代消解。官方文档称在 sighan2005 PKU 语料上训练 6 分钟可复现 96.73% 的准确率。

代价是体积和依赖。它要拉模型文件，CPU 可跑但推荐 GPU。只为中文 BM25 分词引入 HanLP，等于为了一个函数装一整个 NLP 平台。只有在同一套代码里还需要实体识别、句法分析时才划算。

需要注意它的授权分层：代码是 Apache 2.0 可商用，但多语种模型沿用 CC BY-NC-SA 4.0，中文模型「仅供研究与教学使用」。商用场景要先确认模型授权。

### THULAC 与 pkuseg：学术出身，工程化程度低

THULAC 是清华的词法分析工具，pkuseg 是北大的分词工具。两者在论文和竞赛场景常见，工程集成少。THULAC 的 Python 版是纯 Python 实现（`thulac/base`、`thulac/character`、`thulac/manage` 三模块，无 C++ 扩展），另有独立的 C++ 版仓库（MIT 授权）；pkuseg 的维护活跃度明显低于前两者。

THULAC 与 jieba 的架构差异值得记一笔，源码里看得很清楚。jieba 是「词典 + DAG 最短路径 + HMM 新词发现」三段式（见 `docs/分词器的组成环节.md`），THULAC 走的是逐字序列标注：`base/Node.py` 定义字节点、`base/WordWithTag.py` 是带词性的词节点、`base/AlphaBeta.py` 承担标注解码，`cut()` 把句子切成段后逐段跑 `__cutline`。两者结果形态都是词序列，但歧义消解机制不同，THULAC 的词序列天然带词性标注，jieba 的词性要另开 `posseg`。这决定了它们在「只要词」的 BM25 场景里等价，在需要词性的场景里 THULAC 更省一层。

局限同样是架构带来的：THULAC 最后提交停在 2018 年，没有 Rust 实现，Milvus/LanceDB 这类把分词器编译进二进制的库不可能内嵌它，只能走外部预处理。这一点和 jieba 形成鲜明对比，jieba-rs 让 Milvus 直接内置了中文分词能力。

本次调查早期尝试 clone THULAC 时用错了仓库路径（`thu-colj/THULAC`），该组织下并无仓库，`Repository not found` 被我误判成网络故障。修正为 `thunlp/THULAC-Python`（2083 star）与 `thunlp/THULAC`（C++ 版，833 star）后 clone 成功，见下表。这个误判过程本身值得记：把「路径写错」和「网络不通」当成同一类失败，会让排查方向整个偏掉。

### IK Analyzer：Java 与 Elasticsearch 生态的默认选择

如果检索栈是 Elasticsearch，IK Analyzer 是国内最常用的中文分词插件。它支持 `ik_smart` 粗粒度切分和 `ik_max_word` 细粒度切分两种模式，后者对应 jieba 的全模式思路，用切细换召回。

它基于正向、逆向、双向最大匹配融合，加词频与词性统计的动态权重，支持用户词典热加载。对电商搜索、日志分析这类场景成熟度较高。

本文不把它列为首选，因为它是 Java 生态组件，而本次基准的六个向量库都不走 Elasticsearch。列出来是为了完整性：选 ES 做检索时，IK 是默认答案。

### 一句话区分这几个

jieba 是「够用且零摩擦」，HanLP 是「全能但重」，THULAC 和 pkuseg 是「学术可用但工程冷」，IK 是「ES 生态专用」。中文检索没有「哪个精度最高」的单一答案，因为精度高度依赖领域词典，而词典是用户自己配的。

## 字符级与规则分词器：没有词典时的默认行为

这类分词器决定「不装任何中文分词器时会怎样」。答案是：中文会被整句切成一个 token，BM25 退化成字符串精确匹配。这是本次基准里四个库中文不可用的根因。

### tantivy SimpleTokenizer：按 `is_alphanumeric` 切

LanceDB 默认走的就是它。源码在 `tantivy/src/tokenizer/simple_tokenizer.rs`，核心是 `search_token_end()`：

```rust
.filter(|(_, c)| !c.is_alphanumeric())
```

它把「连续的字母数字字符」视为一个词。中文的每个字都是 alphanumeric，字与字之间没有非字母数字字符，所以整句命中成一个 token。英文按空白和标点断开，行为正确。这就是为什么 LanceDB 不换 `base_tokenizer` 就完全不能用中文。

tantivy 还提供 `RawTokenizer`（整段不切）、`WhitespaceTokenizer`（只按空白切）、`NgramTokenizer`（按固定窗口切字符）、`LowerCaser`、`AsciiFoldingFilter`、`RemoveLong`、`StopWordFilter`、`Stemmer`。这些是组件，可以自由拼成分析器流水线。

### ICU：按 Unicode 标准切，中文按单字

ICU 走的是完全不同的路线，依据 Unicode Standard Annex #29 的词边界规则切分，不依赖任何语言的词典。对中文它按单字输出，对日文按词输出，对泰文有专门处理。

它的价值在跨语言统一。一个 ICU 分词器覆盖中文、日文、韩文、泰文、阿拉伯文以及所有拉丁字母语言，不需要为每种语言配一个分词器。代价是中文按单字切会有噪声，本次实测中 icu 把无关文档也召回了，而 jieba 按词切没有这个问题。

Milvus 和 LanceDB 都提供 ICU 选项（Milvus 的 `{"tokenizer":{"type":"icu"}}`，LanceDB 的 `base_tokenizer="icu"` 或 `"icu/split"`）。作为兜底方案够用，追求中文精度仍应选 jieba。

### Lucene Standard 与 CJKBigramFilter

Lucene 的 StandardTokenizer 同样按 Unicode 类别切，对中文输出单字。它的中文能力靠 `CJKBigramFilter` 补齐，该 filter 把 StandardTokenizer 或 ICUTokenizer 输出的单字再两两组成二元词，官方注释写明「Forms bigrams of CJK terms」。这是「二元覆盖方式」，相邻两字成词。

SmartChineseAnalyzer 是 Lucene 里基于隐马尔可夫模型的中文分词器，输出词级结果，但只在 `lucene/analysis/smartcn` 模块，不在 common 里，需要额外依赖。

## 子词分词器：给模型用的，BM25 用不到

这一类要单独说清楚边界，因为很容易被误插到检索链路里。

BPE（Byte Pair Encoding）、WordPiece、Unigram、SentencePiece、tiktoken 都是为了解决同一个问题：词表不可能覆盖所有词，要把词拆成可复用的子词单元。它们的优化目标是压缩率和模型效果，不是语言学正确性。`database` 被切成 `data` 加 `base` 再加后缀，在人看来是错的，在模型看来是高效的。

BM25 的打分依赖词频和文档频率统计，子词切分会把一个词拆成多个统计单元，破坏 IDF 的语义。所以全文检索链路里不应该出现子词分词器，它们在 embedding 模型输入侧。

一个容易混淆的点：ChromaDB 的 `Bm25Tokenizer` 用了 snowballstemmer 做词干提取，那是词元过滤不是子词分词。词干提取把 `databases` 归到 `database`，子词分词把 `database` 拆成碎片，两者方向相反。

## 各库内置分词器对照

这张表回答「我用的向量库自带什么，能不能换」。

| 库 | 默认 | 可选项 | 中文可用 |
|---|---|---|---|
| Milvus 3.0.0 | standard（按 Unicode 类别） | `jieba` `icu` `lindera` `language_identifier` `ngram` `whitespace` `class` `blank` `punct` `camel` | jieba 原生，可自动识别语言路由 |
| LanceDB 0.38.0 | simple（tantivy 的 is_alphanumeric） | `raw` `whitespace` `ngram` `icu` `icu/split`，model-backed 的 `jieba/*` `lindera/*` | icu/ngram 可用，jieba 需外挂词典 |
| SurrealDB 3.2.4 | 无内置，必须 `DEFINE ANALYZER` | `Blank` `Camel` `Class` `Punct` | 无 |
| Qdrant 1.19.0 | BasicTokenizer（`split_whitespace`） | 无 | 无 |
| ChromaDB 1.5.9 | Bm25Tokenizer（正则去符号加空白切加 snowballstemmer） | 无 | 无 |
| sqlite-vec 0.1.9 | 无全文检索 | 宿主 SQLite FTS5 | 取决于宿主 |
| VikingVectorIndex | 无（只有 FLAT / FLAT_HYBRID 两种向量索引） | 无 | 无，需调用方自算稀疏向量 |

Milvus 的 `language_identifier` 值得单独说。它用语言识别库（可选 whatlang 或 lingua）判断每段文本的语言，按映射表路由，映射表里 `"Chinese": "jieba"` 和 `"Mandarin": "jieba"` 是硬编码的。这让中英混合语料能自动分流，实测中文查询只召回中文文档、英文查询只召回英文文档，六个库里独一份。

## 局限

本文对 jieba、THULAC、tantivy、Lucene、ICU 的描述有源码支撑，对 pkuseg、IK Analyzer、HanLP 模型精度的描述来自官方文档与二手对比文章，未做本机实测（这三个仓库未 clone，结论未做源码级核实）。HanLP 的 96.73% 是官方文档在 sighan2005 PKU 语料上的自报结果，我没有复现，引用时应当作厂商口径而非独立验证。

各分词器在中文上的精度对比（jieba vs HanLP vs THULAC 在同语料同词典条件下的 F1）本次没有做。那需要一份统一标注的分词语料和受控的实验设计，属于另一个课题。本文只做到「有哪些、底层怎么切、我的场景选哪个」。
