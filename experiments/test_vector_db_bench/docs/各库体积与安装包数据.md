# 各向量库体积与安装包数据对比

## 这个文档是干嘛的

记录本次基准测试涉及的七个向量库在三个维度上的体积：克隆源码、分发的安装包、运行时的内存占用。三者的量级差一个数量级以上，混谈会得出错误结论（「仓库几百 MB 所以不适合嵌入式」是错的）。

同时记录 seekdb 从 v1.3.0 到 v1.4.0 的轻量化进展，这是判断它能否进入嵌入式/边缘场景选型的关键依据。

## 七个库的体积总览

| 库 | 类型 | clone 源码（depth 1） | pip 包 | Docker 镜像 | 二进制安装包 |
|---|---|---|---|---|---|
| Milvus | 服务型 | 167 MB | 4.4 MB（pymilvus） | 3.93 GB（含 etcd+minio） | — |
| Qdrant | 服务型 | 50 MB | 4.7 MB（qdrant-client） | 270 MB | 29-35 MB（各平台 tar.gz/zip） |
| SurrealDB | 服务型 | 50 MB | 0.5 MB（surrealdb） | — | 110 MB（surreal.exe Windows） |
| LanceDB | 嵌入式库 | 31 MB（Python SDK）+ 78 MB（Rust core） | 313.7 MB（含 Rust 核心） | — | 60-104 MB（PyPI wheel） |
| sqlite-vec | 嵌入式库 | 4.4 MB | 0.3 MB | — | — |
| ChromaDB | 嵌入式库 | — | 3.6 MB | — | — |
| seekdb | 服务型 | 315 MB | 50 MB（Python package） | — | 54.6-218 MB（RPM/deb） |

注：clone 体积为 `du` 实测（2026-09-05），pip 包体积为本地 site-packages 实测，Docker 镜像体积为 `docker images` 实测，二进制安装包体积来自 GitHub Releases / PyPI（2026-09-05 检索）。

## 三个维度不能混谈

以 seekdb 为例（2026-09-05 实测）：

| 维度 | seekdb 实际值 | 说明 |
|---|---|---|
| 克隆源码 | 315 MB（depth 1，已删 `.git`） | 给开发者看的，含测试工具链 |
| 安装包 RPM x86_64 | 54.6 MiB（v1.4.0） | 压缩包，用户实际下载量 |
| 安装包 deb amd64 | 218.2 MiB（v1.4.0） | Debian 系打包，含组件更多 |
| 安装后 binary | 132.4 MiB（v1.4.0 官方数据） | 可执行文件本体 |
| 稳态运行内存 | 166.3 MiB（v1.4.0 官方数据） | 空载常驻 |

clone 体积里有 140 MB 是 `tools/obtest/` 测试工具链，对使用者无价值，其中 `mytest.jar` 89 MB 是 Oracle JDBC 驱动（OceanBase 要兼容 Oracle 协议，压测需连 Oracle；该驱动在 oracle.com 下载需登录，故提交进仓库保证 CI 可离线搭建），`prepare_t2_10w_data.sql` 16 MB 是造数脚本。

## 轻量化进展：seekdb v1.3.0 → v1.4.0

官方 release notes 给出的对比（这是判断它能否进嵌入式场景的核心依据）：

| 指标 | v1.3.0 | v1.4.0 | 降幅 |
|---|---|---|---|
| Binary | 366.2 MiB | 132.4 MiB | 63.9% |
| Python package | 160.0 MiB | 50.0 MiB | 68.8% |
| 稳态内存 | 630.6 MiB | 166.3 MiB | 73.6% |
| 稳态 CPU | 0.05 cores | 0.01 cores | 70.3% |
| macOS M4 构建耗时 | 16:31.7 | 6:16.4 | 62.0% |

官方列出的手段：集成 jemalloc 降低碎片；回收 memstore、plan cache、KV cache 的空闲内存；削减冗余后台线程与默认线程栈大小；删除冗余代码与依赖。PL 执行框架从 LLVM JIT 改为 tree-walking 解释器，牺牲部分执行性能换取构建依赖与运行时开销下降。

同一版本的架构变化：embedded mode 从「宿主进程内 in-process 执行」改为「独立后台进程 + MySQL 协议通信」，多语言绑定统一走 `seekdb-bindings`，多个 embedded 应用可共享同一实例。

## 运行时内存占用对比

来自内存基准报告（`reports/2026-09-05-内存占用基准.md`）的实测数据（100k 向量，384 维）：

| 库 | 索引类型 | 内存增量 |
|---|---|---|
| Qdrant | HNSW | +11 MB |
| sqlite-vec | FLAT | +6 MB |
| Milvus | IVF_SQ8 | +144 MB |
| LanceDB | HNSW_PQ | +146 MB |
| Milvus | SCANN | +228 MB |
| ChromaDB | HNSW | +287 MB |
| Milvus | IVF_FLAT | +342 MB |
| SurrealDB | HNSW | +544 MB（RocksDB 主导） |
| LanceDB | IVF_FLAT | +761 MB |

安装包体积和运行时内存没有正相关关系。Qdrant 的 Docker 镜像 270MB，但运行时内存增量只有 11MB（mmap 策略）。LanceDB 的 pip 包 104MB，但运行时内存最高达 761MB（IVF_FLAT）。选型时要区分「下载多大」和「跑起来吃多少内存」。

## 对基准测试的意义

四点可直接用于选型判断：

1. **部署成本差异巨大。** Milvus 需要 4.24 GB Docker 镜像（三个容器），Qdrant 只需 270 MB，嵌入式库（sqlite-vec 0.3MB、ChromaDB 3.6MB）pip 即用。seekdb 的 RPM 54.6 MiB 与一个 Docker 镜像层相当，远低于 Milvus 的 Docker 部署门槛。

2. **它与本基准现有五库不同类。** Milvus、Qdrant 是服务型，LanceDB、sqlite-vec 是嵌入式库。seekdb 即使走 embedded mode，v1.4.0 起也是独立后台进程，属服务型。若要纳入基准，应归入服务型分组与 Milvus / Qdrant 对比，不与 LanceDB 同组。

3. **132.4 MiB binary 与 166.3 MiB 常驻内存仍是纯向量库的数十倍。** 对比 sqlite-vec（pip 0.3MB，运行时 6MB）这类形态，差距来自它要承担 MySQL 协议兼容、事务、ACID。这是路线差异而非实现优劣，但如果场景只是「存 embedding 做相似度检索」，为用不到的能力付这个代价需要明确理由。

4. **安装包体积不预示运行时内存。** LanceDB 的 pip 包（104 MB）比 Qdrant 的 Docker 镜像（270 MB）小，但运行时内存（761 MB vs 11 MB）高一个数量级。这是存储策略的差异：LanceDB 把数据读进内存做列式编码，Qdrant 用 mmap 把数据放磁盘。下载体积和运行内存是两个独立的维度，不能用一个推断另一个。
