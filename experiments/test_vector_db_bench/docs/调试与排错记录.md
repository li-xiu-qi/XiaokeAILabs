## 一、连接与建表

### 1.1 Milvus 的 `create_collection` 传 `index_params` 会被降级成 AUTOINDEX

**现象**：按常规写法在建表时传索引参数，`describe_index` 返回 `index_type: 'AUTOINDEX'`
而不是预期的 `HNSW`。更隐蔽的是 AUTOINDEX 不吃查询侧 ef，实测 ef 从 32 扫到 1024，
召回率和延迟完全不变（恒为 0.228 / 5.0 ms），极易误判成「ef 传不进去」。

**根因**：MilvusClient 的快捷建表路径会自己挂一个默认索引，之后 `create_index`
会撞 `at most one distinct index is allowed per field`。

**解法**：走 `CollectionSchema` 路径建表，不传索引参数；数据写入后再显式 `create_index`。

```python
schema = CollectionSchema(fields=[
    FieldSchema(name="pk", dtype=DataType.INT64, is_primary=True),
    FieldSchema(name="vector", dtype=DataType.FLOAT_VECTOR, dim=dim),
])
c.create_collection(collection_name=n, schema=schema)
# 写入数据之后再建索引
ip = IndexParams()
ip.add_index(field_name="vector", index_type="HNSW", metric_type="L2",
             params={"M": 16, "efConstruction": 200})
c.create_index(collection_name=n, index_params=ip)
```

**证据**：`scripts/index_bench.py` 的 `MilvusAdapter.setup()` 用这个写法，8 种索引全部建成。

### 1.2 Milvus 3.0 的索引是异步构建的

**现象**：`create_index` 返回后立刻查询，召回率异常低（实测从 0.53 崩到 0.23），
且 ef 变化无响应。

**根因**：`create_index` 只是提交了构建任务，返回时索引还没建完，查询打在半成品索引上。

**解法**：轮询 `describe_index` 到就绪。

```python
d = c.describe_index(collection_name=n, index_name="vector")
# 等 d["state"] == "Finished" 且 d["pending_index_rows"] == 0
```

只有 `state` 就绪还不够，`pending_index_rows` 必须归零，否则已 flush 的数据还没进索引。

**证据**：`MilvusAdapter.build_index()` 里带 300 秒超时的轮询，FLAT 大约 3.2 秒、
DISKANN 大约 11.7 秒。

### 1.3 Qdrant 的 Docker 卷挂载被 Git Bash 静默改写

**现象**：容器跑得正常，Qdrant 能写入能查询，但 host 上 `data/qdrant` 目录始终是空的，
存储测量全读到 0。

**根因**：Git Bash 会把 `-v "C:/..."` 里的 Windows 路径改写成 `/c/...`，Docker 解析失败后
**静默降级成匿名卷**，不报错。容器内的 `/qdrant/storage` 确实有数据，只是不在 host 上。

**解法**：加 `MSYS_NO_PATHCONV=1` 禁止路径改写。

```bash
MSYS_NO_PATHCONV=1 docker run -d --name qdrant -p 6333:6333 -p 6334:6334 \
  -v "$(pwd)/data/qdrant:/qdrant/storage" qdrant/qdrant
```

**验证方法**：`docker inspect qdrant --format '{{range .Mounts}}{{.Source}}{{end}}'`，
Source 必须是 Windows 路径（`C:/...`），不是 `/var/lib/docker/volumes/...`。

**证据**：实测 host 创建标记文件、容器内可见；容器内创建标记文件、host 可见。双向互通
说明 bind mount 生效。单 collection 落盘 host 与容器内读数一致（593MB）。

### 1.4 Qdrant 的 `delete_collection` 异步释放空间

**现象**：`delete_collection` 返回后，下一轮的 `empty_bytes` 带上上一轮残留，
实测残留可达 593MB。

**根因**：删除操作返回时落盘空间还没回收，需要数秒。

**解法**：`teardown()` 里轮询目标目录消失，最多等 30 秒。

```python
d = QDRANT_DATA / self.coll
for _ in range(60):
    if not d.exists():
        return
    time.sleep(0.5)
```

**证据**：实测单 collection 593MB，delete 后轮询到目录消失，`du` 归零。

### 1.5 本机 `pkm-hub-runtime/.venv` 的 Python 有 OpenSSL 缺陷

**现象**：任何 `urlopen()` 调用都崩，报 `OPENSSL_Uplink(00007FF9...,08): no OPENSSL_Applink`，
与目标是否可达无关（连 `http://127.0.0.1:9/x` 也崩）。

**根因**：那个环境是 uv 版 CPython 3.12.11，在该机器上有缺陷。

**解法**：用 python.org 版 3.13 自建 venv。本实验的 `.venv` 就是这么来的。

## 二、查询语义

### 2.1 SurrealDB 的 KNN 必须用 `<|K,EF|>` 操作符

**现象**：用常规的 `ORDER BY distance LIMIT k` 写法，召回率为 0。

**根因**：那种写法退化成全表扫描，不走向量索引。

**解法**：用 `<|K,EF|>` 操作符。

```sql
-- 走索引
SELECT pk, emb FROM vec WHERE emb <|10,64|> $q;

-- 退化，召回率为 0
SELECT pk, emb, vector::distance::euclidean(emb, $q) AS d
FROM vec ORDER BY d LIMIT 10;
```

### 2.2 SurrealDB 的事务必须在同一条语句里

**现象**：分两次调用执行 `BEGIN;` 和 `COMMIT;`，报
`Cannot COMMIT without starting a transaction`。

**根因**：每次 `db.query()` 是独立的请求，服务端不保留事务状态。

**解法**：`BEGIN; ... COMMIT;` 用分号拼接成一条语句一次性发送。

## 三、写入性能

### 3.1 SurrealDB 批量写入有 payload 上限

**现象**：批次放大到数千条时被 HTTP 层以 413 Payload Too Large 拒收，WS 大 payload 也会断连。

**根因**：服务端对单请求体大小有限制。

**解法**：400 条一批。这是实测阈值。

**影响**：SurrealDB 的写入吞吐因此只有 976 vec/s 左右，这个数字是受限条件下的下限，
不是引擎上限。跨库对比写入吞吐时要考虑这一点。

## 四、存储测量

这一节的四个坑都是「测出来的数字是错的」而非「跑不起来」，更隐蔽。

### 4.1 Milvus 不能用 `collection_id` 过滤 minio 对象

**现象**：按 `describe_collection` 返回的 `collection_id` 去拼对象路径，
只能统计到 `insert_log`，`index_files` 完全统计不到。结果是所有索引的存储读数趋同
（都是原始向量那 17.4MB 左右），FLAT、IVF_PQ、HNSW、DISKANN 看不出差别。

**根因**：Milvus 3.0 的对象路径是 `files/<kind>/<id>/1/<seg>/<field>/<idx>/<uuid>/part.N`，
第一段 `<id>` 与 `describe_collection` 的 `collection_id` 不是同一个值（实测不匹配）。
它是内部的分片或段标识，没有公开 API 可以直接查。

**解法**：快照差分。跑分前拍一张 `{(kind, top_id): bytes}` 基线，后续每次 `storage()`
只统计相对这张基线新增的 `(kind, id)` 对象。

```python
def _snapshot(self):
    agg = {}
    for kind in ("insert_log", "stats_log", "index_files"):
        kd = MILVUS_MINIO / kind
        for sub in kd.iterdir():
            if sub.is_dir():
                t = dir_bytes(sub)
                if t:
                    agg[(kind, sub.name)] = t
    return agg

def storage(self):
    agg = self._snapshot()
    base = getattr(self, "_base_agg", {})
    return sum(v for k, v in agg.items() if k not in base)
```

**证据**：修正后各索引的存储读数正常分化，DISKANN +44.8MB > HNSW +36.3MB >
IVF_PQ +18.1MB > FLAT +17.3MB。

### 4.2 Milvus 的 `drop_collection` 不回收 minio 空间

**现象**：两轮连续跑（建表、插入、建索引、drop），minio bucket 从 279MB 涨到 387MB 不回落。

**根因**：对象存储的删除是标记删除，实际空间由后台 GC 回收，不像本地文件系统那样立即释放。

**影响**：不能直接 `du` 整个 bucket 当基线，否则每轮基线累积，增量测量全部失真。
这也是 4.1 必须用快照差分的原因之一。

### 4.3 SurrealDB 无法在 adapter 层隔离存储路径

**现象**：想在每个索引规格之间用独立的 rocksdb 目录，在 adapter 里 `mkdir` 一个路径，
然后连接共享的 SurrealDB 实例，结果那个目录始终是空的。

**根因**：rocksdb 路径是**服务启动参数**决定的（`surreal start ... rocksdb:<path>`），
连接时改不了。而且同实例内 `drop table` 也不回收空间。

**解法**：每个规格起一个独立的 SurrealDB 进程，独立端口加独立数据目录。

```python
self.proc = subprocess.Popen(
    [str(SURREAL_BIN), "start", "--user", "root", "--pass", "root",
     "--bind", "127.0.0.1:%d" % self.port,
     "rocksdb:%s" % self.dbpath],
    stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL)
```

**代价**：SurrealDB 只有两种索引规格，起两个进程的成本可接受。规格多的库不能用这招。

### 4.4 Qdrant 的空 collection 预分配 352.6MB

**现象**：`create_collection` 之后、写入任何数据之前，落盘就已经有 352.6MB。
空 collection、零向量、零索引。

**根因**：Qdrant 的 HNSW 图结构在建表时按预估规模预分配了内存映射文件。

**影响**：跨库对比存储不能用总量比值。Qdrant 的总倍数因此高达 52.9x，失真。
要用「索引增量」（建索引后减写入后），Qdrant 的 HNSW 索引增量 +296.0MB 与 Milvus 的
+19.0MB 才有可比性。

**另一个发现**：Qdrant 的 `FLAT`（`m=0` 关闭 HNSW）预分配也是 352.6MB，与 HNSW 完全相同。
说明这笔开销来自存储层预分配，不是图结构本身，`m=0` 并不省。

### 4.5 文本存储用 A/B 单独测，正文源是一次数据抢救

**需求**：报告要把存储拆成「向量 / 文本 / 索引」三段。主表的「数据增量」只含向量加 pk，
不含正文。正文要单独测。

**方法**（`scripts/index_bench.py --text-storage`）：同一索引下跑两轮，一轮只写向量加 pk，
一轮再加正文，两轮落盘字节差就是文本增量。向量加 pk 那轮的读数与主表数据增量吻合
（Qdrant 268.6MB、LanceDB 17.4MB、sqlite-vec 19.2MB 全部一致）即证明 A/B 干净、没有串轮。

**正文来源是一次数据抢救**：`data/20news.pkl.gz` 一直以为损坏，`pickle.load` 报
`unpickling stack underflow`。实际它没坏，是被误命名的 20news-bydate tar.gz，md5 与
重新下载的 `20news-bydate.tar.gz` 完全一致（`d6e9e45...`），`file` 显示是 gzip 压缩的 tar。
解包后用 `gen_emb.py` 的同一套预处理（去 header、按 `\n\n` 切正文、空白折叠、截断 1200 字符、
正文不足 30 字跳过）跑出 11,293 条，与 `train_emb` 行数和名字逐条对齐，落盘为
`data/20news_texts.npz`（9.6MB UTF-8）。教训：`.pkl.gz` 扩展名不可信，先 `file` 看真实类型。

### 4.6 Qdrant 的文本增量测出来是 0，这是预分配掩盖不是文本免费

**现象**：`--text-storage` 对 Qdrant 测出文本增量 0.0MB（向量加 pk 与加文本都是 268.6MB）。
其余四库都有正增长（Milvus 3.4MB、SurrealDB 14.0MB、LanceDB 6.0MB、sqlite-vec 11.5MB）。

**验证不是没存**：把文本读回，逐字命中；灌 90MB 文本进去，落盘依然不变、读回仍正常。
文本确实存了，只是文件大小不增长。

**根因**：Qdrant 的 payload 存在固定大小的预分配页里（`payload_storage/page_0.dat`，
实测单页 33.55MB）。11,293 条时 payload 区预分配 268MB，文本写进去落在预分配余量中。
`dir_bytes` 量的是文件已分配大小，不是页内已用字节，所以看不到文本增长。这与 4.4 的
空 collection 预分配同源，都是 Qdrant 按点数预分配、文件大小不随实际用量线性变化。

**影响与处置**：Qdrant 的文本成本真实值大于 0，但用文件大小差分测不出。跨库比文本成本时
Qdrant 这行只能当「下界、实际更高」，不能当 0 或「文本免费」。要精确值得读页内已用字节，
本次没做。报告第三节已按此口径标注。

## 五、被测对象的能力边界

这几条不是我们的 bug，是实测推翻了文档或网上教程的说法。写在这里避免后人重复踩。

### 5.1 SurrealDB 3.2.4 不支持 MTREE 向量索引

**现象**：网上多篇文档（含官方博客）写 SurrealDB 支持 `MTREE` 向量索引，
实测 3.2.4 三种写法全部解析失败：

```
DEFINE INDEX idx ON probe FIELDS emb MTREE DIMENSION 4 DIST EUCLIDEAN;
→ Parse error: Unexpected token `an identifier`, expected Eof
```

**实测支持**：只有 `HNSW`，参数是 `EFC`（构建宽度）和 `M`（连接数）。

### 5.2 LanceDB 的 IVF_FLAT 不能用 `num_sub_vectors=0` 构造

**现象**：按直觉设 `num_sub_vectors=0` 想关掉量化走纯倒排，报
`num_sub_vectors must divide vector dimension 128, but got 0`。

**解法**：走新统一 API 的配置对象。

```python
from lancedb.index import IvfFlat
tbl.create_index("vector", config=IvfFlat())
```

旧 API（`num_partitions` + `num_sub_vectors`）只能构造 IVF_PQ。

### 5.3 Milvus Lite 不支持 Windows

**矛盾**：网上有教程写「Windows/Mac/Linux/Jupyter/Colab 全部支持」，
[官方文档](https://milvus.io/docs/zh/milvus_lite.md)列的支持环境只有
Ubuntu 20.04 及以上（x86_64 和 arm64）和 macOS 11.0 及以上。

**结论**：以官方文档为准，Windows 不在支持列表。Windows 上要用 Milvus 只能走 Docker 的
Standalone。另外 Milvus Lite 只有 FLAT 暴力索引，不支持 HNSW、IVF 等加速索引。

### 5.4 Milvus 在本机（无 GPU）上 GPU 系列索引不可用

`GPU_IVF_FLAT` 和 `GPU_CAGRA` 报 `invalid index type`，属预期。有 GPU 的机器才能用。

### 5.5 sqlite-vec 有 partition key，能实际提速但不是 ANN

**容易被忽略的机制**：`vec0` 虚拟表支持分区键，查询时带等值约束可以裁掉大部分扫描。

```sql
CREATE VIRTUAL TABLE docs USING vec0(
  id INTEGER PRIMARY KEY,
  cat INTEGER PARTITION KEY,
  embedding FLOAT[384]
);

-- 只扫 cat = 0 那个分区
SELECT id, distance FROM docs
WHERE embedding MATCH ? AND k = 10 AND cat = 0;
```

**实测**（11,293 条 384 维，v0.1.9）：

| 查询方式 | p50 |
|---|---:|
| 无分区键全表扫描 | 34.27ms |
| 建了分区键但查询不带约束 | 59.58ms |
| 带 `cat = 0` 约束（1/20 数据） | 2.39ms |

分区约束能快 14 倍。但要注意两点。

**它不是 ANN。** 分区查询只在该分区内找 top10，不保证是全局 top10。实测全表真值 top10 与
`cat = 0` 分区内返回结果只有 2/10 命中。这是精确的分区过滤，不是近似最近邻加速，
不碰精度问题，也就不是 ANN 定义下那种「牺牲可接受精度换速度」的索引。

**分区表本身有开销。** 上表第二行，建了分区键但查询不带约束时是 59.58ms，比不带分区的
34.27ms 还慢。建了分区表却不用约束，会比不建更慢。

### 5.6 sqlite-vec 确实没有 ANN 索引

多个独立来源一致确认：`vec0` 只有 brute-force KNN，复杂度 O(N×d)，
没有 IVF、HNSW 之类的近似索引。官方 README 也只描述 KNN 查询，未提任何 ANN 结构。

所以「sqlite-vec 没有 ANN 索引」这个结论成立。但完整表述应该加上 5.5 的 partition key：
没有 ANN 索引，只有暴力扫描，但分区键约束能裁扫描量。
