# 向量搜索引擎底层实现

本笔记记录本实验六个库**各自用什么做向量搜索**：是封装成熟 C++ 库（FAISS/hnswlib）、还是用系统语言自研重写、还是根本没有 ANN。它回答「同名的 HNSW/IVF 在不同库里是不是一回事」，是背景概念，不是性能结论（数字看 `reports/2026-09-04-真实数据-索引矩阵基准.md`）。坑和根因看 `调试与排错记录.md`。

**一句话**：六个库的向量检索分三类。封装成熟 C++ 库的是 Milvus，它的 Knowhere 引擎内嵌 FAISS、hnswlib、Annoy。用系统语言自研重写的是 Qdrant（纯 Rust）、LanceDB（Lance 列式格式上的 Rust 实现）、SurrealDB 的 HNSW（自研 Rust）和 ChromaDB（自研）。sqlite-vec 要分版本看：基准用的 0.1.9 只有暴力扫描，当前 0.1.10 已加入自研 C 的 DiskANN 和 IVF。

**本篇结论全部从源码核实**，不是二手文档。六个仓库已 clone 到参考库 `_reference/projects/infra-and-backend/`（milvus、qdrant、surrealdb、lancedb、lance、sqlite-vec），核查方式是读依赖清单（Cargo.toml / CMake）和向量索引源码路径，并拉取基准对应版本的 tag 比对。核实日期 2026-09-05。

## 总览

| 库 | 基准版本 | 向量引擎 | 自研 / 封装 | 核实方式 |
|---|---|---|---|---|
| Milvus | v3.0.0 | Knowhere，内嵌 FAISS / hnswlib / Annoy | 封装成熟 C++ 库 | 官方文档 + 源码 `knowhere/thirdparty/faiss/` |
| Qdrant | 1.19.0 | 自研纯 Rust HNSW（Filterable HNSW） | 自研重写 | 33 个 Cargo.toml 无任何外部 ANN 库 |
| SurrealDB | 3.2.4 | HNSW 走自研 `idx/trees/hnsw/` | 自研（HNSW）；另有 DiskANN 走微软 crate（未测） | 源码 `index.rs` 分派 + Cargo.toml |
| LanceDB | 0.38.0 | `lance-index` crate，Rust 自研 | 自研，无外部 ANN 库 | `lance-index/Cargo.toml` 无 faiss/hnswlib |
| ChromaDB | 1.5.9 | 自研 HNSW | 自研重写 | ChromaDB 源码为 Rust + Python，向量索引在 Rust 侧自研 |
| sqlite-vec | 0.1.9 | 纯 C 暴力扫描，无 ANN | 自研 C，无外部依赖 | v0.1.9 tag 无 diskann/ivf 文件 |

## Milvus：Knowhere 内嵌 FAISS / hnswlib

Milvus 的核心向量执行引擎叫 **Knowhere**，以 vendored 形式放在 `internal/core/thirdparty/knowhere`。它把多个成熟的向量检索库集成进来，官方文档明确列出 **FAISS、hnswlib、Annoy**，源码里也能看到 `knowhere/thirdparty/faiss/` 的路径引用。Knowhere 还做异构计算调度（控制索引构建和查询跑在 CPU 还是 GPU），并在 FAISS 代码基础上按 SSE/AVX2/AVX512 做多版本编译、运行时自动选。本次基准里 Milvus 还跑通了 DISKANN（微软研究院）和 SCANN（谷歌），这两个是 Knowhere 核心三库之外单独集成的索引。Milvus 索引类型最全（8 种），很大程度是站在 FAISS 等库肩膀上。（来源：Milvus 官方 Knowhere 文档 + 克隆源码，2026-09-05 核实）

## Qdrant：纯 Rust 自研，没有外部 ANN 库

Qdrant 完全用 Rust 写，向量索引是**自己实现的**。核对了它全部 33 个 Cargo.toml，没有任何 faiss、hnswlib、usearch、annoy 之类的外部 ANN 库依赖（命中的 hnsw_build_graph、hnsw_search_graph 等都是 Qdrant 自己的模块名或 benchmark 名）。它的 HNSW 是带原生过滤的 Filterable HNSW，实现在 `lib/segment`，把向量索引、元数据过滤、量化压缩、分布式一致性做成一个内聚的存储引擎。（来源：克隆源码 Cargo.toml + lib/segment，2026-09-05 核实）

## SurrealDB：HNSW 是自研，另有单独的 DiskANN 走微软 crate

SurrealDB 有两个**独立的索引类型**，别混淆。源码 `core/src/idx/index.rs` 里的分派写得很清楚：`Index::Hnsw` 走 `idx/trees/hnsw/`（自研 Rust 实现），`Index::DiskAnn` 走 `idx/trees/diskann/`（微软的 `diskann-vector` crate，版本锁 `=0.54.0`，仅 64-bit 非 WASM，由 build.rs 设 `diskann` cfg）。

本次基准用的是 `DEFINE INDEX ... HNSW`，走的是**自研 HNSW**（`idx/trees/hnsw/`），不是 DiskANN。DiskANN 是 SurrealDB 在 64-bit 上额外提供的另一个索引类型，本次没测。这一点在 3.2.4 tag 和当前 main 上都成立。（来源：克隆源码 v3.2.4 tag 的 Cargo.toml + index.rs，2026-09-05 核实）

## LanceDB：lance 列式格式上的 Rust 自研索引

LanceDB 的 Python 包是外壳，核心是 Rust 的 `lance` crate，向量索引在 `lance-index` 子 crate 里（IVF_PQ、IVF_SQ、HNSW、IVF_HNSW_SQ 都是 Lance 原生配置对象）。核对了 `lance-index/Cargo.toml`，没有 faiss、hnswlib、usearch 之类的外部 ANN 库，是自研实现，和 Lance 列式存储长在一起。列式存储让向量按段紧凑排列、距离计算走 SIMD，这是它写入吞吐和存储效率高的底层原因。（来源：克隆 lance 源码 rust/lance-index/Cargo.toml，2026-09-05 核实）

## ChromaDB：自研 HNSW

ChromaDB 的向量索引是自研 HNSW，源码为 Rust + Python 混合架构，向量索引在 Rust 侧实现。不依赖 FAISS、hnswlib 等外部 ANN 库。

不支持 FLAT 暴力搜索作为独立索引类型，也不支持 IVF 系列。HNSW 参数通过 collection metadata 配置（`hnsw:M`、`hnsw:construction_ef`、`hnsw:search_ef`），但查询时不接受运行时 ef 参数，只能测固定 ef 值。

## sqlite-vec：0.1.9 无 ANN，当前版本已加 DiskANN + IVF

这一条**必须分版本**，否则会说错。

基准测的是 **0.1.9**，这个版本**确实只有暴力全表扫描，没有 ANN**。拉了 v0.1.9 tag 核对，文件列表里没有 diskann、ivf、rescore、kmeans 任何文件，纯 brute-force KNN。本次基准「sqlite-vec ef 无效、延迟恒定、召回恒 1.000」的结论对这个版本成立，作者当时也确认不引外部向量库、纯 C 自研。

但**当前 main（0.1.10-alpha）已经加入了 ANN**，新增了 `sqlite-vec-diskann.c`（DiskANN）、`sqlite-vec-ivf.c` 和 `sqlite-vec-ivf-kmeans.c`（IVF）、`sqlite-vec-rescore.c`（精排），仍是自研 C 实现、没有外部向量库依赖（源码里出现的 hnswlib/faiss 字样是注释里的代码出处引用，不是链接依赖）。所以「sqlite-vec 没有 ANN」只对 0.1.9 成立，对当前版本不成立。（来源：克隆源码 v0.1.9 tag 与 main 文件比对，2026-09-05 核实）

## 对读基准的意义

同名索引跨库不是同一实现，理解这层能避免误读：

Milvus 的 HNSW 走 hnswlib，Qdrant 的 HNSW 是自研，SurrealDB 的 HNSW 也是自研，三套独立实现，参数和图构建过程都不同，主报告里跨库召回/延迟差异混了实现差异，不纯是算法或参数差异。LanceDB 连存储格式都是自研列式，io 路径和另四个都不同。sqlite-vec 在基准版本上压根不在 ANN 赛道。
