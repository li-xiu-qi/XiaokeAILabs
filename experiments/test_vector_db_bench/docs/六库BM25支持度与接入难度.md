# 六库 BM25 支持度与接入难度

## 这个文档是干嘛的

回答两个问题：本次基准的六个向量库**能不能做 BM25 全文检索**，以及**接进来要花多大力气**。BM25 是混合检索（向量 + 关键词）的必经之路，纯向量检索在精确术语、版本号、专有名词、长尾词上是盲区，这一节给出选型时的能力底牌。

分词器怎么实现的、中文能不能用，不在本文档范围，见 [六库分词器实现与中文支持.md](六库分词器实现与中文支持.md)。

证据分两级，文档里明确标注：**实测**（本机跑通并返回 BM25 打分结果）与**源码级**（读了实现代码但本机跑不通，原因写明）。两者不混谈。

## 总览

| 库 | 支持等级 | 实现路径 | 证据 |
|---|---|---|---|
| Milvus 3.0.0 | **NATIVE** | `BM25BuiltInFunction` + `SPARSE_FLOAT_VECTOR` + `SPARSE_INVERTED_INDEX` | 实测 |
| LanceDB 0.38.0 | **NATIVE** | native FTS（tantivy 已在 0.38 移除）+ `query_type="fts"` | 实测 |
| SurrealDB 3.2.4 | **NATIVE** | `DEFINE ANALYZER` + `DEFINE INDEX ... FULLTEXT BM25(k1,b)` + `search::score()` | 实测 |
| ChromaDB 1.5.9 | **NATIVE** | `ChromaBm25EmbeddingFunction` / `Bm25EmbeddingFunction`（`SparseEmbeddingFunction`） | 源码级 |
| Qdrant 1.19.0 | **NATIVE** | `Document(model="qdrant-bm25", options=Bm25Config)` | 源码级 |
| sqlite-vec 0.1.9 | **NONE** | 无任何 FTS 接口，需自己在 `vec0` 表旁建 FTS5 表再 JOIN | 实测 |

结论与直觉相反的地方有两处，都值得单独说：**ChromaDB 原生支持 BM25**（以 sparse embedding function 形态提供，不是只有布尔过滤），**Qdrant 也有原生 BM25**（1.19 起以 local inference model 形态提供，`lib/bm25` crate 297 行）。

## 实测验证：BM25 抓得到向量检索不到的东西

探针用 8 条文档、查询词 `fox`。其中 doc 6 是「The dog barked loudly at the midnight fox」，它与查询在语义上无关（讲狗吠，不是讲狐狸），纯向量检索基本不可能排进前 10。BM25 命中了它，这是能力的直接证明。

| 库 | 返回 top3（doc_id, 分数） | 是否命中 doc 6 |
|---|---|---|
| Milvus | (6, 1.229), (0, 1.166) | 是，排第 1 |
| LanceDB | (6, 1.319), (0, 1.223) | 是，排第 1 |
| SurrealDB | 返回 BM25 打分排序结果 | 是 |

三个库给出一致结论：doc 6 都排第 1，doc 0（「The quick brown fox jumps over the lazy dog」）排第 2。排序方向正确。

脚本：`scripts/probe_bm25.py`，数据：`results/bm25probe-20260906-115030.json`。

## 逐库实现细节

### Milvus：最完整，但有一个必踩的坑

 schema 里加 `SPARSE_FLOAT_VECTOR` 字段，挂一个 `FunctionType.BM25` 的内置函数，输入是带 `enable_analyzer=True` 的 `VARCHAR` 字段。插入时只给原始文本，BM25 稀疏向量由服务端生成。

坑在这里：**sparse 字段必须单独建 `SPARSE_INVERTED_INDEX` 索引，然后才能 `load_collection`**。顺序反了会报 `index not found`。用 `IndexParams().add_index(field_name="sparse", index_type="SPARSE_INVERTED_INDEX", metric_type="BM25")`。

检索时 `search(anns_field="sparse", data=["查询文本"])`，返回的 `distance` 即 BM25 分。

### LanceDB：API 最简单，但 tantivy 已死

`tbl.create_fts_index("text")` 建索引，`tbl.search(q, query_type="fts")` 查询，`_score` 字段即 BM25 分。不需要任何额外依赖。

注意版本迁移：**0.38 起 tantivy 实现已被移除**，传 `use_tantivy=True` 会直接报错。所有网上教程（包括 LanceDB 官方文档的 Tantivy 章节）都已过期，要用 native FTS。

原生 FTS 的 tokenizer 可选 `simple` / `raw` / `whitespace` / `ngram` / `icu` / `icu/split`，支持 `language`、`stem`、`remove_stop_words`、`ascii_folding` 等。中文要用 `icu/split`。

### SurrealDB：BM25 是真的，但 analyzer 要自己搭

源码 `surrealdb/core/src/idx/ft/fulltext.rs` 里有 `Scorer::new` + `Bm25Params{k1, b}`，`Scoring` 枚举有 `Bm` 变体，`k1`/`b` 可在建索引时指定（如 `BM25(1.2, 0.75)`），是真 BM25 不是近似。

代价是**没有内置 analyzer**，必须先 `DEFINE ANALYZER`。而 analyzer 的能力很弱，`Tokenizer` 枚举只有四个值：`Blank` / `Camel` / `Class` / `Punct`；`Filter` 有 `Lowercase` / `Snowball` / `Ngram` / `EdgeNgram` / `Ascii` / `Uppercase` / `Mapper`。没有停用词表配置项，没有中文分词。

查询用 `WHERE body @1@ 'fox'` 配合 `search::score(1)` 取分。

### ChromaDB：原生 BM25，以 sparse EF 形态存在

`chromadb.utils.embedding_functions` 下有两个实现：

`ChromaBm25EmbeddingFunction(k=1.2, b=0.75, avg_doc_length=256.0, token_max_length=40, stopwords=None, include_tokens=False)`，参数就是标准 BM25 三件套。

`Bm25EmbeddingFunction` 更完整，多出 `language`、`disable_stemmer`、`token_max_length`、`task`（document/query）、`query_config`。

两者都继承 `SparseEmbeddingFunction`，输出稀疏向量，走 Chroma 现有的稀疏向量检索路径。

本机实测受阻，原因要写清楚：这两个 EF 内部走 `fastembed.sparse.bm25.Bm25`，需要 `snowballstemmer` 且会触发 onnx 模型下载。当前 PyPI 默认源与清华镜像都取不到 `fastembed` 轮子，`snowballstemmer` 同样装不上。所以判定为源码级 NATIVE，不是没支持。

### Qdrant：1.19 新增，crate 已就位但未接入主路径

`qdrant_client.models` 里有 `Bm25Config` 和 `Document`。`Bm25Config` 的字段完整：`k`(1.2) / `b`(0.75) / `avg_len`(256) / `tokenizer` / `language` / `lowercase` / `ascii_folding` / `stopwords` / `stemmer` / `min_token_len`，与 Milvus、LanceDB 的同级能力对齐。

源码侧 `qdrant/lib/bm25/src/lib.rs`（297 行）有 `Bm25Params{k1, b, avg_doc_len}`、默认值 `DEFAULT_K1=1.2` / `DEFAULT_B=0.75` / `DEFAULT_AVG_DOC_LEN=256.0`，以及参数校验（`k1` 必须有限非负，`b` 必须在 `[0,1]`），还带一个 `basic_tokenizer`。这是完整实现不是 stub。

但有一个事实要指出：在 clone 的 v1.19.1 里，`bm25` crate 虽然注册在 workspace members 中，**没有任何其他 crate 依赖它**（`grep -rln` 只命中根 `Cargo.toml`）。它是通过 `lib/api/src/rest/schema.rs` 以 local inference model 的形式暴露的，属新并入、尚未完全接入 segment 主路径的功能。

本机实测同样受阻：客户端构造 `Document(model="qdrant-bm25")` 时要求 `fastembed`（本地推理）或 `cloud_inference=True`（需 Qdrant Cloud key），两者在本环境都不可得。故判定为源码级 NATIVE。

### sqlite-vec：确实没有，宿主 SQLite 可以补

sqlite-vec 不提供任何 FTS 或 BM25 接口，`vec0` 虚拟表只做向量。这是本次实测确认的 NONE。

但宿主 SQLite 自己带 FTS5，`bm25()` 函数可用：

```sql
CREATE VIRTUAL TABLE fts USING fts5(text);
SELECT rowid, bm25(fts) FROM fts WHERE fts MATCH 'fox' ORDER BY bm25(fts);
```

实测这条路是通的。代价是 BM25 分数和向量距离是两套量纲，融合时要自己归一化，而且两次查询的结果要自己做 JOIN 或 RRF。能用，但属于自己搭。

## 接入难度分三层

**第一层：几行代码搞定。** Milvus、LanceDB、ChromaDB、Qdrant 都是 API 调用级别，建索引加一个查询参数即可。其中 LanceDB 最简单（一个 `create_fts_index`），Milvus 最啰嗦（要建 sparse 索引再 load，顺序错了报错）。

**第二层：要理解 analyzer 机制。** SurrealDB 必须先 `DEFINE ANALYZER`，而且只有 4 种 tokenizer、没有停用词表配置、没有中文分词。英语场景够用，中文场景要自己写 `Mapper` filter。

**第三层：自己搭流水线。** sqlite-vec 要在 `vec0` 表旁建 FTS5 表，写两套查询，自己做分数归一化和结果融合。工作量约为第一层的十倍，好处是全程可控、无额外依赖。

## 混合检索实验：详见独立报告

混合检索（向量 + BM25，RRF 融合）的完整实测与两个导致结论错误的缺陷分析已拆到独立报告：
[2026-09-06-混合检索BM25对比.md](../reports/2026-09-06-混合检索BM25对比.md)。

这里只留与本文档（BM25 支持度）直接相关的三点：

**本轮数据作废过一轮。** 最早跑出的 Milvus 0.807/0.944/0.493/0.775 有两个缺陷：查询文本取的是 `test_texts[:40]`，而查询向量是分层随机采样，40 条里只有 4 条真正对应，其余 36 条的 BM25 那一路搜的是无关文本；`min_overlap=10` 从未真正校准，实际 GT 覆盖 49.3% 的语料，`bm25_hit=0.997` 是分母塌掉后的必然。修完重跑的有效数据在报告里。

**`bm25_truth` 曾有名不副实的文档字符串。** 注释写着「已去停用词」，实现里只有长度过滤，没有任何停用词表。补上停用词后重叠计数整体下移，校准区间必须跟着下移，这个连带关系容易漏。

**SurrealDB 的 BM25 打分为真，但在 11293 条规模上取不回结果。** 单词查询部分命中且分值合理，`article`(df=173)、`1993`(df=23) 返回 0 条，所有多词查询返回 0 条，已排除空匹配退化和异步构建。行为未定位，所以它没进混合检索对比表。这不影响本文档对它的 NATIVE 判定，判定依据是单文档探针。

## 对基准测试的意义

三点可直接用于选型：

**BM25 已不是稀缺能力。** 六库里五个原生支持，只有 sqlite-vec 没有。所以「这个库能不能做混合检索」不该作为选型的否决项，该问的是「它的 BM25 实现够不够用」。

**实现质量差异比有无更重要。** SurrealDB 有真 BM25 但 analyzer 只有 4 种 tokenizer，中文场景要先自己写 filter；Milvus 的 BM25 与向量检索共用同一套稀疏向量 ANN 路径，可以自然进入多路召回和 rerank 体系；LanceDB 的 FTS 与向量检索是两条独立路径，融合要自己做。

**Qdrant 和 ChromaDB 的 BM25 值得跟进但暂不可依赖。** Qdrant 的 `bm25` crate 还没被 segment 依赖，属新并入功能；ChromaDB 的 BM25 EF 走 fastembed，离线环境装不上。两者在本环境都无法实测，结论来自源码。要用的话先在自己的环境验证一遍。
