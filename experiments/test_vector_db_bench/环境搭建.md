**测试日期**：2026-09-02 至 2026-09-04

## 环境搭建

五个库分三种部署形态。SurrealDB 有 Windows 原生二进制，Milvus 和 Qdrant 走 Docker，
LanceDB 和 sqlite-vec 是嵌入式库不需要起服务。

### 当前状态

实验目录里 `.venv` 需要时重建（`pip install -r requirements.txt`）。`bin/surreal.exe` 是
SurrealDB 的 Windows 原生二进制（v3.2.4），未入库、按需从 GitHub Releases 下。
数据（`data/20news_emb.npz`、`data/20news_texts.npz`、`data/20news.pkl.gz`）和脚本完好。
重建方式见下面各节。

### Milvus

Windows 上无原生二进制，走 Docker：

```bash
curl -L -o config/milvus-standalone-compose.yml \
  https://raw.githubusercontent.com/milvus-io/milvus/master/deployments/docker/standalone/docker-compose.yml
docker compose -f config/milvus-standalone-compose.yml up -d
```

三个容器：`milvus-standalone`（19530）、`milvus-etcd`（2379）、`milvus-minio`（9000/9001）。

Milvus Lite（嵌入式 Python 库）**不支持 Windows**，官方文档列的支持环境只有
Ubuntu 20.04 及以上和 macOS 11.0 及以上。网上教程写的「Windows/Mac/Linux 全部支持」
与官方矛盾，以官方为准。Lite 还只有 FLAT 暴力索引。所以 Windows 上跑 Milvus 只能走
Docker 的 Standalone。

### Qdrant

Windows 上有原生二进制，本实验走 Docker（镜像 270MB）：

```bash
MSYS_NO_PATHCONV=1 docker run -d --name qdrant -p 6333:6333 -p 6334:6334 \
  -v "$(pwd)/data/qdrant:/qdrant/storage" qdrant/qdrant:latest
```

`MSYS_NO_PATHCONV=1` 不能省，原因见排错记录 1.3（Git Bash 改写卷路径导致 bind mount
静默失效）。

原生二进制路线是从 GitHub Releases 下 `qdrant-x86_64-pc-windows-msvc.zip`，解压出
`qdrant.exe` 加一份 `config.yaml`，不依赖 Docker。

### SurrealDB

Windows 原生二进制：

```bash
curl -L -o bin/surreal.exe \
  https://github.com/surrealdb/surrealdb/releases/download/v3.2.4/surreal-v3.2.4.windows-amd64.exe
./bin/surreal.exe start --user root --pass root --bind 127.0.0.1:8000 "rocksdb:data/surreal.db"
```

`index_bench.py` 跑 SurrealDB 时会自己起独立进程（每轮一个端口加一个数据目录，原因见
排错记录 4.3），不需要手动起这个共享实例。手动起的是给 `multi_bench.py` 之类的旧脚本用的。

### LanceDB、ChromaDB 和 sqlite-vec

嵌入式库，不需要起服务。LanceDB 的数据是本地目录里的 Lance 列式文件，ChromaDB 的数据
是本地目录里的 sqlite 和二进制文件，sqlite-vec 的数据是单个 `.db` 文件，都由 adapter
在每轮自动创建独立路径。

### Python 环境

```bash
python -m venv .venv
./.venv/Scripts/python.exe -m pip install -r requirements.txt
```

依赖锁定在 `requirements.txt`，八个包：`surrealdb`、`pymilvus`、`qdrant-client`、
`lancedb`、`chromadb`、`sqlite-vec`、`numpy`、`pandas`。

本机 `py` 启动器在 Git Bash 里不可用，直接用 Python 安装路径下的 `python.exe`。

> **不要用本机全局环境里那个 uv 版 CPython 3.12 的 Python。** 那个 uv 版 CPython 3.12 的 OpenSSL 在本机
> 有缺陷，任何 `urlopen()` 调用都崩（排错记录 1.5）。

### 服务自检

```bash
netstat -ano | grep -E ":(19530|6333|8000) " | grep LISTENING
```

三个端口都该在监听。Milvus 的就绪检查可以多等一会，它启动比另两个慢。

## 测试设计

主脚本是 `scripts/index_bench.py`，按 (库 × 索引类型) 两重循环跑。每个 (库, 索引)
组合独立一轮，drop 重建，避免索引间互相污染。

比早期的 `multi_bench.py` 多测三块：索引类型维度、索引构建时间、存储分段记账。

### 数据与召回基准

- 数据：20 Newsgroups，all-MiniLM-L6-v2，384 维 float32；train 11,293 篇入库，
  test 分层采样 40 条查询（20 类 × 2）
- 召回率基准：暴力精确 top-k（用 `|a-b|^2 = |a|^2 + |b|^2 - 2ab` 展开式，
  避免开 7.7 GB 中间张量）
- ef 扫描：64 / 128 / 256，每档 3 轮，第 1 轮第 1 条作冷启动单独记录
- 查询集延迟取后 2 轮的 p50 / p95，召回率取全部轮次均值
- 合成数据模式（`--synthetic`）：30,000 条 768 维均匀随机向量，50 条查询。
  这个模式只用于验证脚本能跑通，不做性能结论，随机向量无聚类结构会让召回全部失真

### 索引能力矩阵

各库实际支持的索引由 `scripts/probe_index.py` 逐个试建确认，不照抄文档。完整矩阵和三处
推翻文档的实测（SurrealDB 的 MTREE、LanceDB 的 IVF_FLAT 构造方式、Milvus Lite 的
Windows 支持）见排错记录第五节。

### 存储测量口径

四个库的落盘位置和取法不同，其中三个有坑，不避开就会测出错误数字：

- **Milvus** 用 minio 对象存储，`drop_collection` 不回收空间，且对象路径的 id 与
  `collection_id` 不匹配。用跑分前后的快照差分，只统计本轮新增对象。见排错记录 4.1、4.2
- **Qdrant** 的空 collection 就预分配 352.6MB，跨库对比不能用总量比值，要用索引增量。
  它的 payload 还存在固定大小的预分配页里（单页 33.55MB），文本增量落在预分配余量中、
  文件大小不增长，`dir_bytes` 看不到，文本成本被系统性低估。见排错记录 4.4、4.6
- **SurrealDB** 每轮起独立进程加独立数据目录。见排错记录 4.3
- **LanceDB、sqlite-vec** 是本地文件或目录，直接 `du`

主表的「数据增量」只含向量加 pk。正文文本单列，用 `--text-storage` 做 A/B：同索引下
一轮只写向量加 pk、一轮再加正文，两轮落盘差即文本增量。正文来源是 `data/20news_texts.npz`
（从 `data/20news.pkl.gz` 解出的 20news-bydate 正文，与 `train_emb` 逐条对齐，9.6MB UTF-8）。
向量加 pk 那轮的读数与主表数据增量吻合即说明 A/B 干净。完整三段拆分见报告第三节。

### 两处必须单列标注的差异

LanceDB 的 IVF_PQ 配 `refine_factor` 是粗排加精排，与其余库的纯 HNSW 不同构，
延迟对比要单列。sqlite-vec 无 ANN 索引但有 partition key 机制（排错记录 5.5），
ef 参数无效而分区约束有效。两处的完整数据见报告第五节。

## 复现

```bash
# 1. 起服务（Milvus / Qdrant 走 Docker）
docker compose -f config/milvus-standalone-compose.yml up -d
MSYS_NO_PATHCONV=1 docker run -d --name qdrant -p 6333:6333 -p 6334:6334 \
  -v "$(pwd)/data/qdrant:/qdrant/storage" qdrant/qdrant:latest

# 2. 索引能力探测（确认各库支持哪些索引，约 3 分钟）
./.venv/Scripts/python.exe scripts/probe_index.py

# 3. 索引矩阵基准（真实数据，11293 x 384，20 组，约 12 分钟）
./.venv/Scripts/python.exe scripts/index_bench.py

# 3b. 文本存储成本（每库 A/B：向量+pk vs 向量+pk+文本，只报存储，约 5 分钟）
./.venv/Scripts/python.exe scripts/index_bench.py --text-storage

# 只跑指定库 / 指定索引
./.venv/Scripts/python.exe scripts/index_bench.py --only milvus qdrant --index HNSW IVF_PQ
./.venv/Scripts/python.exe scripts/index_bench.py --synthetic   # 合成 30000 x 768
```

结果文件：`results/indexbench-*.json`（索引矩阵）、`results/textbench-*.json`（文本存储）。
分析见 `reports/2026-09-04-真实数据-索引矩阵基准.md` 第三节。

旧的 `multi_bench.py` 和 `bench.py` 仍可跑，但只测单一索引，不记录构建时间和存储，
新实验统一走 `index_bench.py`。
