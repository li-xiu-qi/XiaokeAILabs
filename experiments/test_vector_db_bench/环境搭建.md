# SurrealDB vs Milvus 本地性能对比

**机器**：Windows 11，AMD Ryzen 9 5900HX（8 核 16 线程），64 GB 内存，Docker Desktop 28.4.0
**测试日期**：2026-09-03
**被测版本**：SurrealDB 3.2.4（Windows 原生二进制）/ Milvus v3.0.0（Docker standalone）+ pymilvus 3.0.1

## 环境搭建

### SurrealDB

Windows 原生二进制，无需 Docker：

```bash
# 下载（约 115 MB）
curl -L -o bin/surreal.exe \
  https://github.com/surrealdb/surrealdb/releases/download/v3.2.4/surreal-v3.2.4.windows-amd64.exe

# 启动（3.x 起 file:// scheme 已废弃，必须用 rocksdb:// 或 surrealkv://）
./bin/surreal.exe start --user root --pass root --bind 127.0.0.1:8000 "rocksdb:data/surreal.db"
```

### Milvus

Windows 上无原生二进制，走 Docker（`Milvus Lite` 明确不支持 Windows，且只有 FLAT 索引）：

```bash
curl -L -o config/milvus-standalone-compose.yml \
  https://raw.githubusercontent.com/milvus-io/milvus/master/deployments/docker/standalone/docker-compose.yml
docker compose -f config/milvus-standalone-compose.yml up -d
```

三个容器：`milvus-standalone`（19530）、`milvus-etcd`（2379）、`milvus-minio`（9000/9001）。

### Python 环境

```bash
py -3.13 -m venv .venv
./.venv/Scripts/python.exe -m pip install surrealdb pymilvus numpy
```

> **不要用 `pkm-hub-runtime/.venv` 的 Python**。那个 uv 版 CPython 3.12 的 OpenSSL 在本机有缺陷，
> 任何 `urlopen()` 调用都崩（`OPENSSL_Uplink: no OPENSSL_Applink`）。用 python.org 版 3.13。

## 实测结果（2026-09-03，本机）

30,000 条 768 维向量，k=10，两边都 HNSW（`M=16`，`efConstruction=200`）。

| 指标 | SurrealDB 3.2.4 | Milvus v3.0.0 |
|------|----------------:|--------------:|
| 写入吞吐 | 407 vec/s | 3,938 vec/s |
| 查询 p50（ef=64） | 95 ms | 6 ms |
| 查询 p50（ef=512） | 22 ms | 8 ms |
| 召回率（ef=512） | 0.84 | 0.83 |

ef 扫描：

| ef | SurrealDB p50 | SurrealDB recall | Milvus p50 | Milvus recall |
|---:|--------------:|-----------------:|-----------:|--------------:|
| 32 | **16,210** | 0.61 | 6 | 0.30 |
| 64 | 95 | 1.00 | 6 | 0.40 |
| 128 | 84 | 1.00 | 6 | 0.55 |
| 256 | 84 | 1.00 | 9 | 0.70 |
| 512 | 22 | 0.84 | 8 | 0.83 |

两个值得注意的现象。SurrealDB 的 ef 曲线不平滑且不单调，ef=64 到 256 延迟恒定在
84-95ms，ef=512 反而降到 22ms，ef=32 直接劣化到 16 秒。正常 HNSW 应该是 ef 越大越慢。
召回率方面，SurrealDB 在 ef=64 就到 1.00，然后 ef=512 掉到 0.84，不可能是同一算法的输出。

详细分析见 `reports/2026-09-03-性能对比.md`。

## 三个必须踩过才知道的坑

### 1. Milvus 在 `create_collection` 里传 `index_params` 会被降级成 AUTOINDEX

```python
# 这样建出来的索引是 AUTOINDEX，不是 HNSW
c.create_collection(..., index_params=ip)
c.describe_index(...)   # → index_type: 'AUTOINDEX'
```

AUTOINDEX **不吃查询侧的 ef 参数**。实测 ef 从 32 扫到 1024，召回率和延迟完全不变
（恒为 0.228 / 5.0 ms），极易误判成「ef 传不进去」。

正确做法是建表后再显式建索引：

```python
c.create_collection(collection_name=n, dimension=768, metric_type="L2",
                    id_type="int", primary_field_name="pk", vector_field_name="vector")
ip = IndexParams()
ip.add_index(field_name="vector", index_type="HNSW", metric_type="L2",
             params={"M": 16, "efConstruction": 200})
c.create_index(collection_name=n, index_params=ip)
```

### 2. Milvus 3.0 的索引是异步构建的

`create_index` 返回时索引还没建完，此时查询走的是未索引数据。必须轮询到就绪：

```python
d = c.describe_index(collection_name=n, index_name="vector")
# 等 d["state"] == "Finished" 且 d["pending_index_rows"] == 0
```

### 3. SurrealDB 的 KNN 必须用 `<|K,EF|>` 操作符

```sql
-- 这样走索引
SELECT pk, emb FROM vec WHERE emb <|10,64|> $q;

-- 这样退化成全表扫描，召回率为 0
SELECT pk, emb, vector::distance::euclidean(emb, $q) AS d
FROM vec ORDER BY d LIMIT 10;
```

另：`BEGIN; ... COMMIT;` 必须在**同一条 query 语句**里分号拼接，分两次调用会报
`Cannot COMMIT without starting a transaction`。

## 测试方法

- 数据：`numpy` 确定性生成的均匀随机向量（`default_rng(42)`），768 维，float32
- 查询集：200 条均匀随机向量
- 召回率基准：暴力搜索精确 top-k（用 `|a-b|^2 = |a|^2 + |b|^2 - 2ab` 展开式，
  避免开 7.7 GB 中间张量）
- 两边都用 HNSW，`M=16`，`efConstruction=200`，查询侧 `ef=64`
- 延迟：5 轮，第 1 轮作冷启动单独记录，后 4 轮取分布
