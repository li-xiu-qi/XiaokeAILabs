# 主流数据库的索引与存储设计

> 实证日期 2026-09-07 · 基于官方文档与源码分析

本笔记记录主流数据库在索引和存储层面的设计选择：用了什么索引结构、存储引擎采用了什么范式、为什么这样设计。目的是把前面各篇的理论模型映射到真实系统上，看到理论如何落地。

## 索引结构与存储架构总览

| 数据库 | 核心索引 | 存储架构 | 写模式 | 设计哲学 |
|---|---|---|---|---|
| PostgreSQL | B-tree、GiST、GIN、BRIN、Hash | Heap + 索引 | 追加 WAL + 原地更新 | 功能最全的通用关系数据库 |
| MySQL InnoDB | 聚簇 B+树、自适应哈希索引 | 聚簇索引（主键即数据） | WAL + Double Write Buffer | OLTP 性能优先 |
| SQLite | B-tree（表即索引） | 单文件 B-tree | WAL / Rollback Journal | 嵌入式零配置 |
| DuckDB | 无显式索引（向量化扫描） | 列式存储 | 追加写 + 检查点 | 分析型 OLAP |
| RocksDB | 无显式索引（Key 有序） | LSM-tree (MemTable + SSTable) | WAL + 顺序写 | 写密集型 KV |
| Elasticsearch | 倒排索引 (Lucene) | 分段文件 (segment) | 追加写 + 后台合并 | 全文搜索 + 向量搜索 |
| Redis | 跳表 (Sorted Set)、哈希表 | 全内存 | AOF / RDB 持久化 | 内存数据结构服务器 |

## PostgreSQL：功能最全的索引体系

### 索引架构

PostgreSQL 提供 6 种索引类型，是主流关系数据库中索引类型最多的：

**B-tree**（默认，覆盖 80% 场景）：
- 底层是平衡多路搜索树（Lehman & Yao 高并发 B+树变体）
- 支持等值查询、范围查询、排序、前缀匹配
- 非聚簇设计：数据和索引分开存储，索引叶子节点存 TID（tuple ID）
- 支持覆盖索引（只扫描索引不访问数据）
- 设计原因：通用性，默认覆盖最常见查询模式

**Hash**（仅等值查询，较少用）：
- 桶数组 + 链表溢出
- 只支持 `=` 和 `<>` 操作符
- 不支持崩溃恢复（不支持 WAL），8.3 后被废弃
- 设计原因：特定场景下比 B-tree 更小更快，但维护成本高

**GiST**（通用搜索树）：
- 为任意标量数据类型提供通用搜索框架
- 后端实现包括 R-tree（空间数据）、B-tree（继承）
- 支持 PostGIS 的地理空间查询
- 设计原因：统一框架，一个接口支持多种数据类型

**GIN**（倒排索引）：
- 每个被索引值映射到一组行标识符（TIDs）
- 内部用 B-tree 对"键 → TID 列表"做索引
- 支持 JSONB 查询、全文搜索、数组包含查询
- 设计原因：JSON 和全文搜索是 PostgreSQL 的热门用例（9.4+ JSONB 后爆发）

**BRIN**（块范围索引）：
- 记录每个数据块（默认 1 MB）的极值信息
- 索引体积极小（TB 级表只需几 MB 索引）
- 适合时序数据（按时间顺序排列）
- 设计原因：应对超大表的"大区间过滤"场景，用最小存储跳过无关块

### 存储架构

PostgreSQL 采用 Heap 存储（数据和索引分离）：

- 表数据（Heap）：按 8 KB 页存储，页内记录无序（除非 CLUSTER 后重新排列）
- 每个页头包含 MVCC 信息：xmin（创建事务）、xmax（删除事务）
- 索引页：内部节点和叶子节点都是 8 KB 页，叶子节点存（索引键值, TID）
- VACUUM 进程清理死元组（已提交事务的旧版本）

设计原因：MVCC 需要原地更新（新版本写入新位置），不适合聚簇索引（聚簇索引移动行会级联更新所有索引）。Heap + 非聚簇索引是 MVCC 友好的设计。

### WAL（预写日志）

- 所有修改先写 WAL（追加写），然后更新 Buffer Pool
- WAL 默认 16 MB 段文件，无限循环
- Checkpointer 进程定期刷新脏页到数据文件
- 设计原因：崩溃恢复。WAL 是增量日志，崩溃后重放 WAL 即可恢复到一致状态

## MySQL InnoDB：OLTP 性能极致

### 存储架构

InnoDB 采用聚簇索引（Clustered Index）：

- 主键索引就是数据本身：B+树叶子节点存完整行数据
- 二级索引（非主键索引）叶子节点存主键值：查询二级索引后需要"回表"查主键索引
- 页大小 16 KB（可配置），页内有序
- 页之间用双向链表连接，叶子层构成有序链表

设计原因：主键查询最常见，聚簇索引把数据和主键索引放在一起，省一次查找。但二级索引回表是代价，所以 InnoDB 推荐用自增主键。

### 缓冲池（Buffer Pool）

- 内存中的页缓存，默认 128 MB，可调至几十 GB
- LRU 链表 + Free 链表管理页
- 预读：线性预读（顺序读 56 个页触发预读 64 个页）、随机预读（同一 extent 内 13 个页触发）
- 设计原因：内存比磁盘快 10^5 倍。Buffer Pool 命中率 99% 时，平均 IO 延迟从毫秒级降到微秒级

### 双写缓冲区（Double Write Buffer）

- 页刷盘时先写 Double Write Buffer（2 MB 连续空间），再写实际数据文件
- 防止"部分写失效"：16 KB 页由 4 KB OS block 组成，断电可能只写 8 KB
- 设计原因：页损坏是不可容忍的。Double Write Buffer 是"草稿本"，确保页完整

### 自适应哈希索引（Adaptive Hash Index）

- InnoDB 在 Buffer Pool 中自动建立热点页面的哈希索引
- 不需要 DBA 手动创建，后台线程自动维护
- 设计原因：B+树点查是 O(log n)，热点页面的点查改为 O(1)。AHI 是"免费午餐"

### 写缓冲（Change Buffer）

- 二级索引的非唯一页不在 Buffer Pool 中时，修改暂存 Change Buffer
- 页被读入 Buffer Pool 时再合并变更
- 设计原因：减少随机 IO。二级索引的插入/更新是随机 IO，Change Buffer 把多次修改合并成一次

## SQLite：单文件的极致简约

### 存储架构

SQLite 把所有数据存在一个文件中，用 B-tree 组织：

- 每个表和索引都是独立的 B-tree，存储在同一个数据库文件中
- 页大小默认 4 KB（可配置 512 B ~ 64 KB）
- B-tree 内部页和叶子页都是 4 KB 页，叶子页存 (Key, Value) 对
- 文件头 100 字节：魔数、页大小、编码、修改计数等

**设计亮点——表即索引**：
- 表数据本身就是一个 B-tree（rowid 为主键）
- 所有数据都存在主键 B-tree 的叶子节点中
- 不需要单独的聚簇索引/非聚簇索引概念
- 设计原因：单文件存储，所有数据有序排列在主键 B-tree 上，自然支持范围查询

### WAL 模式

- WAL 文件追加所有修改，读取和写入不互斥
- 多个 reader 不阻塞，writer 顺序追加
- 自动检查点：WAL 达到 1000 页时合并回主数据库文件
- 设计原因：传统的 Rollback Journal 模式写事务需要复制整个页，WAL 模式只需要追加，写吞吐提高 2-10 倍

## DuckDB：列式分析的杀手锏

### 存储架构

DuckDB 采用列式存储，所有数据按列组织：

- 每个列是一个连续的内存/磁盘块
- 读取查询只加载需要的列，不加载整行
- 列内数据连续存储，压缩效率高（相同类型、相似值）

**压缩**：
- 字典编码（低基数列）：字符串列先建字典，每行只存字典索引
- RLE 编码：重复值只存一次（如城市列："北京"出现 100 万次）
- 位打包（bit packing）：整数用最小位数存储
- 压缩比典型 5-10x，比行式存储高 2-3 倍

设计原因：OLAP 查询通常只访问少数列（如 `SELECT city, AVG(age) FROM users GROUP BY city`），列式存储只需读 2 个列，行式存储需要读整行。实测查询快 10-50 倍。

### 向量化执行引擎

- 不逐行处理数据，而是批量处理（每批 1024 行）
- 利用 SIMD 指令（AVX2/AVX-512）并行计算
- 表达式求值、过滤、聚合全部向量化
- 设计原因：CPU 的 SIMD 指令一次处理 8-16 个元素，向量化执行能把函数调用开销摊到多个元素上，CPU 利用率从 10% 提升到 80%+。

### 零拷贝 Parquet 直读

- 直接读取 Parquet 文件，不需要导入数据
- 通过 MMAP 映射 Parquet 到内存，零拷贝
- 谓词下推：在 Parquet 层过滤，不读取不需要的行
- 设计原因：数据湖场景下，数据已在 Parquet 中，导入数据库是多余的。DuckDB 的定位是"分析引擎"，不是存储系统。

## RocksDB：写密集型的工业级引擎

### 存储架构

RocksDB 采用 LSM-tree，核心组件：

**WAL（Write-Ahead Log）**：
- 所有写入先追加到 WAL（顺序写），崩溃后重放恢复
- WAL 是操作系统文件的追加写，不随机

**MemTable（内存表）**：
- 跳表（Skip List）实现，保证按键有序
- 写入 MemTable 是内存操作，立即返回
- 满后转为 Immutable MemTable，后台刷盘

**SSTable（磁盘有序表）**：
- 不可变文件，按键有序
- L0 层：文件按生成时间排序，key 范围可重叠
- L1-L6 层：每层文件 key 范围不重叠，按大小排序
- 每个 SSTable 分块，块内有布隆过滤器

**Compaction（后台合并）**：
- L0 → L1 → L2 → ... 逐层合并
- 默认 size_ratio = 10：L1 总大小是 L0 的 10 倍，L2 是 L1 的 10 倍
- Leveling 策略：每层 key 不重叠，写放大 ~30x
- Universal 策略（tiering 变体）：每层多个 run，写放大更低

设计原因：
- 随机写 → 顺序写：WAL 和 MemTable 都把随机写变成顺序写
- 范围查询：每层 key 有序，归并范围查询
- 写放大是代价：Compaction 需要重写数据，但换来的是写入吞吐量提升 10-100 倍

### 为什么 WAL + LSM-tree 比 WAL + B-tree 更适合写密集？

B-tree（如 InnoDB）的写入流程：WAL → Buffer Pool（修改页）→ Checkpoint → 数据文件。WAL 是顺序写，但 Buffer Pool 的脏页刷新可能是随机 IO，而且页分裂会导致页分裂和页合并，产生额外的随机 IO。

LSM-tree（如 RocksDB）的写入流程：WAL → MemTable（跳表插入）→ Flush → SSTable。全部顺序写，没有页分裂。Compaction 是后台顺序写。

实测：RocksDB 随机写吞吐是 InnoDB 的 5-10 倍。

## Elasticsearch：全文搜索的倒排索引

### 存储架构

Elasticsearch 基于 Lucene，核心是倒排索引：

- Segment：不可变的倒排索引文件，由内存缓冲区刷新生成
- 每个 segment 是一个独立的倒排索引，有词典 + 倒排列表
- 倒排列表用 FST（Finite State Transducer）压缩词典，用 Block-based 编码压缩 docID

### Segment 合并

- 后台线程定期合并小 segment 为大 segment
- 合并策略：Tiered（按大小和文档数分层，默认）、Log（适合日志场景）、Force Merge
- 设计原因：小 segment 查询时需要遍历多个，合并后查询更快，存储更紧凑（合并时删除标记被清理）

### 向量搜索

- 从 8.0 开始支持 HNSW + IVF 向量索引
- 向量数据存储在专门的 segment 中，用 HNSW 图加速近似搜索
- 设计原因：RAG 场景爆发（2023-2024），用户需要在同一系统支持全文搜索 + 语义搜索

## Redis：内存数据结构的多样性

### 存储架构

Redis 全内存存储，持久化可选：

**数据结构映射**：
- String：动态字符串（SDS）或整数
- List：双向链表（Linked List）或 ZipList（紧凑数组）
- Set：哈希表
- Sorted Set：跳表（Skip List）+ 哈希表
- Hash：ZipList（小 hash）或 哈希表
- Stream：Rax 基数树

### 持久化

- RDB：定时快照，全量数据写入二进制文件
- AOF：追加所有写命令到日志文件
- 混合持久化：RDB 快照 + AOF 增量

**为何 Sorted Set 用跳表不用 B+树？**
- 跳表实现简单（B+树需要旋转、分裂、合并）
- 跳表并发友好（Redis 单线程不需要，但其他实现需要）
- 范围查询 O(log n + k)，和 B+树同级
- Redis 的跳表用 p=0.25，因为 Sorted Set 的 ZADD 和 ZRANGE 操作比点查多

## 设计模式的共性与差异

### 为什么有的用 B-tree、有的用 LSM-tree？

| 因素 | B-tree 优先 | LSM-tree 优先 |
|---|---|---|
| 读写比例 | 读密集 | 写密集 |
| 数据量 | 内存可缓存 | 远超内存 |
| 磁盘类型 | SSD（随机 IO 不贵） | HDD（顺序写优先） |
| 延迟敏感 | 点查 P99 低延迟 | 吞吐优先 |

MySQL InnoDB 和 PostgreSQL 用 B-tree：因为 OLTP 场景读远多于写，B-tree 的点查延迟更低。

RocksDB 和 Cassandra 用 LSM-tree：因为它们用于写密集场景（日志、时序、KV），LSM-tree 的顺序写吞吐比 B-tree 高 10 倍。

### 为什么有的用行式存储、有的用列式存储？

| 因素 | 行式存储 | 列式存储 |
|---|---|---|
| 查询模式 | 点查整行 | 聚合少数列 |
| 事务 | 需要行级锁定 | 不需要行级锁定 |
| 更新频率 | 频繁更新 | 批量加载 + 只读 |
| 压缩效率 | 低（不同类型混合） | 高（同类型连续） |

MySQL 和 PostgreSQL 用行式：OLTP 场景需要事务和行级锁定，行式存储修改一行只需要改一个页。

DuckDB 和 ClickHouse 用列式：OLAP 场景只查少数列，列式压缩效率高，向量化执行快。

### 索引选择的原则

1. **数据访问模式决定索引结构**：点查用哈希或 B-tree，范围查询用 B-tree，文本搜索用倒排，写密集用 LSM-tree
2. **内存/磁盘层级决定设计**：全内存用跳表/哈希，磁盘存储用 B-tree/LSM-tree
3. **并发模型决定实现**：单线程不需要锁，多线程需要无锁结构（CAS、RCU）
4. **写放大是换吞吐的代价**：LSM-tree 写放大 30x 换写入吞吐 10 倍，Compaction 是后台支付的账单
