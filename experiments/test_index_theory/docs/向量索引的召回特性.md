# 向量索引的召回特性

同一个 HNSW ef=64，在随机向量上召回 0.38，在真实文本 embedding 上召回 0.9933。差距不在索引实现，在数据的几何结构。这一篇说明为什么召回率必须在真实语料上测，以及这份实测数据的适用边界。

## 召回率与前两项的性质不同

存储占用是几何问题，`n × d × 系数` 是闭式解，随机向量与真实向量算出来一样。查询延迟取决于计算量，FLAT 扫 n 个向量、HNSW 走图、IVF 访问 nprobe 个聚类，这些关系式也与向量内容无关。两项都用随机数据测过，结论成立。

召回率不一样。它问的是「近似索引找到的邻居，有多少是真邻居」，而「谁是邻居」完全由数据分布决定。随机均匀向量在高维空间里任意两点距离接近相等，邻居关系不成立，近似索引的剪枝和导航就都在随机丢弃正确结果。这不是索引的缺陷，是测量对象不存在。

## 实测证据

数据用 `all-MiniLM-L6-v2` 编码的 20 Newsgroups，11293 条底库加 600 条查询，384 维，L2 归一化。数据来自 `test_vector_db_bench`，五库对比用的同一份，没有重新编码。

| 索引 | 参数 | recall@10 | 说明 |
|---|---|---|---|
| HNSW | M=16 ef=16 | 0.943 | 搜索代价最低的一档 |
| HNSW | M=16 ef=64 | 0.993 | 召回与延迟的平衡点 |
| HNSW | M=16 ef=256 | 0.9995 | 接近精确搜索 |
| IVF | nlist=1024 nprobe=4 | 0.704 | 只访问 4 个聚类 |
| IVF | nlist=1024 nprobe=32 | 0.956 | 访问 1/32 的聚类 |
| SQ8 | 8bit 标量量化 | 0.995 | 精度损失可忽略 |
| PQ | m=32 nbits=8 | 0.654 | 乘积量化损失明显 |
| IVF-PQ | nlist=1024 nprobe=8 | 0.591 | 量化与剪枝损失叠加 |

对照之前用随机 d=128 数据测的 HNSW ef=64，召回 0.38。同一套索引、同一个 ef，换真实 embedding 后跳到 0.993。

## 这份数据的适用边界

n=11293 太小，有三个结论不能从它得出来，混用会得出错误判断。

**加速比不能比。** FLAT 只需扫 1 万个向量，0.042 ms 就返回。HNSW ef=256 召回 0.9995，实测只比 FLAT 快 1 倍。生产环境里 HNSW 在百万级要比 FLAT 快几百倍，这个差距要到 n 足够大才显现，与索引好坏无关，是规模效应。n 小时图遍历的固定开销占比过高，测出来的是劣势。

**量化索引的收益看不出来。** SQ8 召回 0.995 高于 HNSW ef=64，但延迟 0.743 ms 反而更差。量化索引的价值在于把 2 GB 压到 250 MB，在 17 MB 数据集上没有任何体现，测它的延迟没有意义。

**绝对延迟数字不能外推。** 0.007 ms/query 这个量级说明数据全在内存和缓存里，没有触及内存带宽上限。真实场景的延迟还受索引加载、内存换页、并发影响，这里的数字只反映纯计算。

n 与延迟的关系在 `向量索引的查询延迟模型.md` 里，那一篇用随机数据测了 100 到 20 万六档，测的是规模趋势，不受数据分布影响，结论独立成立。

## 调参时的判断顺序

分词或检索结果不对时，按召回曲线的形状判断落在哪一层。

召回在 0.38 附近且换真实数据后没有变化，先怀疑数据本身，而不是索引参数。随机向量、未归一化的向量、编码模型与语料不匹配，都会让近邻关系失真。

召回在 0.6 到 0.9 之间，是近似索引的正常工作区间，按代价调。HNSW 提 ef，IVF 提 nprobe，两者都是近似线性的代价换召回。

召回掉到 0.4 以下但参数已经很高，看是不是量化环节。PQ 在 m 太小时码字容量不够，会出现多个向量竞争同一个码字而不可分。换 SQ8 或加大 m。

召回接近 1.0 但仍不够，需要更精确的 ground truth。此时该上重排，用原始向量对候选集做精确打分，那是另一层机制。
