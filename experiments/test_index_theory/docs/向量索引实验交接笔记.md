# 向量索引查询延迟模型 交接笔记

> 供下一轮续接。实验目录 `experiments/test_index_essence/`，当前未提交（git status 显示 `?? experiments/test_index_essence/`）。

## 一、这轮修正了什么

两处错误判断，都来自上一轮。

**错误一：Windows 上跑不起来图量化索引。** 上一轮判断 Windows 上 HNSW_SQ、IVF_RABITQ 三类图量化索引全部失败，依据是 faiss Windows 轮子有缺陷。这个判断错了。根因是 `IndexHNSWSQ` 的参数顺序传反，C++ 签名是 `(d, qtype, M)`，传成 `(d, M, qtype)` 时 Windows 直接进程崩溃（退出码 0xC0000005，无 Python 异常），WSL 抛 `unknown qtype`，两种形态都让人以为是库缺陷。换对顺序后两个平台都正常。当时还留下另一条错判说 `IndexIVFRaBitQ` 的 qb>=2 不可用，见错误三。

**错误二：HNSW-PQ 召回低是因为 m 太小。** 这条代价更大。`IndexHNSWPQ` 的 C++ 签名是 `(d, pq_M, M, pq_nbits)`，而 faiss 自带的 `__init__.pyi` stub 写的是 `(d, pq, M, metric)`，stub 是错的。按 stub 传 `(D, 16, 32, 8)` 不报错，实际取到 pq_M=16，对 d=128 而言每子向量 8 维，召回只有 0.038 且延迟不随 pq_M 变化。当时扫 m 从 8 到 128 召回始终 0.04，这个观察本该直接指向「参数没生效」，却解释成了「m 还不够大」。

**错误三：IVF_RaBitQ 的 qb>=2 不可用。** 这个结论连续存在了两轮，同样是错的。C++ 签名是 `(quantizer, d, nlist, metric, own_invlists, nb_bits)`，第 4 位是 `MetricType`，当时传的 1/2/4 全被当成 metric，依次选中 L2、L1、Lp。RaBitQ 只实现 L2 与内积，所以 2 和 4 命中断言，1 恰好是 L2 才跑通。多比特的 nb_bits 在第 6 位，从来没被测到。用正确签名重扫（Windows，nprobe=8）：nb_bits=1 时 0.109 毫秒召回 0.401，2 位时 0.142 毫秒召回 0.615，4 位时 0.142 毫秒召回 0.850，8 位时 0.162 毫秒召回 0.988。延迟不敏感，召回单调上升，因为 RaBitQ 用 1 位码粗筛、只对通过阈值的候选算精排，加比特的代价在存储不在时间。这一条直接推翻了文档多处「量化不省时间」的说法，是这几轮里最有价值的修正。

三个错误是同一类：参数位置与文档不符、不报错、指标异常，处置方式也一模一样，扫参数看指标，指标不动就归因成算法或封装的局限。第二次本该更容易发现，因为第一次已经得出「faiss 的 .pyi 与 C++ 签名不符」的结论，但当时只当成 HNSW_PQ 的个案，没推广成「所有索引签名以 C++ 头文件为准」。真正该固化的是动作：遇到「跑得通但指标异常」或「断言失败但字段看起来对」，第一动作是打印构造后对象的全部关键属性，与头文件签名逐位对照。

用正确签名重扫（Windows，M=16、nbits=8、ef=64）：pq_M=16 时 0.053 毫秒召回 0.038，pq_M=32 时 0.115 毫秒召回 0.186，pq_M=64 时 0.180 毫秒召回 0.646，pq_M=128 时 0.330 毫秒召回 0.875。延迟随 pq_M 近似线性（16 到 128 涨 6.2 倍），pq_M 必须整除 d，d=128 时合法值只有 16、32、64、128，传 48 会抛 `!(d % M == 0)`。

代价是 WSL 那批 HNSW-PQ 数据也是用错签名采的，主文档对比表里标成 m=32 的那一列实际是 pq_M=16，已整列删除，换成 Windows 的 pq_M=128 数据。`verify_latency_wsl_crosscheck.py` 的 docstring 里已标注该列不可用。其余各列（HNSW-Flat、HNSW-SQ8、HNSW-SQ4、IVF 各量化档）不受影响，因为它们的参数签名是对的。

## 二、已完成的工作

主文档 `向量索引的查询延迟模型.md` 已扩到约 300 行，含量化档位延迟标定、Milvus 之外的索引家族、三档选型边界、跨环境复核四节，索引表列全 Milvus 3.0 全部类型。踩坑记录扩到八节，新增第二节专门记 `IndexHNSWPQ` stub 错误，第八节补了「扫参数时指标不随参数单调变化就应先怀疑参数没生效」这条判据。

Windows 侧图量化数据已落盘 `results/win_graph_quant_d128.json`，脚本 `scripts/verify_latency_graph_quant_win.py`。子进程隔离，一个 case 崩溃不影响其余，失败 case 记录退出码和错误尾行。`results/` 下现在有七个 JSON。

## 三、仍然不知道什么

延迟绝对值带约 25% 的跨次波动，这一条是这轮量出来的。同脚本跑第二遍，HNSW-Flat ef=64 是 0.089 对 0.096，HNSW-SQ8 是 0.166 对 0.157，RaBitQ nb_bits=1 是 0.109 对 0.144。受影响最大的是 HNSW-PQ 在 ef=16 与 ef=32 上的差值，它小于噪声，两次运行排序完全相反（0.231/0.195 单调，0.186/0.290 非单调），这两个档位在文档里已标明不能当趋势用。

`IndexIVFPQFastScan` 已验明可用但只采了 Windows 一侧，签名是 `(index_ivfpq, bbs)`，底层 PQ 的 nbits 必须是 4。实测（nprobe=8）与同参数普通 IVFPQ 对照：m=8 时 0.198 对 0.176 毫秒，m=32 时 0.542 对 0.520，m=128 时 1.448 对 1.785。只在 m 大时占优，m 小时反而慢，与「SIMD 批处理要摊薄固定开销」的预期一致。数据未落盘，也还没写进主文档。

文档选型边界里「一百万以上」分档的延迟常数按缩放律外推，未在 n=100 万级数据上实测。HNSW_PRQ 未标定，已用 `hasattr` 确认 `IndexHNSWPRQ` 不在 faiss 1.15.0 封装里；`IndexIVFHNSW` 同样缺失，而 `IndexIVFPQR` 与 `IndexIVFResidualQuantizer` 在。索引表里标「否」的两行维持原判，但判据从推断变成实测。

HNSW-PQ 只有 Windows 侧数据。上一轮 WSL 那列作废后没重采，跨环境对照缺一半。

## 四、前向计划

`IndexIVFPQFastScan` 已验明可用（签名 `(index_ivfpq, bbs)`，底层 PQ 须 nbits=4），但数据没落盘，主文档也没写，这是下一轮第一件事。HNSW-PQ 的 WSL 侧数据待补。HNSW_PRQ 仍未标定。n=100 万级数据验证选型边界交叉点最耗时。`pkm-hub-runtime/scratch/` 下那批 `win_retry_correct_order.py`、`wsl_*.py` 探测脚本已完成使命，可清。

## 五、对不确定性的诚实

「Windows 原生能测 HNSW_SQ、HNSW_SQ4、HNSW_PQ、IVF_RaBitQ」已验证，`win_graph_quant_d128.json` 现有 32 个 case，30 成功、2 个失败且都是有意保留的对照组。「RaBitQ 的 nb_bits 1 到 8 召回 0.401 到 0.988 单调上升」两次运行都复现，稳。「RaBitQ 比 HNSW-Flat ef=256 更快且更小」依赖单次运行绝对值（0.162 对 0.241 毫秒），两次跑是 0.162/0.241 与 0.153/0.208，方向一致但差值幅度不同，只能说方向稳。「量化定性随平台反转」已验证，双平台数据都在。WSL 的 HNSW-PQ 一列已判定无效并删除。IVFPQFastScan 只在 Windows 上跑过，跨环境未验。Windows 的 HNSW-SQ4 召回只有 0.483，且在 ef=64 时比 SQ8 还慢，这一档没有使用价值。

本轮唯一推翻既有结论的改动是 RaBitQ 那条：文档此前写「IVF 上量化大多亏或打平」，实测 RaBitQ 在 IVF 上可以不付时间代价。已改总述、量化定位、选型边界三处。这条可信度高于其他修正，因为它基于完整的 nb_bits 四档扫描加两次运行复核，不是单点对比。

索引表里标「否」的项已用 `hasattr` 复核：`IndexHNSWPRQ` 与 `IndexIVFHNSW` 确实缺失，`IndexIVFPQR` 和 `IndexIVFResidualQuantizer` 则在封装里。表格这两行维持原判，但判据从推断变成实测。

## 六、前向计划

IVFPQFastScan 数据落盘并写进主文档，成本最低。HNSW-PQ 的 WSL 侧数据要补，否则跨环境对照缺一半。n=100 万级数据验证选型边界交叉点最耗时，且要重跑所有脚本。`pkm-hub-runtime/scratch/` 下那批 `win_retry_correct_order.py`、`wsl_*.py` 探测脚本已完成使命，可清。

HNSW_PRQ 建议在文档里把「未标定」改成「faiss 封装缺失」，两者含义不同：前者暗示可标定而没做，后者说明当前工具链做不到，要标定得走 knowhere 或自行编译。这一项成本高于收益，不建议现在投入。
