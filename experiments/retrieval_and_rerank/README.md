# 检索与重排实践：向量库、稀疏向量、ColBERT 与 Reranker 怎么用

检索链路四个关键环节的上手实践，每个子目录对应一种检索范式或一个库的用法。这不是横向对比实验（横向基准见 `test_vector_db_bench`），是「某个组件拿到手怎么跑通」的教程集合，按一条完整检索流水线的先后顺序组织。

## 子目录与流水线位置

一条典型 RAG 检索链路是：召回（稠密或稀疏）可以多路并行，晚期交互是另一种召回思路，召回结果再交给重排，最后只把重排后的少量内容喂给大模型。

| 目录 | 环节 | 内容 |
|---|---|---|
| `faiss_tutorial/` | 稠密向量库入门 | FAISS 索引类型、NumPy 性能对比、索引存取、自定义 ID、大规模与 GPU |
| `bge_m3_sparse/` | 稀疏向量召回 | BGE-M3 词汇权重生成，两种实现：FlagEmbedding 直接调用、transformers 手工复现 |
| `colbert/` | 晚期交互召回 | ColBERT v1 与 v2：逐 token 向量表示加晚期相似度聚合的用法 |
| `bge_reranker/` | 重排 | BGE Reranker 三套 notebook 中英双语：入门、部署、评测 |

## 三种召回范式的区别

这三种召回常被笼统叫成「向量检索」，实际机制不同，选型时要分清：稠密向量把整段文本压成一个向量，靠向量距离召回，快但丢词级细节；稀疏向量保留词项权重（BGE-M3 学到的是词的重要性，不依赖人工规则），能命中精确关键词；ColBERT 给每个 token 保留向量，查询时才做 token 级交互，精度通常更高，代价是存储和计算更重。三者不是互斥的，生产链路常把稠密和稀疏召回结果合并，再统一过 Reranker。

## Reranker 的位置

Reranker 不负责从全库捞候选，全库重排计算量扛不住。它只对前面召回阶段拿到的几十到几百条候选做精排，输入是查询加候选文档全文，输出相关性分数。bge_reranker 目录的三套 notebook 按入门、单模型部署、效果评测递进，中英双语版本内容对应。

## 注意

部分脚本写死了旧本机模型路径（含用户名和旧盘符），重跑时要改成自己的模型目录或模型标识。各子目录依赖不同，按各自脚本和 notebook 里的说明安装。
