# Train Your Own AgentJev (Open-Source Jev Decision Model)

[中文说明](README.md)

Whether a general-purpose decision model works for a specific task must be tested with data from the target setting. This directory provides a training path that starts from public data and a base model, fine-tunes a discriminative decision model end to end, then selects a checkpoint, calibrates it, tests it, and starts a service.

The model code comes from [`malevrigns/agent-jev`](https://github.com/malevrigns/agent-jev) (Apache-2.0). This experiment keeps only the parts required for training. The base model is Qwen3-0.6B, about 1.5 GB. The dataset is [`LocalLLaMA/typed-decisions`](https://huggingface.co/datasets/LocalLLaMA/typed-decisions) on Hugging Face; its two Parquet files total less than 0.8 MB.

## Directory structure

```text
agent-jev-text/
├── agentjev/           # Qwen3 backbone and candidate head
├── jev_service/        # Input protocol, encoding (including shared-prefix acceleration), inference engine, and HTTP service
├── scripts/
│   ├── download_data.py       # Download and verify the dataset
│   ├── download_backbone.py   # Download the Qwen3-0.6B backbone
│   ├── prepare_data.py        # Convert Parquet to JSONL and split reproducibly by case
│   ├── train.py               # Training, checkpoint selection, calibration, and testing
│   ├── smoke_gpu.py           # One-step GPU check using synthetic data
│   ├── serve.py               # Start the inference HTTP service
│   └── protocol.json          # Training hyperparameters
├── data/               # Original Parquet files (generated by download)
├── prepared/           # Split JSONL files (generated by preparation)
└── runs/               # Training outputs (checkpoints and reports)
```

## Environment

A CUDA GPU that supports bfloat16 is required; training runs on the GPU throughout. Python 3.10 or later is required. We recommend creating an isolated environment, installing a CUDA-enabled PyTorch build compatible with the device, and then installing the remaining dependencies:

```bash
python3 -m venv .venv
source .venv/bin/activate
# First install a CUDA-enabled PyTorch build compatible with the device
python -m pip install -r requirements.txt
# This compatible version was used in the clean-environment verification
python -m pip install "transformers==5.16.1"
python -c "import torch, transformers, pyarrow; from transformers import Qwen3Model; print('torch:', torch.__version__, 'CUDA:', torch.cuda.is_available(), 'transformers:', transformers.__version__); assert torch.cuda.is_available() and torch.cuda.is_bf16_supported()"
```

`requirements.txt` specifies minimum versions and is not a complete lockfile. On 2026-11-15, installation and the GPU smoke path were verified in a newly created isolated environment: Python 3.12.3, PyTorch 2.15.0+cu132, Transformers 5.16.1, and PyArrow 26.0.1. `pip check` passed, and CUDA and bfloat16 were available on an NVIDIA GB10. Because the newest Transformers release was not compatible with this script path, the verified setup explicitly pins Transformers to 5.16.1 after installing the requirements. The check trained one step on synthetic data and confirmed a parameter update, then completed initial-model selection, calibration, and reporting. It does not reproduce real-backbone training or the 600-step run in this clean environment. See the [clean-environment GPU smoke record](evidence/clean-env-gpu-smoke-2026-11-15.json). CUDA and bfloat16 availability also does not establish that another GPU has enough memory for full-parameter fine-tuning. Reserve disk space for the model, data, and training outputs. The download commands below use `--mirror` to access hf-mirror; remove that option if no mirror is needed.

A GPU smoke check passed in an existing environment on an NVIDIA GB10 with Python 3.12, PyTorch 2.15.0+cu132 and Transformers 5.22.2. It uses a randomly initialized miniature Qwen3 and synthetic data, checks that one CUDA training step changes a parameter, then runs initial-model selection, calibration and reporting. It does not verify the real backbone or historical metrics. `pip check` in that environment still reports a platform compatibility issue for `nvidia-cusparselt-cu13`, so a fresh installation is not verified.

```bash

```

The output directory must not exist. A second check used the real Qwen3-0.6B backbone and typed-decisions data: five questions from one case per split. After downloading and splitting the data as described below, the following checks the real backbone and data. `/tmp/agentjev-mini` and the output directory must be new paths. If the backbone was already downloaded, verify its revision matches the one above:

```bash
mkdir /tmp/agentjev-mini
for split in train dev calibration test; do
  head -n 5 "prepared/${split}_questions.jsonl" > "/tmp/agentjev-mini/${split}_questions.jsonl"

python scripts/smoke_gpu.py --backbone models/Qwen3-0.6B-Base \

The parameter-change assertion verifies the training step; the selected model is not fine-tuned.

The Qwen3 backbone requires Transformers 4.51.0 or later, according to the [upstream model card](https://huggingface.co/Qwen/Qwen3-0.6B). This minimum indicates model support; it does not mean every later version has been tested.

## Four-step training workflow

Run the following commands from the `agent-jev-text/` directory.

### 1. Download the dataset and backbone

```bash
python scripts/download_data.py --mirror
python scripts/download_backbone.py --mirror
```

The dataset has two files: 1,200 training cases and 400 test cases, with five decision questions per case. Each file's SHA-256 is checked after download; a mismatch raises an error. By default, the backbone is saved to `models/Qwen3-0.6B-Base`, which must not exist or must be empty. The download defaults to upstream `main`; use `--revision <commit>` to pin and record a version for reproduction.

The dataset is written to `data/all/` by default. Before downloading, the script checks both target files and refuses to download or overwrite if either already exists. It writes to the destination only after both files pass verification. You can also download to a separate directory with `python scripts/download_data.py --out-dir /path/to/empty-data-dir`. To use another input directory, pass `prepare_data.py --data-dir /path/to/data-dir`; pass `--out-dir /path/to/empty-output-dir` to choose the split output directory.

The script stages and publishes data using temporary files and hard links on the same filesystem as the output directory, so the target filesystem must support hard links. Ordinary download errors and Ctrl+C clean up temporary files. If an error or interruption occurs during publication, complete files already published are retained; inspect the target directory or retry in a new directory. Forced process termination may leave a `.download-*` temporary directory. A subsequent run still protects existing targets.

### 2. Split the data

```bash
python scripts/prepare_data.py
```

The public data download, SHA-256 verification and case splitting below have been run on Linux. Splitting happens at the case level before questions are expanded. The 1,200 training cases are assigned by a fixed-seed hash to 960 training, 120 dev, and 120 calibration cases. All 400 test cases remain unchanged. The output directory must not exist or must be empty to protect existing files. Each split under `prepared/` contains separate questions and requests JSONL files. The script also writes `prepared/split_manifest.json` with every case ID and the source-file hashes for verification.

### 3. Train

```bash
python scripts/train.py \
  --backbone models/Qwen3-0.6B-Base \
  --run-dir runs/agentjev_v1
```

This is full-parameter fine-tuning, not LoRA. Training runs for 600 steps with a backbone learning rate of `1e-5`, a candidate-head learning rate of `1e-4`, and bfloat16. The initial model is also a candidate; the model is evaluated on the dev split every 100 steps, and a checkpoint is selected by uncalibrated soft cross-entropy. If training never improves on the initial model, step 0 is retained. The run directory must not exist or must be empty. Only after selection does the script fit a temperature for each question type on the separate calibration split; the test split is read last. The code fixes this order so test data does not leak into checkpoint selection.

The device log records a training time of about 49 minutes. On 2,000 test questions, the option with the highest predicted score matched the highest-probability option in the reference distribution 78.05% of the time. This is not accuracy on real-world tasks. `typed-decisions` contains synthetic cases, and its soft reference distributions come from a teacher model rather than real-world outcomes. The 2,000 questions come from 400 cases, so questions from the same case are not independent. This is a single run and cannot establish that the result transfers to other tasks. The training log remains on the device, and the repository does not include per-question predictions, so the result cannot be independently recalculated from this README alone.

On 2026-11-15, the 600-step run was repeated using backbone revision `c1899de289a04d12100db370d81485cdf75e47ca` and dataset revision `ea9306458d6e9563628369a3d1e72e362fb381d2`. Development selection chose step 600; agreement with the reference label was 78.05% on 2,000 test questions. Soft cross-entropy was 0.8584 before and 0.8571 after calibration. Peak CUDA allocation during training was approximately 33.65 GB. The isolated copied environment used Python 3.12, PyTorch 2.15.0+cu132 and Transformers 5.16.1 and passed `pip check`; it was not installed from scratch. The test set has historical results and is not a new blind test, and calibration is measured against the teacher reference distribution.

### 4. Start the service and verify it

```bash
python scripts/serve.py \
  --run-dir runs/agentjev_v1 \
  --backbone models/Qwen3-0.6B-Base \
  --port 8149
```

By default, the service listens only on the local machine. Send a decision request by POST to `http://127.0.0.1:8149/api/evaluate`:

```bash
curl -s http://127.0.0.1:8149/api/evaluate \
  -H 'Content-Type: application/json' \
  -d '{
    "id": "demo-1",
    "state": "My credit card was charged twice this month. Please refund the duplicate charge as soon as possible.",
    "questions": [{
      "id": "route",
      "type": "choice",
      "question": "Which department should handle this request?",
      "options": ["Billing", "Technical support", "Sales", "Other"]
    }]
  }'
```

The response contains a probability for each option and the winning option; the service does not generate text. Latency depends on the device, context length, number of candidates, and service configuration, so measure it with your own workload.

Encoding defaults to `auto`: candidates for the same question share KV computation for the `[STATE]+[QUESTION]` prefix. The prefix is computed once, and each candidate computes only its own suffix. To investigate encoding issues, use `--encoder path` to rerun path by path for comparison. Check output error and actual latency for each implementation and precision.

## Use your own data

The method does not depend on the official dataset. A case consists of a state, several questions, and candidate descriptions with a teacher distribution for each question; its fields should match the official rows. Adapt the `convert` function and split assertions in `scripts/prepare_data.py` to your schema. Keep three constraints: represent the target as a probability distribution rather than a single label, put only the state, question, and candidate descriptions in the model input, and reserve a test set that is not used for checkpoint selection or temperature fitting.
