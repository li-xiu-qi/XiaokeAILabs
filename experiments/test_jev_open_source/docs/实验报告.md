# Jev 系列实验报告

Jev 是 TypeSafe 推出的 System One 决策模型，不做文本生成，只对预设题型输出概率，只提供云端接口，权重不公开。它 2026 年 9 月在开发者社区火起来之后，社区出现三个开源复刻。这篇报告把 Laya、Nimble、metask-jev 拉到同一台机器、用同一套题测了一遍，另加一个生成式模型做对照。

复现步骤看《复现教程.md》，每个数字的原始输出在 `docs/执行日志/`，下面每张表都标了出处。四个模型的实测结论和选型建议在报告末尾「怎么选」一节。

## 测了哪些模型

| 对象 | 形态 | 参数 | 底座 |
|---|---|---|---|
| Laya 1.1B | 双 checkpoint 自动分流 | 1.1B | ModernBERT |
| Nimble 9B | 单模型 | 9B | Qwen3.5-9B 加 LoRA |
| metask-jev-4B | 单模型 | 4B | Qwen3.5-4B |
| Qwen3-VL-4B | 生成式对照 | 4B | Qwen3-VL |

Laya、metask、Qwen 跑的是同一套题，20 条分类加 5 条命题判断。Nimble 的基准是另一组演示题，问的是工单优先级和是否需要人工复核两个字段，所以它的准确率不进表，只进延迟表。

测试输入固定，英文是一条 86 字符的重复扣费投诉，中文是它的对应翻译约 25 字。metask 的 prompt 拆成 token 后是 239 到 244 个。

## 延迟，全部取中位数

单位毫秒，同一台 aarch64 GB10，2026 年 9 月 22 日实测。

| 对象 | 输入 | 完整一次判定 | 常驻显存 |
|---|---|---|---|
| Laya 英文 checkpoint | 英文 1 题 | 16.98 | 5.96 GB |
| Laya 多语言 checkpoint | 中文 1 题 | 8.25 | 5.96 GB |
| Nimble 9B | 英文 2 字段 | 365.33 | 17.57 GB |
| Nimble 9B | 中文 2 字段 | 366.66 | 17.57 GB |
| metask-jev-4B | 英文 1 题 | 133.5 | 8.58 GB |
| metask-jev-4B | 中文 1 题 | 133.7 | 8.58 GB |
| Qwen3-VL-4B 最简输出 | 英文 | 103.48 | 8.30 GB |
| Qwen3-VL-4B 最简输出 | 中文 | 104.85 | 8.30 GB |
| Qwen3-VL-4B JSON 输出 | 英文 | 1448.17 | 8.30 GB |
| Qwen3-VL-4B JSON 输出 | 中文 | 1153.54 | 8.30 GB |

出处是 `docs/执行日志/` 下编号 02、04、05、07、08 五份日志。

Laya 英文比中文慢一倍。原因是 Router 按输入文字的字符构成分流，英文落到英文 checkpoint，中文落到多语言 checkpoint，后者参数量小一半，延迟也就低一半。这不是「中文更快」，是两条路走了不同的模型。

题数合并。一次请求塞 16 道题，总时长 45.32 ms，摊到单题 2.83 ms，只有单独调用的六分之一。冷启动方面，单 checkpoint 加载 23.21 s，三个 checkpoint 全部常驻 60.34 s，之后路由本身的判定开销是 0.02 ms 到 0.19 ms，可以直接当它不存在。

## 准确率，20 条分类题

| 对象 | 英文 | 中文 |
|---|---|---|
| Laya | 95.0% | 95.0% |
| metask-jev-4B | 95.0% | 100% |
| Nimble | 未测 | 未测 |
| Qwen3-VL-4B | 未测 | 未测 |

出处是 `docs/执行日志/` 下编号 03 和 07 两份日志。

Laya 中文错的那条：它把一条该归「其他」的消息判成了账单问题，置信度 0.906。高置信度的错误比低置信度的错误更难防，调用方如果按置信度设闸，这一条会直接漏过去。

## 三个结构性发现

中文的命题判断题在 Laya 上失效。三个威胁退订的中文句子，模型给出的「命题为真」概率分别是 0.025、0.051、0.028，等于全部判成假。同一套题的英文输入上它三条全对。中文的意图分类它是做得了，准确率 95%，失效的只是「这句话说的对不对」这类真假判断。中文要用命题判断，Laya 得换成别的路线。

我们做了个反方向实验来确认这不是抽样噪声：把同一批中文句子强行灌给英文 checkpoint，准确率掉到 75%，置信度均值掉到 0.384。两个 checkpoint 的差异是真实存在的，Router 的分流不是可以省掉的装饰。

题数合并的成本曲线说明判别式模型天生适合批处理。1 题 16.87 ms，2 题单题 9.22 ms，4 题单题 5.61 ms，8 题单题 3.67 ms，16 题单题 2.83 ms。合并的边际成本在快速下降，因为一次前向就把所有题一起算完了。生成式模型没有这个性质，它必须一条一条生成文本。

生成式模型的成本跟着输出长度走。Qwen3-VL-4B 的单次前向是 49 到 52 ms，和 Laya 的 17 ms 在同一个量级。可一旦要求它输出一个 JSON 对象，它要多生成 23 到 29 个 token，完整一次判定就从约 105 ms 涨到约 1150 至 1450 ms。Laya 输出多少字段都是这个数，因为它根本不生成文本。这不是快慢问题，是成本结构问题。

## 测量口径

全部数字测于一台 aarch64 GB10、20 核 CPU、121 GB 统一内存、单卡 CUDA，时间 2026 年 9 月 22 日。工具是四个子目录里的脚本，样本量与预热方式逐项记在对应日志里。

输入是固定的两条短样本，英文一条 86 字符的重复扣费投诉，中文是它的对应翻译约 25 字，metask 的 prompt 拆成 token 后 239 到 244 个。单次前向的耗时与输入长度成正比，真实业务输入更长，延迟会高于本表。要做容量规划，用自己的真实输入重测一遍。

分类题 20 条，命题判断 5 条。这个量级足以支撑上面的选型结论，因为它回答的是量级差异和结构性事实，不是百分位排名。Laya 中文 95% 与 metask 中文 100% 之间的差距不在本报告的结论范围内，`laya-zh-en.py` 自己也标了这条口径。

Qwen3-VL-4B 那组是在没有推理加速框架的情况下测的，属原生下界。部署时用上推理引擎会快一些，但判别式与生成式之间隔着的是成本结构，不是这一个数量级。

## 上游基准数据的取舍说明

metask 上游文档中列出了校准误差由 0.114 降至 0.040、JevBench 理论排名第一以及每千次决策 0.0029 美元等指标。在实际业务工单的实机测试中，上游的数据我们并未复现；且上游自述该榜单排名属于自测插值，未提交官方评测验证。

因此本报告在选型与对比中未采纳上述理论数字，全部指标均严格基于本地实机运行产生的日志记录（如 metask 方案端到端中位数延迟 133.7 ms 及中文场景 20/20 准确率）。

## 怎么选

只用英文、追求最低延迟和最小显存，选 Laya。8 到 17 ms，6 GB 显存，题数合并能把单题压到 2.83 ms。前提是场景不涉及中文的命题真假判断。

要中文，尤其是意图分类、工单分派、内容审核这类真假或分类判断，选 metask-jev-4B。133.7 ms 不算最快，但它中文 20 条全对，8.6 GB 显存，模型卡自带各题型的温度系数，拿来就能用。

Nimble 9B 在这三条里性价比最低。CUDA 路径上每个字段都要单独跑一次完整前向，上游 README 写得很清楚，Mac 上是共享一次前向后并行打分，CUDA 上不是。两个字段 365 ms，字段加到十个就是另一回事，加上 17.57 GB 的常驻显存是四条路线里最高的。字段数固定在两三个它能用，但相对 metask 看不到优势。

Qwen3-VL-4B 不是候选，是对照。有它做尺子，判别式模型的优势才说得清：不在绝对速度，在成本结构。输出多少字段都不影响耗时，这一点决定了这类模型适合放在高并发的决策路径上，不适合放在需要生成解释的地方。
