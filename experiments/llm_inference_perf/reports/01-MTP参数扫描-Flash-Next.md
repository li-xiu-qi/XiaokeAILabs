# Qwen3.8-Flash-Next 挂载 MTP 草稿头参数实验

## 职责声明

本报告为阶段性进展报告，记录在 GB10 统一内存硬件（DGX Spark 形态）上对超大参数稀疏激活模型 Qwen3.8-Flash-Next 挂载同源 MTP（Multi-Token Prediction）草稿头的投机解码参数探索。本阶段测试仅覆盖 125B 规模 MoE 架构在单请求串行场景下的吞吐与接受率表现，未涉及高并发请求与变长上下文扫描。本报告仅供追溯实验过程数据，完整选型与跨模型机制结论以《投机解码收益的机制条件》综合报告为准，不建议直接孤立引用本报告指标作为部署决策依据。

## 实验元信息

### 运行环境
- 硬件架构：GB10 统一内存架构设备（DGX Spark 形态），Linux aarch64，统一内存池，CUDA 13.0。
- 推理引擎：llama.cpp 源码编译构建，版本号 build 792（Git commit `a0e6dc7`，构建日期 2026-10-14）。
- 主模型配置：Qwen3.8-Flash-Next，IQ4_XS 量化分片（三分片 GGUF 文件总计 97.68 GB），总参约 180B（其中 MoE 主干 125B），单 token 激活参数量约 6B，内置 4B 规模 MTP 输出头。
- 草稿模型配置：`mtp-Qwen3.8-Flash-Next-Q8_0.gguf`，文件体积 4.14 GB，采用 Q8_0 量化精度。
- 服务启动参数：`-ngl 99 -c 262144 -np 1 -t 8 --cache-type-k q8_0 --cache-type-v q8_0`，投机解码配置挂载对应草稿模型路径，上下文长度配置为 262144 满档。

### 测量口径与开销
- 测量端点：服务端 `/completion` 原生端点，使用固定中文 Prompt（长度约 28 token），设置 `n_predict=400`，`temperature=0.7`。
- 测试状态：单客户端连续请求，单机独占运行，GPU 运行前确认处于正常频率与功耗状态（排除现代待机造成的能耗抑制）。
- 测量成本：主模型与草稿模型冷启动载入内存约耗时 70 秒，单次 400 token 生成请求耗时 11 至 15 秒。

### 变异性与干扰控制
同配置下模型生成长度与硬件瞬态对平均吞吐存在约 10% 的变异区间。例如同一配置在 `n_predict=200` 时实测生成吞吐为 31.8 t/s，在 `n_predict=400` 且固定长度时实测为 37.1 t/s。为消除这一扰动，本报告中所有基线与投机配置均在同一会话周期内、基于同一引擎构建版本、使用完全一致的 Prompt 与生成上限连续测量三轮以上。

## 125B 稀疏激活模型上的投机收益探索

投机解码的核心物理假设在于：主模型在解码（decode）阶段属于访存密集型任务，计算单元受制于内存带宽瓶颈，通过体积较小的草稿模型预先预测若干候选 token 并交由主模型单次前向验证，能有效平摊主模型的全量访存开销。

然而 Qwen3.8-Flash-Next 属于超大总参（约 180B，MoE 主干 125B）、极低激活参数量（约 6B）的 MoE 架构。主模型在解码单步中仅载入约 6B 参数对应的专家权重，访存带宽在 decode 阶段并非绝对瓶颈。当为其挂载一个参数量达 4B 的 MTP 草稿模型时，草稿生成本身引入的访存与前向计算开销，可能反噬投机带来的步长收益。本实验旨在检验在该架构下，同源 MTP 草稿能否带来端到端的吞吐收益。

## 基线与 MTP 参数实测对比

在严格锁定引擎构建 commit `a0e6dc7`、单槽位（`-np 1`）以及 `/completion` 接口的受控条件下，基线与 MTP 配置实测表现如下：

| 配置 | 生成吞吐 tg (t/s)，三轮 | 三轮均值 | 草稿接受率 |
|---|---|---:|---:|
| 原生基线（关闭投机） | 37.11 / 37.11 / 37.07 | 37.10 | 不适用 |
| MTP（n_max=2, p_min=0.75） | 34.10 / 39.42 / 38.12 | 37.21 | 78.7% 至 87.8% |

三轮测量的形态差异比均值差异更值得注意。基线三轮的生成吞吐几乎逐字重复，极差只有 0.04 t/s；MTP 三轮却在 34.10 到 39.42 t/s 之间大幅摆动，极差 5.3 t/s，约为均值的 14%。均值口径下两者只差 0.3%，落在 MTP 自身的波动区间之内。

这说明此前一轮测量得出的「MTP 净亏损 4.2%」属于单轮采样偏差，那一轮恰好落在 MTP 的向下波动上。样本量提到三轮后，稳定的结论是 125B MoE 上挂 MTP 没有可确证的吞吐收益，既无稳定增益，也无稳定亏损。

预填充端的损失倒是可重复的。同一 28 token 提示词下的首次请求，基线录得 87.25 t/s，MTP 录得 81.22 t/s，降幅 6.9%。草稿模型常驻内存后，预填充阶段主模型做密集矩阵乘法时的可用带宽被压缩，短提示词场景这块是净亏。

GPU 侧的旁证支持同一判断。基线推理期间 GPU 利用率稳定在 94% 至 95%、SM 时钟 2541 MHz、功耗 44.5 W；挂载 MTP 后利用率降到 73% 至 93%（均值约 82%）、时钟 2528 MHz、功耗 42 W。额外一路草稿前向把算力空档吃掉了一部分，却没有换回等量的输出 token。

## 高接受率为何换不来吞吐

本组实验中最值得解释的现象，是 78% 到 88% 的草稿接受率、2.28 的单轮平均接受长度（mean len），与零增长的生成吞吐并存。

常规经验把 60% 至 70% 的接受率视为投机解码盈利的门槛，在 125B MoE 场景下这条规律给出的预判完全落空。根因是成本结构错配：

主模型单步只激活约 6B 权重，访存开销本就低廉，减少前向次数的收益有限。同源 MTP 草稿头的体积为 4.14 GB、参数量约 4B，单次前向要搬的权重接近主模型单步激活量的三分之二。每轮平均多接住 1.28 个 token 所省下的主模型前向，抵不过草稿模型自己多跑的那些前向，以及两个模型在统一内存里交替调度带来的切换开销。

由此得到本阶段的判定：当草稿模型体量与主模型单步激活量相当，接受率再高也换不来吞吐，因为投机解码省的是前向次数，而这里前向次数本来就不是瓶颈。

## 测量陷阱与构建版本干扰

在本次参数探索过程中，记录到两个会对测试方向产生颠覆性影响的测量陷阱。完整排查过程与工程处置可查阅 `docs/调试与排错记录.md`。

第一个陷阱是推理引擎构建版本的迭代增益。早期探索阶段用旧版构建（commit `ccc3646`，2026-09-07）测得的基线生成吞吐为 30.45 t/s。如果直接拿这个数字去对比新构建（commit `a0e6dc7`，2026-10-14）下的 MTP 表现，会得出「MTP 提升了 12.8%」的虚假正收益。实际上，新构建仅凭底层算子与调度优化就把基线推高到 37 t/s 一线，构建迭代本身是 20% 量级的变量，远超 MTP 带来的那点差异。任何跨构建的对比都会让结论失真。

第二个陷阱是服务端的并发插槽配置。若启动参数未显式声明 `-np 1`，llama.cpp 默认启用 4 个并发插槽，并强行开启统一 KV 管理（`kv_unified=true`），导致单请求下的 KV Cache 被逻辑拆分。实测显示，同一套 MTP 参数在默认多插槽模式下草稿接受率只有 38.57%，显式指定 `-np 1` 后才回到 78% 至 88%。投机解码测试必须在单插槽受控环境下进行。
