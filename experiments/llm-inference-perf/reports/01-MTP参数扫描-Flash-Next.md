# Qwen3.8-Flash-Next 挂载 MTP 草稿头参数实验


> **历史记录阅读提示**：本报告保留当时的测量和分析，其概括性结论、机制归因和单槽硬约束未得到充分验证。当前可采用的结论及测量边界见 [三模型对照](03-三模型投机矩阵-任务类型与参数交互.md)；例如三个提示词无法区分任务类型与内容效应，多槽亦不能一概判定不可用。以下旧版修订声明如与此提示冲突，以此提示为准。

> **修订说明**：阶段一的单提示词结果不能推广为模型级结论。阶段二的三个提示词在 `n_max=3`、`p_min=0.0` 下出现 +16.4% 至 +57.0% 的收益，但每类任务仅一个提示词，无法区分任务和提示词内容的影响；也无法证明该参数普遍最优。单槽并非投机解码的普遍约束，历史 prefill 数据不足以证明可重复损失。

## 职责声明

本报告为阶段性进展报告，记录在 GB10 统一内存硬件（DGX Spark 形态）上对超大参数稀疏激活模型 Qwen3.8-Flash-Next 挂载同源 MTP（Multi-Token Prediction）草稿头的投机解码参数探索。本阶段测试仅覆盖 125B 规模 MoE 架构在单请求串行场景下的吞吐与接受率表现，未涉及高并发请求与变长上下文扫描。本报告仅供追溯实验过程数据，当前结果与限制见[三模型对照](03-三模型投机矩阵-任务类型与参数交互.md)，不建议直接孤立引用本报告指标作为部署决策依据。

## 实验元信息

### 运行环境
- 硬件架构：GB10 统一内存架构设备（DGX Spark 形态），Linux aarch64，统一内存池，CUDA 13.0。
- 推理引擎：llama.cpp 源码编译构建，版本号 build 792（Git commit `a0e6dc7`，构建日期 2026-10-14）。
- 主模型配置：Qwen3.8-Flash-Next，IQ4_XS 量化分片（三分片 GGUF 文件总计 97.68 GB），总参约 180B（其中 MoE 主干 125B），单 token 激活参数量约 6B，内置 4B 规模 MTP 输出头。
- 草稿模型配置：`mtp-Qwen3.8-Flash-Next-Q8_0.gguf`，文件体积 4.14 GB，采用 Q8_0 量化精度。
- 服务启动参数：`-ngl 99 -c 262144 -np 1 -t 8 --cache-type-k q8_0 --cache-type-v q8_0`，投机解码配置挂载对应草稿模型路径，上下文长度配置为 262144 满档。

### 测量口径与开销
- 测量端点：服务端 `/completion` 原生端点，使用固定中文 Prompt（长度约 28 token），设置 `n_predict=400`，`temperature=0.7`。
- 测试状态：单客户端连续请求，单机独占运行，GPU 运行前确认处于正常频率与功耗状态（排除现代待机造成的能耗抑制）。
- 测量成本：主模型与草稿模型冷启动载入内存约耗时 70 秒，单次 400 token 生成请求耗时 11 至 15 秒。

### 变异性与干扰控制
生成长度和硬件状态可能影响平均吞吐；阶段一原始逐次日志不完整，无法给出通用变异区间。例如同一配置在 `n_predict=200` 时实测生成吞吐为 31.8 t/s，在 `n_predict=400` 且固定长度时实测为 37.1 t/s。本报告记录基线与所列 MTP 档各三轮，但阶段一原始逐次响应未随仓库提供，无法独立核实所有测量条件及运行顺序；一致的设置也不能消除所有扰动。

## 125B 稀疏激活模型上的投机收益探索

投机解码先提出候选，再交由主模型验证；如果每次验证能推进更多 token 且额外开销足够低，就可能加速。实际计算与访存开销取决于实现和负载，本次没有分项测量。

Qwen3.8-Flash-Next 是总参约 180B、每 token 激活约 6B 的 MoE 架构。激活参数量不等于实际访存量，本实验没有测带宽或分项推理开销；草稿生成与验证也会增加成本，是否加速须实测。

## 基线与 MTP 参数实测对比

在严格锁定引擎构建 commit `a0e6dc7`、单槽位（`-np 1`）以及 `/completion` 接口的受控条件下，基线与 MTP 配置实测表现如下：

| 配置 | 生成吞吐 tg (t/s)，三轮 | 三轮均值 | 草稿接受率 |
|---|---|---:|---:|
| 原生基线（关闭投机） | 37.11 / 37.11 / 37.07 | 37.10 | 不适用 |
| MTP（n_max=2, p_min=0.75） | 34.10 / 39.42 / 38.12 | 37.21 | 78.7% 至 87.8% |

三轮测量的形态差异比均值差异更值得注意。基线三轮的生成吞吐几乎逐字重复，极差只有 0.04 t/s；MTP 三轮却在 34.10 到 39.42 t/s 之间大幅摆动，极差 5.3 t/s，约为均值的 14%。均值口径下两者只差 0.3%，落在 MTP 自身的波动区间之内。

此前单轮与这三轮的结果不同；这组三轮仅说明特定提示词和配置下未观察到清晰收益，不支持模型级结论。

记录中同一短提示词的 prefill 分别为 87.25 和 81.22 t/s；前缀缓存等条件未充分控制，不能把差异归因为草稿模型，也不能断言损失可重复。

记录的 GPU 利用率和功耗不足以确定各阶段耗时或开销原因。

## 高接受率为何换不来吞吐

本组实验中最值得解释的现象，是 78% 到 88% 的草稿接受率、2.28 的单轮平均接受长度（mean len），与零增长的生成吞吐并存。

接受率只是机制指标，收益还取决于每轮接受的 token 数及草稿和验证开销；本实验没有对这些开销分项计时，不能据参数量断定瓶颈或接受率门槛。

## 测量陷阱与构建版本干扰

在本次参数探索过程中，记录到两个会对测试方向产生颠覆性影响的测量陷阱。完整排查过程与工程处置可查阅 `docs/调试与排错记录.md`。

第一个陷阱是推理引擎构建版本的迭代增益。早期探索阶段用旧版构建（commit `ccc3646`，2026-09-07）测得的基线生成吞吐为 30.45 t/s。如果直接拿这个数字去对比新构建（commit `a0e6dc7`，2026-10-14）下的 MTP 表现，会得出「MTP 提升了 12.8%」的虚假正收益。两条基线记录相差约 22%；原始环境与代码差异没有完整保留，不能归因到具体算子或调度优化。跨构建比较需要控制其他变量并保留原始证据。

第二个需记录的变量是服务端槽位。历史四槽与单槽的接受率分别为 38.57% 和 78% 至 88%，但其他参数也不同，不能归因于槽位。本次记录不能证明单槽是普遍约束。
