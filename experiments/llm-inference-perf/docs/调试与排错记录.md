# 调试与排错记录

本文件收录会**直接影响结论方向**的测量陷阱与踩坑，按影响程度排序。凡"不单列就会被误读"的数字，都在这里给根因。

## 陷阱 1：引擎构建版本是强干扰变量（影响最大）

同一台机器、同一模型、同一参数，仅换 llama.cpp 的构建版本，基线生成吞吐差 **22%**：

| 构建 | 125B 基线 tg |
|---|---:|
| 旧构建（commit ccc3646，2026-09-07） | 30.45 t/s |
| 新构建（build 792，commit a0e6dc7，2026-10-14） | 37.10 t/s |

**后果**：用旧构建的基线去对比新构建的投机版，会得出「MTP 提升 +12.8%」的结论；换成同构建对比，真实差异只有 +0.3%，落在噪声内。机制的真实效应量被构建变量整个吞掉。

**纪律**：任何 A/B 必须锁定同一构建。这条是本实验返工过一次的直接原因，后续所有对比表都标注构建 commit。

## 陷阱 2：把单槽测试配置当作投机解码的通用限制

本实验的矩阵使用 `-np 1`，目的是固定单请求测量条件；一个槽位指一次服务一个序列，不是指一张显卡。历史排错记录曾记下 4 槽时接受率 38.57%、单槽时 78% 至 88%，但缺少足以独立复核的完整配置与逐次原始记录，无法从这组数字确定槽数是原因，更不能推断所有投机解码都要求单槽。

llama.cpp 的具体草稿方式、版本及并发配置可能有各自限制或故障；例如其 [DFlash 并发问题记录](https://github.com/ggml-org/llama.cpp/issues/27117) 描述了特定配置下接受率异常，并不构成所有多槽实现都不能工作的证据。需要并发服务时，应在相同构建、模型与负载下，测单槽和目标槽数的接受率、总吞吐以及每请求延迟。

## 陷阱 3：把接受率当成速度，或把参数偏好归因于草稿类型

草稿接受率上升不一定意味着生成速度上升：投机解码还要花时间生成草稿和验证候选。阈值改变时，接受率的分母及每轮草稿数量也可能改变，不能仅凭接受率判断哪个配置更快。投机采样原理和分布保证的适用条件见 [Leviathan 等，2023](https://proceedings.mlr.press/v202/leviathan23a.html)。

历史记录中不同槽位、模型、阈值和指标混在一起，不能据此证明 MTP 一定偏好某个 `p_min`、DFlash2 一定偏好另一个，更不能认定某类草稿的低置信度 token 必然是噪声。应固定具体引擎构建、主模型、草稿、量化、提示词、采样和槽数，分别记录生成速度、草稿数量和接受率，再比较阈值；[矩阵报告](../reports/03-三模型投机矩阵-任务类型与参数交互.md)保留了本实验范围内的对照。默认阈值也应检查实际构建的帮助信息，不能套用其他版本。

## 陷阱 4：thinking 模型的生成长度不可控，平均吞吐不可直接比

走 chat 端点时，模型自主决定思维链长度，两次运行的 completion 长度可能相差一倍（实测 216 vs 400 token）。llama.cpp 的 `predicted_per_second` 是全程平均，长度差异会引入偏差。

**处置**：机制对比走 `/completion` 端点并固定 `n_predict`，长度可控；chat 端点数据只作真实场景参考，不作 A/B 依据。更稳的做法是加 `ignore_eos` 强制跑满目标长度，实测基线三轮的生成吞吐极差可压到 0.04 t/s。

## 陷阱 5：草稿模型与引擎构建不匹配会直接加载失败

旧构建加载 MTP 草稿文件报错：

```
llama_model_load: error loading model: check_tensor_dims: tensor 'output_hc_norm.weight' not found
common_speculative_init_result: failed to load draft model
```

同一文件在新构建上正常加载。**这不是文件损坏**，是构建版本不认识草稿头的新张量结构。

**处置**：更新引擎到能识别该草稿头的 commit 后再测。更新源码用 `git pull`，重编译只需额外指定 CUDA 编译器路径（`-DCMAKE_CUDA_COMPILER=/usr/local/cuda/bin/nvcc`），否则 cmake 报缺 `CUDACXX`。

## 陷阱 6：服务默认只绑回环

部分参考配置给的启动参数是 `--host 127.0.0.1`，仅本机可达。跨机测试会表现为「连接超时 / 空响应」，容易被误判成服务没起来。

**处置**：跨机测试改 `--host 0.0.0.0`，并确认目标机防火墙放行该端口（默认策略常为 BlockInbound，只放行了 SSH）。

## 陷阱 7：笔记本形态设备的 Modern Standby 会让 GPU 时钟塌陷

Windows on Arm 笔记本在进入 Modern Standby（S0 低功耗空闲）再唤醒后，GPU 时钟与功耗不会自动恢复：

| 状态 | SM 时钟 | 功耗 | 同模型 tg |
|---|---|---:|---:|
| 干净态 | 2151–2223 MHz | 37–38 W | 34.64 t/s |
| 睡眠唤醒后 | 682–910 MHz | 4.0–5.1 W | 11–13 t/s |

`nvidia-smi -lgc` 锁频只能部分恢复，时钟恢复后吞吐仍低。

**处置**：这类设备做性能测试前先完整重启（选「重启」而非「关机」，避免快速启动带回脏状态），测完先确认时钟与功耗在正常区间再采信数字。这类数据只作劣化态参考，不进结论。

## 陷阱 8：远端后台起进程的写法

`ssh host "setsid nohup ./script.sh >> log 2>&1 < /dev/null & disown; echo OK"` 形式在部分环境下 ssh 不返回（超时），但进程实际已起；而在同一条命令里再跟 `kill` 或 `sleep`/`pgrep` 时，刚起的进程可能被一并带掉。

**处置**：启动与查状态分两条 ssh 命令发；启动命令用 `& disown` 收尾，不追加其他语句。
