# 从逐 token 生成到投机解码：如何理解推理速度

![自回归与投机解码执行节奏](decoding-paths.svg)

同一个模型，为什么一次能输出几十个 token，换一组草稿参数却可能更慢？理解这个问题，可以把模型生成拆成两段：先处理输入的 **prefill**，再逐步生成输出的 **decode**。本实验主要比较 decode 阶段的生成速度。它测到的是特定设备和设置下的结果，不是模型质量或线上 API 的性能排名。

## 自回归：为什么要一步一步生成

自回归模型把序列概率写成条件概率的乘积：

$$P(x_1,\ldots,x_n)=\prod_{t=1}^{n}P(x_t\mid x_{<t}).$$

例如生成“机器学习很有趣”，确定下一个 token 时要依赖之前已经生成的内容。注意力的 KV cache 保存历史中间结果，避免每一步重新计算整个前缀，但生成仍有逐步依赖。预填充阶段通常可对已知的输入 token 并行计算；解码阶段的单请求小批量工作负载则可能受到权重读取带宽限制。具体瓶颈取决于上下文、模型、批量和实现，不一定始终是内存带宽。

生成速度常用 token/s 衡量，token 是模型词表中的单位，不等于汉字数或单词数。首 token 时间、每用户生成速度与多用户总吞吐也各自回答不同问题。单请求读到 90 token/s 不等于 90 汉字每秒，也不能据此推出并发服务的每人速度。

## 投机解码：猜一段，再由目标模型验证

草稿模型先提出一串候选 token；目标模型在一次验证中计算这些位置的条件分布，按算法接受可用前缀并在拒绝处修正，然后从新前缀继续。草稿可以来自独立小模型、模型内的辅助预测模块，或已有 token 的 n-gram 匹配。

有概率校正的标准 speculative sampling 可保持目标模型的输出分布：若目标与草稿分布分别为 $p$、$q$，对草稿 token $y$ 的接受概率为 $\min(1,p(y)/q(y))$；拒绝时从相应残差分布采样。这个性质取决于具体算法及实现，不等于相同随机种子下输出逐字相同，也不意味着所有加速模式都有同样的保证。[Leviathan 等，2023](https://proceedings.mlr.press/v202/leviathan23a.html)

一次验证处理多个候选位置时，模型权重和计算可以得到更好的复用；如果每轮接受多个 token，就有机会减少目标模型的串行调用。加速不是免费的：草稿生成、验证和调度都要花时间。可以用一个简化的记账方式理解，而不是拿它代替实测：

$$\text{加速比}=\frac{\text{基线生成时间}}{\text{草稿生成时间}+\text{目标验证时间}+\text{其他开销}}.$$

这里两边必须是生成相同数量 token 的总耗时。接受率上升并不自动意味着加速：较短的草稿可能更容易被接受，却让每轮可接受的 token 数变少；不同草稿实现的额外开销也不同。实际部署应测生成速度、首 token 时间及并发吞吐，而不是只看接受率。

## MTP 与投机解码是什么关系

**多 token 预测（MTP）是模型训练或架构层面的预测方式，投机解码是推理时的验证流程。** 常见自回归训练要求预测下一个 token；MTP 还提供对后续位置的预测目标。具体结构并不唯一，例如 DeepSeek-V3 技术报告描述了保持因果链的多 token 预测模块，并讨论将其用于推理加速。[DeepSeek-V3 技术报告](https://arxiv.org/abs/2412.19437)

MTP 模块可以担当草稿来源，后面仍需由目标模型验证；拥有 MTP 不意味着部署时自动启用投机解码，也不意味着所有 MTP 草稿都来自独立模型文件。我们的矩阵同时包含外置 MTP、内置 MTP 与 DFlash2 草稿，不能把它们的差距直接解释为 MTP 与非 MTP 的纯粹对比。[llama.cpp 投机解码文档](https://github.com/ggml-org/llama.cpp/blob/master/docs/speculative.md)

## 稠密模型与 MoE：容量和每步计算是两件事

稠密模型的前馈层对每个 token 使用同一套参数；混合专家模型（MoE）的路由器为 token 选择部分专家，其他共享层仍参与计算。例如，一个假想的 8 专家层每次选 2 个专家：模型需要保存全部专家，单个 token 的专家计算只使用其中两个。总参数、每 token 激活参数与模型文件大小因此是不同指标。

| 问题 | 稠密模型 | MoE 模型 |
|---|---|---|
| 参数容量 | 主要由模型总参数决定 | 总参数包含全部专家 |
| 单 token 的专家计算 | 使用完整前馈层 | 路由选择部分专家，仍有共享层和路由开销 |
| 内存容量 | 需容纳加载的权重、KV cache 和运行缓冲 | 通常也需容纳全部驻留权重；卸载或分层缓存可改变需求，但会引入传输开销 |
| 速度判断 | 看量化、带宽、计算、批量与上下文 | 还要看专家分布、路由和调度；不能只用激活参数预测 |

模型文件大小也不是完整运行内存；量化、KV cache、工作区、投机草稿和系统开销都影响峰值。多 token 同时处理可能选中不同专家，因此批量计算的实际权重复用需要测量。MoE 能用较小的每 token 激活计算访问更大的总模型容量，但不保证比任意稠密模型更快或质量更好。[Hugging Face MoE 架构说明](https://huggingface.co/blog/moe-transformers)

## 如何把它用于自己的部署

先固定模型文件、量化、引擎构建、上下文上限、采样设置和请求长度，分别启动无投机基线及草稿配置。每组暖机后多次运行，保存服务日志及响应的 timing，再算 $\text{投机生成速度}/\text{基线生成速度}-1$。至少为实际用途准备多条提示词，分别测试短长输入；需要并发服务时还要测不同并发数的总吞吐和每用户延迟。

仓库 [三模型实测报告](../reports/03-三模型投机矩阵-任务类型与参数交互.md) 给出具体命令配置、三轮均值、标准差和原始记录入口。每类仅一个提示词，结果可作为选择下一轮测试配置的线索，不能证明某种任务或模型结构普遍更快。
