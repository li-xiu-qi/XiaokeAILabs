# 向量索引如何交换计算量、召回与内存

假设文档已经编码为向量，用户问题也编码为向量。向量检索要找出与问题最接近的若干文档。直接比较全部文档最容易验证正确性；当文档增多时，索引可以减少需要检查的候选、缩短每个向量的表示，或同时做这两件事。本篇解释这些路径、代价及估算方法；数值实测见[合成数据对照](合成向量索引对照.md)。

## 相似度与正确答案

设查询为 $q$，候选向量为 $x_i$。余弦相似度与平方欧氏距离分别为：

$$
\cos(q,x_i)=\frac{q^{\mathsf T}x_i}{\lVert q\rVert_2\lVert x_i\rVert_2},\qquad
d^2(q,x_i)=\lVert q-x_i\rVert_2^2.
$$

若查询与候选都归一化到单位长度，$d^2(q,x_i)=2-2q^{\mathsf T}x_i$，因此精确内积从大到小与精确平方距离从小到大的排名一致。这个等价依赖单位长度；量化重建后的向量不一定仍为单位长度，不应把不同度量下的压缩结果直接当作同一对照。[Faiss 距离说明](https://github.com/facebookresearch/faiss/wiki/MetricType-and-distances)对这一前提有明确说明。

先用 Flat 得到精确 Top-$k$ 集合 $G_k$，近似索引得到 $A_k$。对 $Q$ 条查询，向量近邻召回率为：

$$
\operatorname{Recall@}k=\frac{1}{Q}\sum_{i=1}^{Q}\frac{|A_k^{(i)}\cap G_k^{(i)}|}{k}.
$$

这衡量索引是否找回精确向量近邻，不衡量这些文档是否能回答问题。后者还需独立相关性标注、Embedding 模型评估与端到端测试。距离完全相同时，集合比较还可能受并列结果选择影响。

## 四条检索路径

### Flat：逐个计算

存储 $N$ 条 $d$ 维向量，查询时对全部向量计算距离，选最接近的 $k$ 个。单查询的距离计算量随 $Nd$ 增长。顺序读取、向量化和批处理可以让暴力扫描非常高效，因此小规模时 Flat 完全可能快于近似索引。Flat 不需要训练索引，适合生成基准和数据规模可控的场景。

### IVF：先定位分区，再扫描分区

建立索引时先训练 `nlist` 个聚类中心，每个向量分配到一个中心对应的倒排列表。查询时先比较中心，选择最接近的 `nprobe` 个列表，再对其中的向量计算距离。正确答案所在的列表没有被选中时，即使列表内距离计算精确也找不回来。

假设列表完全均匀，扫描的候选数约为 $N\cdot\texttt{nprobe}/\texttt{nlist}$；真实数据的列表大小往往不均匀。提高 `nprobe` 通常提升召回，同时增加扫描量；提高 `nlist` 会改变中心训练、分区数量和路由成本，不能孤立断言越大越快。需要有足够且有代表性的训练向量，数据分布变化后也要重新评估聚类质量。

### HNSW：沿多层近邻图导航

向量是图节点，边把邻近节点连起来。搜索从高层的入口节点出发，沿图向查询附近移动，逐层进入更稠密的图，最底层扩展候选并输出近邻。它通过图的连接关系避开全量扫描，但也可能错过更优路径。

`M` 影响建图时的连接规模、内存与搜索路径；`efConstruction` 控制建图探索的宽度；`efSearch` 控制查询时保留和探索的候选范围。增大搜索范围通常提高召回并增加查询工作量，实际结果由数据、实现和参数共同决定。图访问更不规则，距离计算少不一定意味着实际耗时低。Faiss 的 `IndexHNSWFlat` 存储完整向量及图结构；其他实现或图与量化的组合有不同成本。

### SQ 与 PQ：先压缩表示，再近似计算

标量量化 SQ 分别压缩各个维度；SQ8 通常以 8 bit 保存每个维度的编码。乘积量化 PQ 把 $d$ 维向量划为 $m$ 个子向量，每个子空间学习 $2^b$ 个码字；每个子向量只保存对应码字编号。查询时可先算查询各子向量到码字的距离，再通过查表累加近似距离，不必逐个还原完整向量。

量化的误差可能改变排名；更短的编码也不保证更快，因为查表、扫描方式和硬件实现均有代价。IVF-PQ 先定位分区，再使用 PQ 压缩候选，它同时有分区漏召回和量化排名误差。只增大 `nprobe` 不能消除 PQ 本身的误差。

保留原始向量时，可先取更大的候选集，再用原始距离重排，降低候选内的量化排序误差；没有进入候选的结果仍找不回。原始向量占用必须算进总成本。Faiss 各索引的存储形式见[索引类型说明](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)。

## 内存从哪里来

以下估算针对 Faiss 常见 CPU 索引，向量为 float32，每个数 4 字节。只计算主体，未包含进程、分配器、查询工作区、对象元数据或额外副本。$n_l$ 为 `nlist`，$m$ 为 PQ 子空间数，$b$ 为每个编号的位数，$M$ 为 HNSW 参数。

| 索引 | 主体大小估算，单位字节 | 组成 |
|---|---:|---|
| Flat | $4Nd$ | 每条向量 $d$ 个 float32 |
| SQ8 | $Nd+O(d)$ | 每维 1 字节，加量化参数 |
| PQ | $N\lceil mb/8\rceil+4d2^b$ | 每条编码加全部子空间码本，假设 $d$ 可被 $m$ 整除 |
| IVF-Flat | $4Nd+8N+4n_ld$ | 原始向量、每条 8 字节 ID、float32 聚类中心 |
| IVF-PQ | $N(\lceil mb/8\rceil+8)+4d2^b+4n_ld$ | 压缩码、ID、PQ 码本、聚类中心 |
| HNSW-Flat | $4Nd+8MN+O(N)$ | 完整向量与粗略的底层图边；高层边和实现开销另计 |

PQ 码本项可以这样得到：每个子空间有 $2^b$ 个码字，每个码字有 $d/m$ 个 float32 数，共 $m\times2^b\times(d/m)\times4=4d2^b$ 字节。Faiss 的 IVF 列表另外保存每条向量的 64 位 ID。HNSW 粗略式假设底层最多约 $2M$ 个 32 位邻居槽，实际图层、数组与分配方式会改变结果。

例如 $N=20{,}000,d=128,m=8,b=8,n_l=64$ 时，原始向量是 10,240,000 字节；PQ 编码是 160,000 字节，码本 131,072 字节，主体合计 291,072 字节。一次 Faiss 序列化得到 291,158 字节，差值含格式元数据；这个比较不是进程内存或峰值内存。IVF-PQ 还需列表 ID 与中心，本次序列化为 484,532 字节。实测配置和全部字节数见[证据文件](../evidence/synthetic_n20000_d128_20261107.json)。

## 实际使用顺序

1. 固定业务上的向量模型、归一化规则、距离、过滤条件与查询样本。对足够有代表性的样本运行 Flat，保存精确近邻。
2. 先确定可接受召回与延迟，再扫描 `nprobe` 或 `efSearch`；在相近召回下比较延迟、吞吐、构建时间和索引体积。区分单请求延迟与批处理平均值。
3. 空间紧张时评估 SQ/PQ 或 IVF-PQ，检查候选放大和精排是否能恢复质量，并计入原始向量、元数据、工作区和副本。
4. 把真实写入、删除、更新、过滤、并发、冷启动与内存峰值纳入系统级实验。不同库在这些操作及实现细节上可能不同，不能由索引名字推断生产性能。

先用满足质量要求的最简单方案建立基线，再根据实际瓶颈增加索引复杂度。合成随机向量可以检查实现和展示机制，不能代替业务向量的分布与相关性评估。
