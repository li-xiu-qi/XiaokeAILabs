# 排错记录

七条踩坑，按出现顺序。每条给出现象、根因和判据，判据是下次遇到同类现象时直接用的那个。

## 1. hf-mirror 下 LFS 文件停在 1 KB 后彻底静默

现象：`hf-mirror.com/<repo>/resolve/main/model.safetensors` 下载到 1106 字节后长时间零进度，curl 不报错。

根因：hf-mirror 现在只代理非 LFS 小文件，LFS 文件返回 308 跳 `huggingface.co`，再 302 到 `us.aws.cdn.hf.co`。Spark 上 `huggingface.co` 官方域不通，拿不到签发的 policy；而 `us.aws.cdn.hf.co` 本身是通的，单看 CDN 可达性会误判成「网络没问题，再等等」。

判据：下载源按文件类型分工判断，不按域名通断判断。非 LFS 小文件走 hf-mirror，LFS 大文件走 ModelScope。`curl -I` 看有没有 308/302，有就说明这条链在本机走不通。

## 2. git clone 在 GnuTLS 层被 reset

现象：`git clone --depth 1 https://github.com/OpenBMB/MiniCPM-OCR.git` 三分钟只下 124 KB，最后报 `GnuTLS recv error (-110)`。

根因：不是仓库大，是 git 的 TLS 通道在这台机器上不稳。同一个域名用 `curl` 直连 raw 文件是好的（实测 8.8 MB/s）。

判据：git 协议不通不等于网络不通。拉源码优先 `codeload.github.com/<org>/<repo>/tar.gz/<ref>` 的 tar 包，单条 HTTPS 可续传，比 git clone 快也稳。

## 3. pip 整树解析在拉大包时卡死

现象：连接活着，零流量，长时间无进度。

根因：既有环境里已知的问题，本次复现一次。

判据：逐包 `--no-deps` 升级，不做整树解析。torch 这类大包直接从同机既有 venv 复制 site-packages，NVMe 上 6.8 GB 只要 30 秒。

## 4. transformers serve 对未知字段回 422

现象：SDK 发请求后每个区域都失败，表现为任务长时间等待。

根因：serve 的请求校验用字段白名单，SDK 的 vLLM 方言多发四个字段，直接 `422 Unexpected fields`。

判据：接第三方 OpenAI 兼容服务时，先拿客户端实际会发的 payload 打一次，再决定用哪个方言。字段对不上就换 dialect，不要改服务端。

## 5. force_model 模式下 model 名必须是绝对路径

现象：`400 Server is pinned to '<目录>'; requested 'minicpm-ocr'`。

根因：`transformers serve <目录>` 把请求钉死到那个目录，`/v1/models` 列表和请求里的 model 是两套。

判据：这种启动方式下，客户端配置的 model 字段填模型目录绝对路径。健康检查显示 `model_match: false` 是预期的，不用追。

## 6. 自渲染测试页用拉丁字体渲染中文出豆腐块

现象：模型把表格表头输出成 `□□`，一度误判成模型不识别的中文表头。

根因：测试页生成脚本对表头行用了 Arial，中文没有字形，PIL 画出豆腐块，模型照抄。

判据：质量异常先验证测试输入本身。用像素统计确认渲染区有墨（本次标题带 8165 个暗像素、正文带 9555，都不是空白），再用带 CJK 字形的字体重渲染。修好后同一张表头识别正确，证明是输入问题不是模型问题。

## 7. mem-guard 的 pattern 表不覆盖新进程族

现象：新起的推理服务不在看门狗监控内，内存尖峰时不会被兜底。

根因：看门狗按 `TARGET_PATTERNS` 匹配进程命令行，新部署的 venv 路径不在表里。

判据：换新模型、新引擎、新脚本先核 pattern 是否命中，不命中就补，补完重启服务并核 `is-active` 与 `is-enabled`。本次补的是 `minicpm-ocr/.venv-ocr/bin/python`，一条覆盖 transformers serve、SDK 解析和冒烟三类进程。补丁见 `artifacts/mem_guard.patch`。
