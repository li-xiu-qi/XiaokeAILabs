# MiniCPM-OCR 部署实录

这份文档是主报告，结论以它为准。它记录 2026-10-28 在 DGX Spark 上把 MiniCPM-OCR 1.0 跑通的完整过程：为什么绕开官方主路线、实测数据、以及这些数字在什么范围内成立。

## 测了什么，没测什么

测的是「这条替代路线能不能跑通，跑通的代价是多少」。输入是三类：一张自渲染的 A4 页（中文标题与段落、英文段落、4×4 表格、两条公式）、官方仓给的两条法文真实裁切样张、以及同一张自渲染页转出的 PDF。输出按 SDK 的 Markdown 组装规则核对。

没测的是模型在真实文档分布上的通用准确率，没有跑 OmniDocBench 或任何官方基准，也没有和多模型横向对比。所有质量结论只对上面三类输入成立，不外推。

## 为什么绕开官方主路线

官方 `docs/SKILL_en.md` 给的主路线是 sdk-env 加 vllm-ocr-env，DSpark 投机解码加速。三个环节在这台机器上分别撞墙，替代方案逐个如下。

**布局检测不能装 Paddle。** `paddlepaddle` 与 `paddlepaddle-gpu` 在 PyPI 只发布 x86_64 和 macos arm64 轮子，没有 linux aarch64，官方 `scripts/install.sh sdk-gpu` 与 `sdk-cpu` 两个 profile 都装不上。SDK 里另有第三个布局 provider `ppdoclayout3_torch`，纯 torch 加 numpy 后处理，配 `PaddlePaddle/PP-DocLayoutV3_safetensors`（`model_type=pp_doclayout_v3`）。它的 docstring 声明 batch_size=1 时与 PaddleX 参考实现坐标一致，本次全部按单页跑，没有触发批量路径。它仍然 `import cv2`，补装 `opencv-contrib-python==4.11.0.86`（有 aarch64 轮子，与 numpy 1.26.4 兼容）。

**推理服务不能用 vLLM 或 SGLang。** `scripts/install.sh` 对这两个 profile 有 `uname -m == x86_64` 硬校验，本机是 aarch64；且这台机器的 Docker Hub 与国内镜像站本来就不通，官方镜像路线也断。官方文档列了 `transformers serve` 作为备选后端，本次走这条。

**transformers 不能用 PyPI 版。** `minicpm_ocr` 架构 2026-10-26 才合入上游 main，PyPI 最新的 5.21.0 里没有对应文件。按官方仓 `pyproject.toml` 的 pin 装源码 commit `549e5b41`，用 `pip install --no-deps -e`。该 commit 要求 `huggingface_hub>=1.31`，从既有环境复制过来的 1.16.1 需要升级。

## SDK 与推理服务的对接口径

SDK 的 `vllm` 方言会在请求体里塞 `mm_processor_kwargs`、`top_k`、`repetition_penalty`、`no_repeat_ngram_size` 四个字段，transformers serve 的请求白名单会直接回 422。解法是把引擎类型改成 `openai`（只发 model、messages、max_tokens、stream、temperature、top_p），采样参数改走 `generation_config` 字段传 JSON 串，serve 会解析成 `GenerationConfig`。`mm_processor_kwargs` 省略没有损失：模型的 `preprocessor_config.json` 默认就是 `downsample_mode=4x, max_slice_nums=9`，与 SDK 要发的一致。

另一个口径细节：`transformers serve <模型目录>` 用 force_model 模式后，请求里的 `model` 必须填模型目录的绝对路径，填 `minicpm-ocr` 会被 400 拒绝。WebUI 健康检查里的 `model_match: false` 由此而来，`/v1/models` 列的是本机 HF 缓存里的其他模型，仅展示用，不影响识别。

## 实测数据

| 项 | 值 | 口径 |
|---|---|---|
| 端到端解析一页 A4 | 11.22 秒 | `/usr/bin/time` 包整条 CLI，含进程启动、布局模型加载、约 12 个区域识别 |
| WebUI 上传到出结果 | 9.75 秒 | 一个 A4 PDF，单页，任务状态 queued 到 done |
| 显存峰值 | 3.0 GiB | `torch.cuda.max_memory_allocated` |
| 进程 RSS 峰值 | 2.3 GB | `/usr/bin/time` 的 Maximum resident set size |
| 权重下载 | 2.5 GB，约 15 MB/s | ModelScope 单流，与既有观察的 20 MB/s 量级一致 |
| 环境构建 | venv 复制 30 秒，源码拉取约 5 分钟 | torch 从既有环境整份复制，未重新下载 |

质量核对结果：中文段落、英文段落、表格（含中文表头「模型 / 参数量 / 吞吐 (页/秒) / 准确率」）、公式（转 LaTeX）、阅读顺序全部正确；法文真实样张识别结果与直接推理一致。两处已知弱项：堆叠上下标（`∫₀^∞`、`e^(−x²)`）被读成 `\Box`、`\Lambda` 一类近似符号；`∇` 同样读成 `\Box`。页脚页眉被布局模型标为 footer/header，按 SDK 默认 `ignore_labels` 不进 Markdown，是设计行为不是漏识别。

官方宣称的 1.2 页/秒是 RTX 5090 口径，本次没有复测，也不把 11.22 秒换算成官方可比数字：本机是统一内存 273 GB/s 带宽，且 `causal-conv1d` 与 `flash-linear-attention` 两个 kernel 在 aarch64 没有预编译轮子、当前走参考实现，两个条件都和官方口径不同。

## 结论在什么范围成立

路线可行性这条结论不绑定具体机器型号，绑定的是三个约束：aarch64、统一内存、无 Paddle 轮子。换到 x86 机器上官方主路线更优，不必照搬本方案。速度与显存数字只对本次固定配置成立，换 `max_slice_nums`、换并发、换是否启用 speculative decoding 都会变。

## 限制

没有跨机器复现，没有真实文档批量的质量证据，没有多轮性能分布（三项对应 README 里未达成的门槛）。WebUI 的版面校正开关不可用，它依赖 PaddleOCR 的三个小模型，本机没有 Paddle 轮子，runner 捕获异常后自动跳过，不影响解析结果。服务没有配自启，机器重启后要手动起。
